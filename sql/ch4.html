Running Totals & Period-over-Period

Time-series analysis is the most common reason analysts reach for window functions. Running totals accumulate a metric row by row. Period-over-period comparisons measure growth by looking at the same metric in the prior period. Rolling averages smooth out noise over a moving window. All three patterns combine SUM OVER, LAG, and frame specifications.

SUM() OVER (ORDER BY … ROWS BETWEEN …) LAG for MoM Rolling 3-month avg
Core Concept

Frames — Controlling Which Rows the Window Includes

When you add ORDER BY inside OVER(), the default window frame becomes "all rows from the start of the partition up to and including the current row". This is what makes running totals work — each row sees all prior rows.

You can make this explicit with a ROWS BETWEEN frame clause:

  • ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — cumulative total (default with ORDER BY)
  • ROWS BETWEEN 2 PRECEDING AND CURRENT ROW — current row plus 2 rows before = 3-row rolling window
  • ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING — all rows (same as no ORDER BY)
Syntax Anatomy — Running Total + Rolling Average
-- Running total (cumulative from row 1 to current row)
SUM(revenue) OVER (← ORDER BY makes this cumulative
ORDER BY monthdefault frame = UNBOUNDED PRECEDING → CURRENT ROW
) AS running_total
-- Rolling 3-month average (current + 2 prior months)
AVG(revenue) OVER (← explicit frame clause
ORDER BY month
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW3 rows: current + 2 before
) AS rolling_3m_avg
Tasks
TASK 4.1 Monthly Revenue With Running Cumulative Total
Business Question
Show monthly revenue for 2024, plus a running cumulative total that grows with each month. Return month, monthly_revenue, and cumulative_revenue.
Thinking — How to Construct This Query
1CTE — monthly: GROUP BY month, SUM revenue. This produces one row per month with that month's total.
2Running total: In the outer query, SUM(monthly_revenue) OVER (ORDER BY month). Because ORDER BY is present, the default frame is UNBOUNDED PRECEDING → CURRENT ROW. Each month's row sees itself plus all earlier months.
3No PARTITION BY: We want one running total across all months, not restarting per group. Omitting PARTITION BY treats all rows as one window.
4Verification: The last month's cumulative_revenue should equal the SUM of all monthly revenues. In our data: 9330.00.
Solution
WITH
monthly AS (
    SELECT
        MONTH(payment_date)   AS month,
        SUM(amount)           AS monthly_revenue
    FROM   payments
    WHERE  status = 'completed'
      AND  YEAR(payment_date) = 2024
    GROUP BY MONTH(payment_date)
)
SELECT
    month,
    monthly_revenue,
    SUM(monthly_revenue) OVER (
        ORDER BY month
        -- default frame: UNBOUNDED PRECEDING → CURRENT ROW
    ) AS cumulative_revenue
FROM   monthly
ORDER BY month;

TASK 4.2 Month-over-Month Revenue Growth Percentage
Business Question
For each month in 2024, show monthly revenue, the previous month's revenue, and the percentage change. Format growth as a percentage rounded to 1 decimal place.
Thinking — How to Construct This Query
1CTE — monthly totals: Same aggregation as Task 4.1 — GROUP BY month.
2LAG for prior month: LAG(monthly_revenue, 1) OVER (ORDER BY month) gives the previous month's revenue. Month 2 (February) has no prior row, so LAG returns NULL.
3MoM % formula: (current - prior) / prior * 100. Guard against division by zero with NULLIF: / NULLIF(prior, 0) — this returns NULL instead of an error when prior = 0.
4CASE for first month: Use CASE or COALESCE to display 'N/A' or NULL for the first month where there's no prior period to compare against.
Solution
WITH
monthly AS (
    SELECT
        MONTH(payment_date)  AS month,
        SUM(amount)          AS monthly_revenue
    FROM   payments
    WHERE  status = 'completed'
      AND  YEAR(payment_date) = 2024
    GROUP BY MONTH(payment_date)
)
SELECT
    month,
    monthly_revenue,
    LAG(monthly_revenue, 1) OVER (ORDER BY month)  AS prev_month_revenue,
    ROUND(
        (monthly_revenue - LAG(monthly_revenue, 1) OVER (ORDER BY month))
        / NULLIF(LAG(monthly_revenue, 1) OVER (ORDER BY month), 0)
        * 100
    , 1)                                                AS mom_pct_change
FROM   monthly
ORDER BY month;

TASK 4.3 3-Month Rolling Average Revenue
Business Question
For each month, show the monthly revenue alongside a 3-month rolling average (current month + 2 prior months). Rolling averages smooth out noise and reveal underlying trends.
Thinking — How to Construct This Query
1ROWS BETWEEN 2 PRECEDING AND CURRENT ROW: This tells the window to include the current row and exactly 2 rows before it — a 3-row window. If fewer than 2 prior rows exist (first two months), AVG uses however many rows are available.
2AVG vs SUM: AVG(monthly_revenue) OVER (...) automatically divides by the number of rows in the frame. For the first month (only 1 row in frame), it returns that month's value. For month 2, average of 2. From month 3 onwards, average of 3.
3ROWS vs RANGE: ROWS BETWEEN counts physical rows. RANGE BETWEEN counts by value. For sequential months with no gaps, they're equivalent. Use ROWS for counting actual rows; use RANGE when you want "all rows within ±N of the current value".
Solution
WITH
monthly AS (
    SELECT
        MONTH(payment_date)  AS month,
        SUM(amount)          AS monthly_revenue
    FROM   payments
    WHERE  status = 'completed'
      AND  YEAR(payment_date) = 2024
    GROUP BY MONTH(payment_date)
)
SELECT
    month,
    monthly_revenue,
    ROUND(
        AVG(monthly_revenue) OVER (
            ORDER BY month
            ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
        )
    , 2) AS rolling_3m_avg
FROM   monthly
ORDER BY month;

💡
Rolling avg vs cumulative: The cumulative total always grows. The rolling average only looks at a fixed window, so it can go up or down. Rolling averages are better for trend detection; cumulative totals are better for "how much have we made so far this year?"
