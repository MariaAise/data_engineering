Chapter 01 · MySQL 8.0

CTEs & Multi-Step Logic

A CTE (Common Table Expression) is a named intermediate result you define before your main query. Instead of nesting subqueries inside each other, you write each logical step as a named block — then reference those names like tables. The result: queries that read top-to-bottom like a recipe instead of inside-out like a puzzle.

WITH … AS (…) Chained CTEs CROSS JOIN scalar Self-join via CTE
Core Concept

What is a CTE and why does it exist?

SQL evaluates queries inside-out. A subquery buried three levels deep is correct but unreadable. CTEs solve this by letting you name each logical step and reference it by name.

Think of it like assigning variables in code. Instead of writing the same complex expression three times, you compute it once, give it a name, and use the name.

  • Readability — logic flows top to bottom, step by step
  • Reusability — the same CTE can appear multiple times in the main query
  • Chaining — a later CTE can reference an earlier one, layering complexity cleanly
  • Scope — CTEs exist only for the duration of the one query; they don't persist

Performance note: In MySQL 8.0, non-recursive CTEs are materialised or merged depending on the optimiser. They are not automatically faster than subqueries — the value is clarity, not speed.

✓ Use a CTE when

You need to aggregate before filtering on that aggregate. You reference the same derived data more than once. A nested subquery exceeds two levels. You want to self-join a derived result.

✗ Skip CTEs when

A simple JOIN + WHERE answers the question in one step. The "subquery" is a single trivial expression. A window function already solves it inline without an intermediate step.

Syntax Anatomy — Simple CTE
WITH cte_name AS (← keyword WITH starts the CTE block; name it anything
SELECT customer_id, SUM(amount) AS total← the CTE body is any valid SELECT
FROM payments
GROUP BY customer_id
)← close the CTE body with )
SELECT * FROM cte_name WHERE total > 500;← main query — reference the CTE by name like a table
Syntax Anatomy — Chained CTEs (CTE references a prior CTE)
WITH← WITH appears exactly once, before all CTEs
step_one AS (← first CTE defined here
SELECT customer_id, SUM(amount) AS total_paid
FROM payments GROUP BY customer_id
),← comma separates CTEs — never a semicolon
step_two AS (← second CTE — can query step_one directly
SELECT * FROM step_one WHERE total_paid > 500← reference earlier CTE by name
)
SELECT * FROM step_two;← main query — no comma before this line
Tasks
TASK 1.1 High-Value Customers — Filter on an Aggregated Intermediate
Business Question
Find customers whose total completed payments exceed the average total spend across all customers. Return their name, region, and total_paid, ordered by total_paid descending.
Thinking — How to Construct This Query
1Why can't this be one query? You need to compare each customer's total to the average of all totals. That's two levels of aggregation. You cannot write WHERE SUM(amount) > AVG(SUM(amount)) — aggregates can't nest like that in a WHERE clause.
2CTE 1 — customer_totals: Group payments by customer_id, SUM the amount. This gives one row per customer with their total.
3CTE 2 — avg_spend: SELECT AVG(total_paid) from CTE 1. This returns exactly one row — a single scalar value.
4Main query: JOIN customer_totals to customers for the name/region. CROSS JOIN avg_spend to bring the average into every row (one row × one row = same one row, so it's safe). Filter WHERE total_paid > avg_total.
5Why CROSS JOIN for the scalar? avg_spend returns one row. CROSS JOIN multiplies each customer row by that one row, effectively adding the average as a new column on every row — without changing the row count.
Solution
WITH
-- Step 1: total completed payments per customer
customer_totals AS (
    SELECT
        customer_id,
        SUM(amount) AS total_paid
    FROM   payments
    WHERE  status = 'completed'
    GROUP BY customer_id
),
-- Step 2: average of those totals (returns 1 row, 1 column)
avg_spend AS (
    SELECT AVG(total_paid) AS avg_total
    FROM   customer_totals
)
SELECT
    c.name,
    c.region,
    ct.total_paid
FROM       customer_totals  ct
JOIN       customers        c  ON ct.customer_id = c.customer_id
CROSS JOIN avg_spend          a  -- broadcasts the scalar into every row
WHERE  ct.total_paid > a.avg_total
ORDER BY   ct.total_paid DESC;

Key insight: CTE 2 queries CTE 1 — this is chaining. You never have to re-aggregate the payments table a second time. Each step builds cleanly on the one before it.
TASK 1.2 Plan Revenue Share — Percentage of Total per Group
Business Question
For each plan, show total revenue, the company grand total, and that plan's percentage share of total revenue. Order by revenue descending.
Thinking — How to Construct This Query
1CTE 1 — plan_revenue: JOIN payments to plans, GROUP BY plan_name, SUM amount. One row per plan.
2CTE 2 — grand_total: SUM all revenue from CTE 1. One row, one number.
3Main query: CROSS JOIN the two CTEs. Compute ROUND(revenue / total * 100, 1) for the percentage. Because grand_total is one row, CROSS JOIN just adds that column without multiplying rows.
4Alternative: Chapter 4 covers SUM(revenue) OVER() which solves this in one CTE. Understanding the two-CTE approach first builds the muscle for chaining — then the window function version feels like a natural shortcut.
Solution
WITH
plan_revenue AS (
    SELECT
        pl.plan_name,
        SUM(p.amount) AS revenue
    FROM   payments p
    JOIN   plans    pl ON p.plan_id = pl.plan_id
    WHERE  p.status = 'completed'
    GROUP BY pl.plan_name
),
grand_total AS (
    SELECT SUM(revenue) AS total
    FROM   plan_revenue     -- CTE referencing another CTE
)
SELECT
    pr.plan_name,
    pr.revenue,
    gt.total                                   AS grand_total,
    ROUND(pr.revenue / gt.total * 100, 1)    AS pct_of_total
FROM       plan_revenue pr
CROSS JOIN grand_total  gt
ORDER BY   pr.revenue DESC;

TASK 1.3 Plan Upgrades — Self-Join a CTE to Compare Rows
Business Question
Find customers who upgraded their plan — meaning they have a later subscription with a higher tier_level than an earlier one. Return customer name, from_plan, to_plan, and both start dates.
Thinking — How to Construct This Query
1The problem shape: An "upgrade" involves two rows in the subscriptions table for the same customer, where the later row has a higher tier_level. This means comparing a table against itself — a self-join.
2CTE — sub_with_tier: JOIN subscriptions to plans so each row has plan_name and tier_level alongside start_date and customer_id. This enriched view is what we'll self-join.
3Self-join in main query: Reference the CTE twice with different aliases (old and new). Join conditions: same customer, new.start_date > old.start_date, and new.tier_level > old.tier_level.
4Why CTE makes self-joins cleaner: Without a CTE, you'd write the same 3-table JOIN twice inside the same query. The CTE names that derived table once; both aliases reference the name.
Solution
WITH
sub_with_tier AS (
    SELECT
        s.customer_id,
        s.start_date,
        pl.plan_name,
        pl.tier_level
    FROM   subscriptions s
    JOIN   plans          pl ON s.plan_id = pl.plan_id
)
SELECT
    c.name,
    old_s.plan_name  AS from_plan,
    new_s.plan_name  AS to_plan,
    old_s.start_date AS old_start,
    new_s.start_date AS new_start
FROM   sub_with_tier old_s
JOIN   sub_with_tier new_s
    ON  old_s.customer_id  = new_s.customer_id
   AND  new_s.start_date   > old_s.start_date
   AND  new_s.tier_level   > old_s.tier_level
JOIN   customers c ON c.customer_id = old_s.customer_id
ORDER BY c.name, old_s.start_date;

Multiple upgrade pairs per customer: Acme appears 3 times because the self-join finds every valid (old, new) combination — not just adjacent transitions. If you only want direct consecutive upgrades, add a NOT EXISTS clause to exclude cases where an intermediate subscription exists between old and new.
