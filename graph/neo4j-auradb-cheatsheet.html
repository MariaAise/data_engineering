AuraDB Orientation
AuraDB is Neo4j's fully managed cloud service. You get the native graph engine without managing infrastructure — but with constraints on config, plugins, and scaling that differ from self-hosted Neo4j.
AuraDB vs. Self-Hosted Neo4j
What you get
Full Neo4j engine, Cypher, ACID transactions, GDS (Pro+), Bloom, Browser/Workspace tools
What you don't control
OS, JVM settings, neo4j.conf, plugin installation, raw file system access, custom ports
APOC on Aura
A subset of APOC is available on Pro/Enterprise — not all procedures. Always verify before building a dependency on a specific APOC proc.
Upgrades
Neo4j version upgrades are managed by Aura — you don't control timing on Free tier
Region
GCP, AWS, Azure availability varies by tier. Choose region at creation — cannot be changed later without recreating the instance

Cypher Fundamentals
Cypher uses ASCII-art to describe graph patterns — you draw what you want to find, and the engine finds it. If you know SQL, Cypher will feel familiar in structure but very different in what it expresses natively.
Pattern Anatomy
MATCH (a:Person {name: "Alice"})-[r:WORKS_AT {since: "2022"}]->(c:Company) RETURN a.name, c.name, r.since
(a:Person)
Node with variable a and label :Person. Variable lets you reference it in RETURN/WHERE.
{name:"Alice"}
Inline property filter — shorthand for WHERE a.name = "Alice"
-[r:WORKS_AT]->
Directed relationship of type WORKS_AT, variable r. Arrow shows direction.
-[:WORKS_AT]-
No arrow = undirected match — finds the rel regardless of storage direction.
()
Anonymous node — exists in the pattern but you don't reference it.
[:A|B]
Match multiple relationship types using pipe separator.
Core Clause Map
MATCH
Find patterns. Primary read clause. Analog of SELECT + FROM + JOIN.
OPTIONAL MATCH
Like MATCH but returns null if pattern not found. Analog of LEFT JOIN.
WHERE
Filter results after MATCH. Supports property predicates and functions.
RETURN
Specify output. Can return nodes, rels, properties, or expressions.
WITH
Pipe results between clauses. Allows mid-query aggregation. Analog of CTE.
CREATE
Create nodes/rels. Always creates new — no duplicate check.
MERGE
Match or create. Idempotent write. Analog of INSERT OR IGNORE + UPDATE.
SET
Update/add properties on a node or rel. Also used to add labels.
REMOVE
Delete a property or remove a label from a node.
DELETE
Delete node or relationship. Node must have no relationships first.
DETACH DELETE
Delete a node and all its relationships in one operation.
UNWIND
Expand a list into individual rows. Batch-write workhorse.
CALL {}
Subquery — correlated (uses outer vars) or uncorrelated (independent).
FOREACH
Apply write operations to each element in a list. Side-effects only.
LOAD CSV
Read CSV line by line and execute Cypher per row. Built-in import tool.
Parameters — Always Use in Production
Parameters prevent query plan cache misses and protect against injection. Neo4j caches plans keyed by query structure — literal values create a new cache entry every call.
✗ Literals (bad in production)
MATCH (p:Person {email: "[email protected]"}) RETURN p
✓ Parameters (correct)
MATCH (p:Person {email: $email}) RETURN p // pass {"email": "[email protected]"} from driver
Reading Data
All reads start with MATCH. WHERE filters, WITH pipes and reshapes, aggregation functions summarise. The WITH clause is the structural tool for complex multi-step queries.
MATCH + WHERE Filtering
-- equality + AND MATCH (p:Person) WHERE p.age > 30 AND p.city = $city RETURN p.name, p.age -- IN list WHERE p.status IN ['active', 'trial'] -- string predicates WHERE p.name STARTS WITH 'Al' WHERE p.bio CONTAINS 'engineer' -- null checks WHERE p.phone IS NOT NULL
OPTIONAL MATCH — the LEFT JOIN
-- returns Person even if no Company found MATCH (p:Person) OPTIONAL MATCH (p)-[:WORKS_AT]->(c:Company) RETURN p.name, coalesce(c.name, 'unemployed') -- c and c.name are null when no rel found -- coalesce() = IFNULL() analog
Plain MATCH drops the row if pattern not found — like INNER JOIN. Use OPTIONAL MATCH when the relationship may not exist.
WITH — Piping and Reshaping (CTE Analog)
WITH ends one clause segment and starts another. Use it to aggregate mid-query, filter on aggregated values, or pass only certain variables forward to the next MATCH.
Filter after aggregation (HAVING analog)
MATCH (p:Person)-[:KNOWS]->(f) WITH p, count(f) AS numFriends WHERE numFriends > 5 RETURN p.name, numFriends ORDER BY numFriends DESC
Multi-hop with intermediate reshaping
MATCH (p:Person {name: $name}) WITH p MATCH (p)-[:PURCHASED]->(prod:Product) WITH prod, count(*) AS times RETURN prod.name, times ORDER BY times DESC LIMIT 10
Aggregation Functions
MATCH (p:Person)-[r:PURCHASED]->(prod) RETURN p.name, count(prod) AS total, sum(r.amount) AS spend, avg(r.amount) AS avgOrder, min(r.amount) AS minOrder, max(r.amount) AS maxOrder, collect(prod.name) AS productList // collect() builds a list — analog of GROUP_CONCAT
Sorting and Pagination
MATCH (p:Person) RETURN p.name, p.age ORDER BY p.age DESC, p.name ASC SKIP 20 // offset — skip first N rows LIMIT 10 // return max N rows // SKIP + LIMIT = pagination // Always pair LIMIT with ORDER BY for // deterministic paging across requests
Writing Data
The most important concept: CREATE always makes something new. MERGE makes it only if it doesn't already exist. Getting this wrong is the most common source of duplicate nodes.
CREATE vs. MERGE — The Critical Distinction
CREATE — always inserts
// Runs twice → two Alice nodes CREATE (p:Person { name: "Alice", email: "[email protected]" }) RETURN p
Use when you're certain the entity doesn't exist yet and want to fail fast on duplicates.
MERGE — match or create
// Runs twice → still one Alice node MERGE (p:Person {email: "[email protected]"}) ON CREATE SET p.name = "Alice", p.createdAt = timestamp() ON MATCH SET p.lastSeen = timestamp() RETURN p
Use for idempotent writes — pipelines, retryable imports, upsert semantics.
MERGE pitfall: MERGE matches on the exact combination of properties you specify. Always MERGE on a stable unique key (email, UUID, external ID) — not display names or mutable values that might change.
SET and REMOVE
-- update a property MATCH (p:Person {email: $email}) SET p.name = $newName -- merge props (keeps existing, adds new) SET p += {city: "NYC", verified: true} // += merges; = replaces ALL properties -- add a label SET p:Admin -- remove a property REMOVE p.tempToken -- remove a label REMOVE p:Trial
DELETE vs. DETACH DELETE
-- DELETE fails if node has relationships MATCH (p:Person {id: $id}) DELETE p // ✗ errors if p has any rels -- DETACH DELETE removes node + all rels MATCH (p:Person {id: $id}) DETACH DELETE p -- delete a single relationship only MATCH (a)-[r:FOLLOWS]->(b) WHERE a.id = $aId AND b.id = $bId DELETE r
UNWIND — Batch Inserts from a List
UNWIND expands a list parameter into individual rows, then runs the rest of the query once per element. This is the equivalent of multi-row INSERT ... VALUES (...), (...).
// params: {"people": [{"name":"Alice","email":"[email protected]"}, ...]} UNWIND $people AS row MERGE (p:Person {email: row.email}) ON CREATE SET p.name = row.name, p.createdAt = timestamp() ON MATCH SET p.name = row.name RETURN count(p) AS processed // Recommended batch size: 500–1000 rows per transaction // Too large = memory pressure; too small = too many round trips
Schema & Indexes
Neo4j is schema-optional — nodes don't need to conform to a rigid structure. But constraints and indexes are essential for correctness and performance. Create them before loading data.
Constraints
-- UNIQUE (also creates a backing index) CREATE CONSTRAINT person_email_unique FOR (p:Person) REQUIRE p.email IS UNIQUE -- NODE KEY (multi-prop uniqueness) CREATE CONSTRAINT order_key FOR (o:Order) REQUIRE (o.userId, o.orderId) IS NODE KEY -- existence (property must be present) CREATE CONSTRAINT person_name_exists FOR (p:Person) REQUIRE p.name IS NOT NULL -- manage SHOW CONSTRAINTS DROP CONSTRAINT person_email_unique
UNIQUE
Enforces uniqueness + creates a backing range index. Most common constraint.
NODE KEY
Multi-property uniqueness + all listed properties must exist. Stronger than UNIQUE.
IS NOT NULL
Property must be present on every node with this label. No index created.
On relationships
Same syntax: FOR ()-[r:TYPE]-() REQUIRE r.prop IS UNIQUE
Index Types — Decision Table
TypeUse whenCreate syntax hint
RangeEquality, range (>, <), ORDER BY on numeric or string. Default and most common.CREATE INDEX FOR (n:L) ON (n.prop)
TextSTARTS WITH, ENDS WITH, CONTAINS on string properties.CREATE TEXT INDEX … FOR (n:L) ON (n.prop)
Full-textFree-text Lucene search across multiple properties. Returns scored results.CREATE FULLTEXT INDEX … FOR (n:L|M) ON EACH [n.a,n.b]
PointGeospatial — distance, bounding box — on point() property values.CREATE POINT INDEX … FOR (n:L) ON (n.location)
CompositeMultiple properties queried together. All props in the filter must be in the index.CREATE INDEX … FOR (n:L) ON (n.a, n.b)
RelationshipFiltering on relationship property (e.g. r.since, r.amount).CREATE INDEX … FOR ()-[r:TYPE]-() ON (r.prop)
EXPLAIN and PROFILE — Reading the Query Plan
EXPLAIN
Shows planned execution tree without running the query. Zero cost. Use to check if an index will be used.
PROFILE
Runs the query and shows actual rows + db hits per operator. Use to find the expensive step.
NodeIndexSeek
Good — index lookup used for entry-point node. This is what you want to see.
NodeByLabelScan
Full label scan — no index used. Add a range/unique index on the filter property.
db hits
The cost metric. Minimize db hits on the critical path of your most frequent queries.
-- prepend EXPLAIN or PROFILE to any query EXPLAIN MATCH (p:Person {email: $email}) RETURN p PROFILE MATCH (p:Person)-[:KNOWS*1..3]->(f) RETURN f.name // Green flags: NodeIndexSeek // Red flags: NodeByLabelScan // CartesianProduct // Run in Browser/Workspace to see // the visual plan tree
Advanced Cypher
Variable-length traversal, path algorithms, subqueries, and list operations — the patterns that make Cypher genuinely more expressive than SQL for graph problems.
Variable-Length Paths
-- exact depth MATCH (a)-[:KNOWS*3]->(b) -- range (1 to 5 hops) MATCH (a)-[:KNOWS*1..5]->(b) -- 1 or more hops (unbounded — use carefully) MATCH (a)-[:KNOWS*]->(b) -- multiple rel types MATCH (a)-[:KNOWS|FOLLOWS*1..3]->(b) -- capture relationships, compute hop count MATCH (a)-[rels:KNOWS*1..3]->(b) RETURN b.name, size(rels) AS hops
Unbounded * on a dense graph can exhaust memory. Always use an upper bound in production. Start with *1..5 and profile before relaxing.
shortestPath and allShortestPaths
MATCH (a:Person {name: $from}), (b:Person {name: $to}) MATCH path = shortestPath( (a)-[:KNOWS*]-(b) ) RETURN length(path), nodes(path) -- all paths of the same minimum length MATCH path = allShortestPaths( (a)-[:KNOWS*]-(b) ) RETURN path // Note: shortestPath uses unweighted BFS. // For weighted shortest path → GDS Dijkstra.
CALL {} Subqueries
-- uncorrelated (independent) CALL { MATCH (p:Person) RETURN count(p) AS total } RETURN total -- correlated (uses outer variable) MATCH (p:Person) CALL { WITH p // import outer variable MATCH (p)-[:PURCHASED]->(prod) RETURN count(prod) AS purchases } RETURN p.name, purchases
List Comprehension + CASE
-- list comprehension: filter + transform MATCH (p:Person)-[:KNOWS]->(f) WITH p, collect(f) AS friends RETURN [x IN friends WHERE x.age>30 | x.name] AS olderFriends -- CASE expression RETURN p.name, CASE WHEN p.age < 25 THEN 'junior' WHEN p.age < 40 THEN 'mid' ELSE 'senior' END AS tier
FOREACH — Side-Effect Writes Inside a Read
FOREACH applies write operations to each element of a list or path. You can't RETURN from inside it — it's purely for side effects when you need to write while traversing.
-- mark all nodes along a path MATCH p = shortestPath( (a:Person {name:$a})-[*]-(b:Person {name:$b}) ) FOREACH (node IN nodes(p) | SET node.visited = true ) RETURN length(p) AS pathLength
Python Driver
The official neo4j Python driver is the production path for application queries and data pipelines. It uses Bolt protocol and manages connection pooling, retry logic, and transactions.
Install + AuraDB Connection
# Install pip install neo4j from neo4j import GraphDatabase import os # Load from environment — never hardcode credentials URI = os.environ["NEO4J_URI"] # neo4j+s://xxxx.databases.neo4j.io USER = os.environ["NEO4J_USERNAME"] # "neo4j" PASSWORD = os.environ["NEO4J_PASSWORD"] # Create driver once at app startup — it manages the connection pool driver = GraphDatabase.driver(URI, auth=(USER, PASSWORD)) driver.verify_connectivity() # raises ServiceUnavailable on failure print("Connected to AuraDB") # Close when shutting down (releases the pool) # driver.close()
Driver / Session / Transaction — Three Layers
Driver
Manages the connection pool. One per application. Thread-safe. Create once, reuse everywhere.
Session
Logical context for running queries. Not thread-safe — don't share across threads. Cheap to create per request.
Transaction
ACID unit of work. Use execute_read / execute_write (managed) over explicit transactions — they handle transient error retries automatically.
Prefer managed transactions. execute_read / execute_write automatically retry on transient errors (deadlocks, temporary unavailability) — critical for AuraDB's cloud environment.
Read Transaction Pattern
def get_person(tx, email: str): result = tx.run( """ MATCH (p:Person {email: $email}) RETURN p.name AS name, p.age AS age """, email=email ) return [record.data() for record in result] with driver.session() as session: people = session.execute_read( get_person, email="[email protected]" ) print(people) # [{'name': 'Alice', 'age': 31}]
Write Transaction Pattern
def upsert_person(tx, name: str, email: str): result = tx.run( """ MERGE (p:Person {email: $email}) ON CREATE SET p.name = $name, p.createdAt = timestamp() ON MATCH SET p.name = $name RETURN p.name AS name """, name=name, email=email ) return result.single()["name"] with driver.session() as session: name = session.execute_write( upsert_person, name="Alice", email="[email protected]" ) print(f"Upserted: {name}")
Batch Write with UNWIND
def batch_upsert(tx, people: list[dict]): """people = [{'name': 'Alice', 'email': '[email protected]'}, ...]""" result = tx.run( """ UNWIND $people AS row MERGE (p:Person {email: row.email}) ON CREATE SET p.name = row.name, p.createdAt = timestamp() ON MATCH SET p.name = row.name RETURN count(p) AS processed """, people=people ) return result.single()["processed"] BATCH_SIZE = 500 def load_all(driver, all_records: list[dict]) -> int: total = 0 with driver.session() as session: for i in range(0, len(all_records), BATCH_SIZE): batch = all_records[i : i + BATCH_SIZE] n = session.execute_write(batch_upsert, batch) total += n print(f" batch {i//BATCH_SIZE+1}: {n} processed") return total
Connection Pool Config
# Tune for your AuraDB tier's connection limit driver = GraphDatabase.driver( URI, auth=(USER, PASSWORD), max_connection_pool_size=50, # default: 100 connection_timeout=30, # seconds max_transaction_retry_time=30, # retry window (s) keep_alive=True, ) # Free tier: keep pool small (≤ 10) # Pro tier: 50–100 is fine # Check tier connection limit in Aura console
Error Handling
from neo4j.exceptions import ( ServiceUnavailable, TransientError, ClientError, ) try: with driver.session() as s: s.execute_write(upsert_person, ...) except TransientError as e: # Deadlock / temp unavailable # execute_write retries this automatically print(f"Transient (auto-retried): {e}") except ClientError as e: # Constraint violation, syntax error # e.code → "Neo.ClientError.Schema..." # e.message → human-readable detail print(f"Client error {e.code}: {e.message}") except ServiceUnavailable: # AuraDB unreachable or Free tier paused print("DB unavailable — check Aura console")
Importing Data into AuraDB
Three main paths: LOAD CSV for moderate files from a URL, the Aura Data Importer UI for no-code loads, and Python UNWIND batches for production pipelines. Each has a clear role.
LOAD CSV
-- WITH HEADERS uses first row as keys LOAD CSV WITH HEADERS FROM 'https://your-bucket.s3.amazonaws.com/people.csv' AS row MERGE (p:Person {email: row.email}) SET p.name = row.name, p.age = toInteger(row.age) RETURN count(*) AS loaded -- non-comma delimiter LOAD CSV FROM '...' AS row FIELDTERMINATOR '|'
File location
AuraDB cannot read local files. CSV must be at a public HTTPS URL (S3, GCS, GitHub raw).
Type casting
All values are strings. Use toInteger(), toFloat(), date() to cast types explicitly.
PERIODIC COMMIT
Not available on AuraDB (self-hosted only). For large files, use Python UNWIND batches.
Practical limit
LOAD CSV works well up to ~100K rows per run. Beyond that, use the Python batch pattern.
AuraDB Data Importer UI
What it is
Visual drag-and-drop tool in Neo4j Workspace for mapping CSV columns to node/relationship properties.
Best for
One-off data loads, prototyping, non-developer stakeholders. No Cypher required.
Supports
Multiple CSV files, node + relationship mapping, type conversion, MERGE key selection.
Limitations
Not scriptable or idempotent. Not suitable for production pipelines or repeated ingestion.
Python CSV → AuraDB (Production)
import csv def load_csv(driver, filepath: str) -> int: with open(filepath) as f: rows = list(csv.DictReader(f)) # Cast types in Python before sending for r in rows: r['age'] = int(r['age']) # load_all from Tab 07 handles batching return load_all(driver, rows)
Cast all types in Python before passing to the driver. Don't rely on Cypher coercion for bulk loads — it's inconsistent and harder to debug.
APOC — Flagged, Verify Before Use
APOC is a library of extended Cypher procedures. A subset is available on AuraDB — not all procedures present in self-hosted Neo4j. Always verify availability on your specific tier before building a dependency.
apoc.load.json
Load and iterate over a remote JSON file — REST API ingestion
apoc.periodic.iterate
Batch-process large MATCH results with configurable batch size
apoc.merge.node
Dynamic MERGE where label and properties are computed at runtime
apoc.export.csv
Export query results — limited on Aura (no local filesystem)
⚠ Verify first
Always run CALL dbms.procedures() YIELD name WHERE name STARTS WITH 'apoc' RETURN name in your actual Aura instance before building on a specific APOC procedure. The fallback for any unavailable APOC proc is always the Python driver.
GDS — Graph Data Science (Light Reference)
GDS is a library of graph algorithms that runs in-memory on a projection of your stored graph. Available on AuraDB Professional and Enterprise only. A dedicated GDS sheet covers this in depth.
GDS Workflow — Three Steps Every Time
1
Project
Load a subgraph into in-memory GDS graph. Define which node labels and relationship types to include.
2
Run Algorithm
Execute an algorithm against the projected graph in stream, stats, or write mode.
3
Write Back
Persist scores, community IDs, or embeddings as node/rel properties in the stored graph.
Graph Projection
Native projection (fast, recommended)
CALL gds.graph.project( 'myGraph', 'Person', // node label(s) 'KNOWS' // rel type(s) ) // Drop when done / data changes: CALL gds.graph.drop('myGraph')
Cypher projection (flexible, filtered)
CALL gds.graph.project.cypher( 'myGraph', 'MATCH (n:Person) RETURN id(n) AS id', 'MATCH (a)-[:KNOWS]->(b) RETURN id(a) AS source, id(b) AS target' )
Projections are in-memory snapshots — they don't reflect graph changes after creation. Drop and re-project when data changes.
Key Algorithms — One Per Category
PageRank
Centrality — who is most influential?
Ranks nodes by importance of incoming connections. A node is important if important nodes point to it. Use for: influencer ranking, document importance, risk scoring.
CALL gds.pageRank.stream('myGraph') YIELD nodeId, score RETURN gds.util.asNode(nodeId).name, score ORDER BY score DESC LIMIT 10
Louvain
Community Detection — what clusters exist?
Finds densely connected communities by maximizing modularity. Use for: customer segmentation, fraud ring detection, topic clustering, social communities.
CALL gds.louvain.write('myGraph', { writeProperty: 'communityId' }) // writes communityId to each node
Dijkstra Source-Target
Path Finding — weighted shortest path
Finds minimum-cost path using edge weights. Unlike shortestPath() in Cypher, this respects weights. Use for: routing, supply chain optimization, network costing.
CALL gds.shortestPath.dijkstra.stream( 'myGraph', { sourceNode: $sourceId, targetNode: $targetId, relationshipWeightProperty: 'cost' } ) YIELD totalCost, nodeIds
Node Similarity
Similarity — who is most alike?
Computes Jaccard or overlap similarity based on shared neighbors. Use for: collaborative filtering, duplicate detection, "users like you" recommendations.
CALL gds.nodeSimilarity.stream('myGraph') YIELD node1, node2, similarity WHERE similarity > 0.7 RETURN gds.util.asNode(node1).name, gds.util.asNode(node2).name, similarity
Stream vs. Write vs. Mutate Modes
// stream: results returned to query, not stored CALL gds.pageRank.stream('myGraph') YIELD nodeId, score // write: results saved as node property in the DB CALL gds.pageRank.write('myGraph', { writeProperty: 'pageRankScore' }) // mutate: updates only the in-memory projection (not the DB) // useful when chaining multiple algorithms on the same projection CALL gds.pageRank.mutate('myGraph', { mutateProperty: 'pageRankScore' })

Python Boilerplate (Copy-Paste)
from neo4j import GraphDatabase import os driver = GraphDatabase.driver( os.environ["NEO4J_URI"], auth=(os.environ["NEO4J_USERNAME"], os.environ["NEO4J_PASSWORD"]) ) driver.verify_connectivity() def read(query: str, **params): with driver.session() as s: return s.execute_read( lambda tx: [r.data() for r in tx.run(query, **params)] ) def write(query: str, **params): with driver.session() as s: return s.execute_write( lambda tx: tx.run(query, **params).consume() )
Common Errors + Fixes
Error / symptom
Cause
Fix
Cannot delete, still has relationships
Used DELETE on a node with connected edges
Use DETACH DELETE to remove node + all its rels
CartesianProduct warning
Two unrelated MATCH patterns with no connecting WHERE — produces N×M rows
Add WHERE connecting the patterns, or restructure as a traversal
NodeByLabelScan in PROFILE
Full scan on a label — no index being used for the filter property
Create a range or unique index on the property used in the filter
Duplicate nodes after MERGE
MERGE key used a mutable property (name, status) that changed between runs
Always MERGE on a stable unique key — UUID, email, external ID
ServiceUnavailable (Free tier)
Free instance auto-paused after ~3 days idle
Resume via Aura console. Upgrade to Pro for always-on. Handle in app startup retry.
Slow queries / plan cache misses
Literal values in queries create a new plan per unique value
Replace all literals with $params — always use the driver parameter dict
LOAD CSV: can't read local file
AuraDB has no local filesystem — file:/// URLs don't work
