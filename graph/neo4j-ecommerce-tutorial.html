What's happening

UNWIND + MERGE is the idiomatic way to load list data into Neo4j. UNWIND turns the inline list into rows, then MERGE ensures each node is created exactly once — even if you re-run the script.

WITH between MERGE and MATCH is required when you need to reference a node created in one clause and match another node in the next — WITH passes variables forward between clause segments.

The += operator in SET o1 += {...} merges properties into the node rather than replacing all properties. Safe to use in idempotent pipelines.

After running all three steps, verify with: MATCH (n) RETURN labels(n), count(n) — you should see 4 labels with node counts of 8, 12, 4, and 15.

02
Find All Customers
Return the name, email, and city of every customer in the graph, sorted alphabetically by name.
MATCHRETURNORDER BY
Cypher Query
MATCH (c:Customer) RETURN c.name AS name, c.email AS email, c.city AS city ORDER BY c.name
Expected output (8 rows)
"Alice Novak" · alice@example.com · "New York"
"Ben Okafor" · ben@example.com · "London"
"Cara Singh" · cara@example.com · "Toronto"
… 5 more rows
Explanation

MATCH (c:Customer) scans all nodes with the :Customer label. Without a label, MATCH (c) would scan every node in the graph — always include a label for production queries.

RETURN c.name AS name projects a specific property as an aliased column. You can also RETURN c to return the whole node object, but projecting individual properties is better practice — it's explicit and transfers less data.

ORDER BY c.name sorts ascending by default. Use ORDER BY c.name DESC for reverse. With no ORDER BY, Neo4j makes no guarantees about row order.

03
Find a Customer by Email
Look up a single customer using their email address. Use a parameter — not a string literal.
MATCHWHERE$params
Cypher Query
MATCH (c:Customer {email: $email}) RETURN c.name AS name, c.email AS email, c.city AS city // In Neo4j Browser/Workspace, set params with: // :param email => "alice@example.com"
Expected output (1 row, $email = "alice@example.com")
"Alice Novak" · alice@example.com · "New York"
Explanation

The inline property filter {email: $email} is shorthand for a WHERE clause. It's equivalent to writing MATCH (c:Customer) WHERE c.email = $email.

Always use $params instead of string literals for two reasons: (1) Neo4j caches query execution plans keyed by query structure — a literal value like "alice@example.com" would be treated as a different query than "ben@example.com", filling the plan cache. (2) Parameters are safe from injection.

In the Python driver, pass parameters as keyword args: tx.run("MATCH (c:Customer {email: $email}) ...", email="alice@example.com")

04
Find All Products in a Category
Return all product names and prices in the "Electronics" category, sorted by price descending.
MATCHtraversalORDER BY
Cypher Query
MATCH (p:Product)-[:IN_CATEGORY]->(cat:Category {name: $category}) RETURN p.name AS product, p.price AS price, p.sku AS sku ORDER BY p.price DESC // :param category => "Electronics"
Expected output (4 rows)
"Mechanical Keyboard" · 119.00 · SKU-003
"Wireless Headphones" · 89.99 · SKU-001
"Webcam HD" · 59.99 · SKU-004
"USB-C Hub" · 34.99 · SKU-002
Explanation

This is a single-hop traversal: start at any :Product, follow a :IN_CATEGORY relationship to a :Category node, then filter on the category name. In SQL this would require a JOIN on a foreign key; here it's expressed as a path pattern.

The direction arrow -[:IN_CATEGORY]-> matches only relationships going from Product to Category. If you omit the arrow (-[:IN_CATEGORY]-), it matches in either direction — fine for undirected graphs, but be explicit when direction has meaning.

Try changing $category to "Sports" or "Home & Kitchen" to explore other categories — same query, different entry point.

05
Find What a Customer Has Purchased
Return all product names purchased by Alice, including the order date and quantity. This requires traversing two relationships: Customer → Order → Product.
MATCHmulti-hoprel props
Cypher Query
MATCH (c:Customer {email: $email}) -[:PLACED]->(o:Order) -[line:CONTAINS]->(p:Product) RETURN p.name AS product, o.orderId AS orderId, o.date AS date, line.qty AS qty ORDER BY o.date // :param email => "alice@example.com"
Expected output (5 rows for Alice)
"Wireless Headphones" · ORD-001 · 2024-01-15 · qty:1
"USB-C Hub" · ORD-001 · 2024-01-15 · qty:1
"Wireless Headphones" · ORD-002 · 2024-02-03 · qty:1
… 2 more rows (ORD-003)
Explanation

This is a two-hop traversal: Customer → Order → Product. In SQL you'd write a join chain: customers JOIN orders ON ... JOIN order_items ON ... JOIN products ON ... — four tables, three joins. Here it's one pattern expression.

Notice [line:CONTAINS] — by naming the relationship variable line, we can access its properties (line.qty, line.unit_price) in the RETURN clause. Relationship properties are first-class data in the graph model.

Alice appears in results with Wireless Headphones twice — once in ORD-001 and once in ORD-002. This is correct and expected: she placed two separate orders containing the same product.

06
Find Customers Who Bought a Specific Product
Given a product SKU, return all customers who purchased it and the date they ordered it. Traversal goes in reverse: Product ← Order ← Customer.
MATCHreverse traversal
Cypher Query
MATCH (c:Customer) -[:PLACED]->(o:Order) -[:CONTAINS]->(p:Product {sku: $sku}) RETURN c.name AS customer, c.city AS city, o.date AS purchaseDate ORDER BY o.date // :param sku => "SKU-001" (Wireless Headphones)
Expected output (3 rows for SKU-001)
"Alice Novak" · New York · 2024-01-15
"Felix Huang" · Singapore · 2024-01-10
"Alice Novak" · New York · 2024-02-03
Explanation

The pattern direction in a graph query determines where traversal starts. Here we anchor on the product ({sku: $sku}) and walk back through orders to customers — exactly the reverse of Task 05, but the same two-hop structure.

This is where graph databases shine vs. SQL for exploratory queries: switching the "entry point" of a traversal doesn't require rewriting the join chain or adding new indexes — just change which node you anchor on and which direction you traverse.

Alice appears twice because she purchased SKU-001 in two separate orders. If you want distinct customers only, add RETURN DISTINCT c.name, c.city.

07
Count Orders per Customer
Return each customer's name and their total number of orders, sorted from most to fewest. Use aggregation with GROUP BY semantics.
count()aggregationORDER BY
Cypher Query
MATCH (c:Customer)-[:PLACED]->(o:Order) RETURN c.name AS customer, count(o) AS totalOrders, sum(o.total) AS totalSpend ORDER BY totalOrders DESC
Expected output (7 rows — Hugo has no orders and won't appear)
"Alice Novak" · 3 orders · totalSpend: 403.96
"Felix Huang" · 3 orders · totalSpend: 273.97
"Ben Okafor" · 2 orders · totalSpend: 243.98
… 4 more rows (1 order each)
Explanation

In Cypher, GROUP BY is implicit. Any non-aggregated variable in RETURN becomes a grouping key. Here c.name is the group key, and count(o) / sum(o.total) are the aggregates — exactly like SELECT name, COUNT(*), SUM(total) FROM ... GROUP BY name.

Notice Hugo doesn't appear. He has one order (ORD-014) in the dataset but the relationship was correctly created. If Hugo had no orders at all, he'd be absent from this result — a plain MATCH only returns rows where the full pattern matched. To include customers with zero orders, use OPTIONAL MATCH (Task 17).

You can reference aliases in ORDER BY — ORDER BY totalOrders DESC works even though totalOrders is defined in the RETURN clause.

08
Add a New Customer
Insert a new customer using MERGE so the operation is safe to re-run. Set all properties only on creation.
MERGEON CREATE SET
Cypher Query
MERGE (c:Customer {email: $email}) ON CREATE SET c.name = $name, c.city = $city, c.createdAt = timestamp() RETURN c.name AS name, c.email AS email, c.city AS city // :param email => "ivan@example.com" // :param name => "Ivan Petrov" // :param city => "Moscow"
Expected output (first run)
"Ivan Petrov" · ivan@example.com · "Moscow"
Second run — no duplicate created, same row returned
"Ivan Petrov" · ivan@example.com · "Moscow"
Explanation

MERGE works like a graph-level "find or create". It first tries to match a :Customer node with the specified email. If found, it returns it. If not found, it creates it and executes the ON CREATE SET block.

MERGE on a single, stable unique key (email here) is critical. If you included name in the MERGE pattern — MERGE (c:Customer {email: $email, name: $name}) — and the name changed later, MERGE would create a second node instead of matching the existing one.

timestamp() returns the current Unix timestamp in milliseconds. Useful for auditing — you can later query "customers created in the last 30 days".

09
Update a Customer's City
Ben has moved from London to Amsterdam. Update his city property and record when the change was made.
MATCHSET
Cypher Query
MATCH (c:Customer {email: $email}) SET c.city = $newCity, c.updatedAt = timestamp() RETURN c.name AS name, c.city AS city // :param email => "ben@example.com" // :param newCity => "Amsterdam"
Expected output
"Ben Okafor" · "Amsterdam"
Explanation

SET c.city = $newCity updates a single property. You can update multiple properties in one SET clause by separating them with commas.

Two ways to set multiple properties at once:

SET c.city = $city, c.updatedAt = timestamp() — updates listed properties, leaves others untouched.

SET c += {city: $city, updatedAt: timestamp()} — merges a map into the node. Same behaviour — keeps existing properties, adds/overwrites listed ones.

Avoid SET c = {city: $city} (without +=) unless intentional — this replaces all properties on the node with only what's in the map, deleting name, email, etc.

10
Add a Review
Felix wants to leave a 4-star review for the Running Shoes (SKU-005). Create a REVIEWED relationship with rating and review text as properties on the relationship.
MERGErelationship props
Cypher Query
MATCH (c:Customer {email: $email}), (p:Product {sku: $sku}) MERGE (c)-[r:REVIEWED]->(p) ON CREATE SET r.rating = $rating, r.text = $text, r.createdAt = timestamp() ON MATCH SET r.rating = $rating, r.text = $text, r.updatedAt = timestamp() RETURN c.name AS reviewer, p.name AS product, r.rating AS rating // :param email => "felix@example.com" // :param sku => "SKU-005" // :param rating => 4 // :param text => "Good grip but narrow fit."
Expected output
"Felix Huang" · "Running Shoes" · 4
Explanation

MERGE works on relationships too. MERGE (c)-[r:REVIEWED]->(p) finds an existing REVIEWED relationship between Felix and Running Shoes, or creates one if it doesn't exist.

Using both ON CREATE SET and ON MATCH SET gives you a proper upsert: set createdAt only on creation, and updatedAt only on update. This preserves the original creation timestamp while tracking when the review was last edited.

Relationship properties like r.rating and r.text are stored directly on the edge — no extra "reviews" table or join needed. This is data that, in a relational model, would require a separate junction table with its own foreign keys.

11
Delete a Review
Ben wants to delete his review of the Winter Jacket (SKU-007). Remove only the REVIEWED relationship — not the nodes.
MATCHDELETE rel
Cypher Query
MATCH (c:Customer {email: $email}) -[r:REVIEWED]-> (p:Product {sku: $sku}) DELETE r RETURN count(r) AS deletedReviews // :param email => "ben@example.com" // :param sku => "SKU-007"
Expected output
deletedReviews: 1
Re-run the same query — no match, 0 returned
deletedReviews: 0
Explanation

DELETE r deletes the relationship only — Ben and the Winter Jacket nodes remain intact. This is the key difference from DETACH DELETE, which deletes a node along with all its relationships.

The pattern (c)-[r:REVIEWED]->(p) anchors both endpoints. Without anchoring both nodes, you risk deleting more reviews than intended. Always be as specific as possible in the MATCH pattern before a DELETE.

If the pattern doesn't match (e.g. the review was already deleted), the query returns 0 rows gracefully rather than throwing an error. This is idiomatic Cypher — no need for "check then delete" logic.

12
Upsert a Product (MERGE with Price Update)
The USB-C Hub price has changed to $39.99. Use MERGE to update it if it exists, or create it if it doesn't. Set the price on both creation and update.
MERGEON MATCH SETupsert
Cypher Query
MERGE (p:Product {sku: $sku}) ON CREATE SET p.name = $name, p.price = $price, p.createdAt = timestamp() ON MATCH SET p.price = $price, p.updatedAt = timestamp() RETURN p.sku AS sku, p.name AS product, p.price AS price // :param sku => "SKU-002" // :param name => "USB-C Hub" // :param price => 39.99
Expected output — existing product updated
"SKU-002" · "USB-C Hub" · 39.99
Explanation

This is the canonical upsert pattern in Cypher. MERGE on the SKU (the stable unique identifier), then use ON CREATE SET for new fields (like createdAt) and ON MATCH SET for fields that should always reflect the latest values (like price and updatedAt).

This is equivalent to a SQL INSERT ... ON DUPLICATE KEY UPDATE or PostgreSQL's INSERT ... ON CONFLICT DO UPDATE SET.

This pattern is the backbone of any incremental sync pipeline: run it repeatedly with new data and it will create new products and update changed prices without ever producing duplicates.

13
Find Products That Have Never Been Purchased
Return all products that have no CONTAINS relationship pointing to them — i.e., they exist in the catalog but have never appeared in any order.
graph patternNOT EXISTS
Cypher Query
MATCH (p:Product) WHERE NOT (p)<-[:CONTAINS]-() RETURN p.name AS product, p.sku AS sku, p.price AS price ORDER BY p.price DESC
Expected output (2 products never purchased)
"Bamboo Cutting Board" · SKU-011 · 24.99
"Merino Wool Socks" · SKU-008 · 18.00
💡 SQL comparison
In SQL: SELECT * FROM products WHERE id NOT IN (SELECT product_id FROM order_items) — a subquery or NOT EXISTS join. In Cypher it's a structural pattern: "find products where no CONTAINS relationship exists pointing to them."
Explanation

NOT (p)<-[:CONTAINS]-() is a pattern existence check. It asks: "does no CONTAINS relationship point inward to this product node?" The () is an anonymous node — we don't care who it is, just whether the relationship exists.

Note the arrow direction: <-[:CONTAINS]- matches relationships arriving at the product, because CONTAINS goes Order → Product. If you used -[:CONTAINS]->() you'd be checking for outgoing CONTAINS rels from the product, which don't exist at all and would return every product.

This is a pure graph structural query — there's no equivalent of "relationship absence" in basic SQL without subqueries or outer joins.

Find Customers Who Reviewed But Never Purchased a Product
Find customers who have a REVIEWED relationship to a product but have never actually purchased that same product. This is a classic graph-native pattern: structural contradiction detection.
graph patternNOT EXISTSmulti-path
Cypher Query
MATCH (c:Customer)-[:REVIEWED]->(p:Product) WHERE NOT (c)-[:PLACED]->()-[:CONTAINS]->(p) RETURN c.name AS customer, p.name AS reviewedProduct, p.sku AS sku
Expected output (1 row — Dan reviewed Bamboo Cutting Board but never ordered it)
"Dan Reyes" · "Bamboo Cutting Board" · SKU-011
🧠 Graph-native thinking
This kind of query — "connected via path A but NOT via path B" — is idiomatic graph reasoning. It's used for fraud detection ("has a link to this account but no legitimate purchase history"), data quality checks, and content moderation pipelines.
Explanation

The query finds every Customer → REVIEWED → Product pair, then filters out any pairs where the customer also traversed Customer → PLACED → Order → CONTAINS → Product to the same product. The () in the NOT pattern is an anonymous Order node — we don't care which order, just whether any purchase path exists.

In SQL this would require a LEFT JOIN followed by a WHERE IS NULL check, or a NOT EXISTS correlated subquery with a multi-table join inside it. In Cypher it's a single declarative WHERE clause.

Dan was set up this way in Task 01 deliberately — he reviewed the Bamboo Cutting Board but only ever ordered a Webcam HD.

Find Products Co-Purchased with a Given Product
Find products that appear in the same order as the Wireless Headphones (SKU-001). This is "customers who bought X also bought Y" — a 4-hop graph pattern.
co-purchase4-hopcount()
Cypher Query
MATCH (target:Product {sku: $sku}) <-[:CONTAINS]-(o:Order) -[:CONTAINS]->(other:Product) WHERE other <> target RETURN other.name AS coPurchasedWith, count(o) AS coOccurrences ORDER BY coOccurrences DESC // :param sku => "SKU-001" (Wireless Headphones)
Expected output
"USB-C Hub" · 2 co-occurrences
"Mechanical Keyboard" · 1 co-occurrence
✦ This is a recommendation engine in 5 lines
Scale this to millions of products and it becomes the foundation of "Frequently Bought Together." The graph traversal cost grows with the neighborhood of SKU-001, not with the total number of orders — that's index-free adjacency in practice.
Explanation

The path is: target product ← (CONTAINS) — Order — (CONTAINS) → other product. Reading it out loud: "find orders that contain the target product, then find all other products those orders also contain." This is a 2-hop traversal from the product's perspective.

WHERE other <> target prevents the product from being listed as co-purchased with itself. Without this, SKU-001 would appear in its own results.

count(o) counts how many distinct orders contain both products — a simple co-occurrence frequency. For a real recommendation engine you'd weight by recency, purchase rate, and similarity score, but this pattern is the foundation.

Collaborative Filtering Recommendation
For a given customer, find products bought by customers who share at least one purchase with them — but that the given customer hasn't bought yet. A 6-hop traversal.
6-hopNOT EXISTSDISTINCT
Cypher Query
MATCH (me:Customer {email: $email}) -[:PLACED]->()-[:CONTAINS]->(shared) <-[:CONTAINS]-()-[:PLACED]<- (similar:Customer) -[:PLACED]->()-[:CONTAINS]->(rec:Product) WHERE similar <> me AND NOT (me)-[:PLACED]->()-[:CONTAINS]->(rec) RETURN DISTINCT rec.name AS recommendation, rec.sku AS sku, rec.price AS price ORDER BY rec.price DESC // :param email => "alice@example.com"
Expected output for Alice (products bought by Felix, who shares purchases with Alice)
"Cast Iron Skillet" · SKU-010 · 44.99
Explanation

This is a 6-hop traversal that implements basic collaborative filtering: me → my orders → products I bought → orders containing same products → similar customers → their other products.

The two WHERE conditions are essential: similar <> me prevents self-recommendation, and NOT (me)-[:PLACED]->()-[:CONTAINS]->(rec) filters out products Alice has already purchased.

In SQL this would require 5+ joins and multiple NOT EXISTS subqueries. Here it's one MATCH pattern with two WHERE filters — the same cognitive model you use to describe the problem in English maps directly to the Cypher structure.

This is why graph databases are the default choice for recommendation engines: the query expresses the algorithm, not the join plumbing.

OPTIONAL MATCH — All Customers Including Those Without Orders
List every customer with the total amount they've spent. Customers who have placed no orders should appear with a spend of 0, not be dropped from the result.
OPTIONAL MATCHcoalesce()LEFT JOIN
Cypher Query
MATCH (c:Customer) OPTIONAL MATCH (c)-[:PLACED]->(o:Order) RETURN c.name AS customer, coalesce(sum(o.total), 0.0) AS totalSpend, count(o) AS orderCount ORDER BY totalSpend DESC
Expected output (9 rows — Ivan from Task 08 has 0 spend)
"Alice Novak" · totalSpend: 403.96 · orders: 3
"Felix Huang" · totalSpend: 273.97 · orders: 3
…
"Ivan Petrov" · totalSpend: 0.0 · orders: 0
Explanation

OPTIONAL MATCH is the Cypher equivalent of a LEFT JOIN. When no matching Order is found for a customer, the variable o is null instead of dropping the row entirely.

coalesce(sum(o.total), 0.0) handles the null case — if sum returns null (because all values were null), replace it with 0.0. Without coalesce, customers with no orders would show null in the spend column.

Compare this to Task 07 where a plain MATCH on the PLACED relationship meant that customers without orders didn't appear in results at all. Choosing between MATCH and OPTIONAL MATCH is the same decision as choosing between INNER JOIN and LEFT JOIN in SQL.

Find Highest-Rated Products
Return all products that have at least one review, with their average rating and review count. Show only products with an average rating of 4.0 or higher.
avg()WITH filterHAVING analog
Cypher Query
MATCH (c:Customer)-[r:REVIEWED]->(p:Product) WITH p, avg(r.rating) AS avgRating, count(r) AS reviewCount, collect(r.text) AS reviewTexts WHERE avgRating >= 4.0 RETURN p.name AS product, avgRating, reviewCount, reviewTexts ORDER BY avgRating DESC, reviewCount DESC
Expected output
"Running Shoes" · avg: 4.67 (Felix added 4★) · 3 reviews
"Wireless Headphones" · avg: 5.0 · 1 review
"Chef's Knife" · avg: 4.0 · 1 review
"Mechanical Keyboard" · avg: 4.0 · 1 review
"Bamboo Cutting Board"· avg: 4.0 · 1 review
Explanation

WITH p, avg(r.rating) AS avgRating is the Cypher equivalent of SQL's GROUP BY p HAVING avg(rating) >= 4.0. The WITH clause computes the aggregation and passes it forward; the subsequent WHERE then filters on the computed value.

You cannot filter on an aggregate in the same clause that computes it (just like SQL doesn't allow WHERE avg(...)). The pattern is always: aggregate in WITH, filter in the following WHERE.

collect(r.text) builds a list of all review texts for each product — equivalent to GROUP_CONCAT in MySQL. The result is a native list type that you can iterate in application code.

Top Products by Total Revenue
Calculate total revenue per product (sum of qty × unit_price across all orders). Return the top 5, with category name included. This uses relationship properties and a category traversal in the same query.

Cypher Query
MATCH (o:Order)-[line:CONTAINS]->(p:Product) -[:IN_CATEGORY]->(cat:Category) WITH p, cat, sum(line.qty * line.unit_price) AS revenue, sum(line.qty) AS unitsSold RETURN p.name AS product, cat.name AS category, revenue, unitsSold ORDER BY revenue DESC LIMIT 5

"Wireless Headphones" · Electronics · revenue: 269.97
"Mechanical Keyboard" · Electronics · revenue: 357.00
"Running Shoes" · Sports · revenue: 224.97

Explanation

This query traverses two hops from Order: Order → Product → Category. By including the category in the MATCH pattern, we can return it without a second query or a join — the graph naturally carries the relationship.
