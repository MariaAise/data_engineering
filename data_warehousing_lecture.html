Lecture reference — from dimensional modeling fundamentals to the 2025 platform landscape

1 Dimensional modeling

Dimensional modeling is the foundational technique for organizing data in a warehouse so that it is optimized for query performance and human comprehension. The core idea: separate what happened (facts) from the context in which it happened (dimensions).

Star schema

The star schema is the most common dimensional model. A central fact table holds quantitative measures (revenue, quantity, cost) at a specific grain. Surrounding dimension tables describe the context — who, what, where, when.

Fact table characteristics: Composite primary key formed by foreign keys to dimension tables. Contains numeric, additive measures. Each row represents one business event at the defined grain (e.g., one sale, one transaction, one shipment).

Dimension table characteristics: Single-column surrogate primary key. Contains descriptive text attributes used for filtering, grouping, and labeling. Typically denormalized — wide tables with many columns.

Grain — the most important design decision

The grain defines the level of detail in the fact table. "One row per transaction per product per store per day" is a grain statement. Every dimensional model starts here. Get the grain wrong and the entire model is unreliable.

Snowflake schema

A snowflake schema normalizes dimension tables into sub-dimensions. A product dimension splits into product → category → department. This reduces storage redundancy but adds join complexity. Used when dimension tables are very large or when normalization is required for governance.

Fact constellations (galaxy schema)

Multiple fact tables sharing dimension tables. A retail business might have a sales_fact and an inventory_fact both referencing the same product and store dimensions. This is the standard pattern for any warehouse with more than one business process.

Slowly changing dimensions (SCDs)

Type 1 — Overwrite

Replace the old value with the new one. No history preserved. A customer changes their address — the old address is gone. Simple, but you lose the ability to analyze historical context.

Type 2 — Add new row

Insert a new row with the updated value, mark the old row as expired (using effective/expiry dates or a current flag). Full history preserved. The standard approach for any dimension where historical analysis matters.

Type 3 — Add new column

Add a "previous value" column alongside the current one. Only tracks the most recent change, not full history. Rarely used in practice — Type 2 is almost always preferred.

Surrogate keys vs natural keys

Warehouses use surrogate keys (auto-incrementing integers) as primary keys rather than natural business keys (product codes, employee IDs). Surrogate keys are system-generated, meaning they insulate the warehouse from source system changes — if a product code format changes upstream, the warehouse doesn't break. They also enable SCD Type 2 tracking: the same natural key can have multiple surrogate keys representing different historical versions.

2 OLAP operations

OLAP (Online Analytical Processing) is a paradigm for interactive, multidimensional analysis of business data. The mental model is a data cube — a multi-dimensional array where each axis represents a dimension (time, product, geography) and each cell contains a measure (revenue, quantity).

The five core operations

OperationWhat it doesExample
Roll-upAggregate to a higher level in a hierarchy, or reduce a dimension entirelyCity → State → Country. Monthly sales → Quarterly sales
Drill-downDecompose to a finer grain — the reverse of roll-upCountry → State → City. Annual → Quarterly → Monthly
SliceFix one dimension to a single value, producing a sub-cubeAll sales where year = 2024
DiceFilter on two or more dimensions simultaneouslySales where year IN (2023, 2024) AND region IN ('APAC', 'EMEA')
PivotRotate the axes to get a different cross-tabulationSwap rows and columns — product on rows vs time on rows

Hierarchies and concept levels

Dimensions have natural hierarchies that enable roll-up and drill-down. Time: day → week → month → quarter → year. Geography: store → city → state → country → region. Product: SKU → subcategory → category → department. The hierarchy defines what "up" and "down" mean in the context of that dimension.

Measure classification

Distributive

Can be computed by partitioning data and combining partial results. SUM, COUNT, MIN, MAX.

Algebraic

Derived from a bounded number of distributive aggregates. AVG = SUM/COUNT. STDDEV.

Holistic

No constant bound on intermediate storage. MEDIAN, MODE, RANK. Expensive to compute on large cubes.

SQL implementation of OLAP

Modern SQL engines implement OLAP operations natively, eliminating the need for dedicated cube servers in many cases:

-- ROLLUP: hierarchical aggregation (country → state → city → grand total)
SELECT country, state, city, SUM(revenue)
FROM sales_fact f JOIN store_dim s ON f.store_key = s.store_key
GROUP BY ROLLUP(country, state, city);

-- CUBE: all combinations of dimensions
SELECT category, quarter, SUM(revenue)
FROM sales_fact f JOIN product_dim p ON f.product_key = p.product_key
GROUP BY CUBE(category, quarter);

-- GROUPING SETS: specific aggregation combinations
SELECT category, region, SUM(revenue)
FROM sales_fact
GROUP BY GROUPING SETS(
  (category, region),
  (category),
  (region),
  ()
);

3 Warehouse architecture

Three-tier architecture

Source systems
→
Staging / ETL
→
Data warehouse
→
Data marts / BI

Source systems — operational databases (OLTP), CRMs, ERPs, SaaS APIs, flat files, event streams. Optimized for transaction processing, not analysis.

Staging area — a landing zone where raw data is temporarily stored before transformation. No business logic applied here. Purpose: decouple extraction from transformation so failures don't cascade.

Data warehouse — the integrated, subject-oriented, time-variant, non-volatile repository. This is where dimensional models live and historical data accumulates.

Data marts — subject-specific subsets of the warehouse scoped to a department or business function (marketing mart, finance mart). Smaller, faster, easier for end users to navigate.

ETL vs ELT

ETL — Extract, Transform, Load

Transform happens before loading into the warehouse. A separate ETL server (Informatica, SSIS, Talend) handles transformation logic. Traditional approach — necessary when warehouse compute was expensive and limited.

ELT — Extract, Load, Transform

Load raw data first, transform inside the warehouse using its own compute power. Modern approach — made possible by cheap, scalable cloud warehouse compute (Snowflake, BigQuery). dbt is the dominant transformation tool in ELT workflows.

Kimball vs Inmon

4 The lakehouse convergence

Three eras of analytical data architecture

Data warehouse (1990s–2010s)

Schema-on-write. Structured data only. Expensive proprietary storage (Teradata, Netezza, Oracle Exadata). Strong governance, ACID transactions, reliable. But rigid — adding new data sources or schema changes required significant rework, and unstructured data (logs, images, JSON) didn't fit.

Data lake (2010s)

Schema-on-read. Cheap object storage (HDFS, then S3/ADLS/GCS). Handles any data type — structured, semi-structured, unstructured. But lacked ACID transactions, schema enforcement, and data quality guarantees. The "data swamp" problem: data goes in, nobody trusts what comes out.

Data lakehouse (2020s–present)

The convergence. Open table formats bring warehouse-grade reliability to lake storage: ACID transactions, schema enforcement, time travel (query historical snapshots), partition evolution — all on top of cheap cloud object storage. You get warehouse trust at lake economics. This is the dominant new-build architecture pattern in 2025.

Open table formats — the enabling technology

FormatOriginPhilosophy
Delta LakeDatabricksSpark-native simplicity. Transaction log tracks file-level changes. Dominant in the Databricks ecosystem.
Apache IcebergNetflix → ApacheVendor-neutral openness. Snapshot-based metadata. Adopted by Snowflake, AWS, Dremio, and increasingly the default open standard.
Apache HudiUber → ApacheOptimized for streaming updates and upserts/deletes. Strong for CDC (change data capture) workloads.

All three provide ACID transactions, time travel, schema evolution, and partition pruning on files stored in object storage. They achieve this by tracking metadata about files (manifests, snapshot logs) rather than relying on directory structures like legacy Hive tables.

Medallion architecture

The modern replacement for monolithic ETL pipelines. Data flows through three progressive refinement layers:

Bronze
→
Silver
→
Gold
Bronze Raw ingestion

Exactly as received from source systems. Append-only, idempotent. The single source of truth — you can always replay from here. No business logic applied.

Silver Cleaned & conformed

Deduplication, type casting, schema enforcement, null handling, cross-source joins. This is where data quality happens. Conformed dimensions emerge here.

Gold Business-ready

Aggregated, modeled, consumption-ready. Star schemas live here — Kimball methodology didn't die, it moved to the gold layer. This is what analysts and BI tools query.

Warehouses are adding lake features (Snowflake supports Iceberg, BigQuery can query Cloud Storage directly). 6 The semantic layer

The problem

Sales says revenue is $18M. Finance says $17.2M. Both are "correct" — they're just calculated differently (different filters, different date logic, different currency handling). This inconsistency across teams and tools is the single most common source of organizational distrust in data.

Legacy solution → modern solution

The legacy approach was to bake metric logic into OLAP cubes — pre-aggregated, pre-defined. This solved consistency but created rigidity (new dimensions required rebuilding the cube) and vendor lock-in.

The modern approach: a semantic layer that defines metrics once, in code, and serves them to every consuming tool (BI dashboards, notebooks, AI agents, APIs).

SolutionApproachBest for
dbt Semantic Layer / MetricFlowMetrics-as-code in YAML, version-controlled in Git, warehouse-native SQL executionMulti-cloud, vendor-neutral environments
Cube.devOLAP-style pre-aggregation as a service, REST/GraphQL APIEmbedded analytics, sub-second latency requirements
Snowflake Semantic ViewsNative database objects storing metric definitionsAll-Snowflake environments
Databricks Metric ViewsUnity Catalog-governed metric definitionsLakehouse-centric organizations
Why AI cares about the semantic layer

LLMs querying a semantic layer are dramatically more accurate than LLMs querying raw tables. The semantic layer provides the business context (what "revenue" means, which filters to apply, how dimensions join) that models need to generate correct SQL. The semantic layer is becoming AI infrastructure, not just BI infrastructure.

7 Real-time analytics

Batch vs streaming

Traditional warehouses operate on batch cycles — nightly or hourly ETL loads. The data is always at least hours behind reality. Increasingly, business decisions require data that is seconds or minutes old, not hours.

Streaming infrastructure

Apache Kafka — distributed event streaming platform, the industry standard. Amazon Kinesis — AWS-native streaming. Google Pub/Sub — GCP-native. These systems ingest millions of events per second and deliver them to consumers in real time.

Real-time OLAP engines

ClickHouse — column-oriented, sub-second queries on billions of rows. Apache Druid — real-time ingestion + fast aggregation. Apache Pinot — LinkedIn-origin, optimized for user-facing analytics. Used when even modern warehouse latency isn't fast enough.

Incremental transformation

Instead of reprocessing entire tables on each run, modern tools transform only what changed:

dbt incremental models — SQL-based, processes only new/modified rows since the last run. Configurable merge strategies.

Apache Hudi upserts — row-level inserts, updates, and deletes on lake storage. Designed for CDC (change data capture) from source systems.

Spark Structured Streaming — continuous micro-batch processing on Delta Lake tables.

Use cases that demand real-time

Fraud detection (decisions in milliseconds), dynamic pricing (react to demand signals), operational dashboards (warehouse throughput, system health), IoT sensor analytics (manufacturing, logistics), real-time personalization (recommendations, ad targeting).

8 Governance & quality

Governance is where data warehouse projects succeed or fail. The technology is secondary — the organizational discipline around data ownership, quality, and access control is what determines whether anyone trusts the numbers.

Data catalogs

A catalog answers: what data exists, who owns it, where did it come from, and is it any good?

CatalogContext
Unity CatalogDatabricks-native. Governs tables, models, notebooks, dashboards in one place.
Snowflake HorizonSnowflake-native. Built-in discovery, lineage, access policies.
Alation / AtlanThird-party, vendor-neutral catalogs. Work across multiple platforms.

Lineage

Column-level tracking from source system to final dashboard. When a number looks wrong, lineage lets you trace it backwards through every transformation to the originating record. Critical for debugging, auditing, and regulatory compliance.

Access control

Row-level security — a sales rep sees only their region's data. Column masking — PII columns are masked for non-privileged users. Role-based access — permissions managed by role (analyst, engineer, admin), not individual user. These are now built into platforms (Snowflake, Databricks) rather than bolted on after the fact.

Data quality tooling

dbt tests

Schema tests (not null, unique, accepted values, referential integrity) defined in YAML alongside your models. Run on every pipeline execution.

Great Expectations

Python-based. Define "expectations" (column ranges, distribution shapes, row counts) as code. Generates data quality reports.

Soda

SQL-based checks with a YAML config. Integrates with orchestrators (Airflow, Dagster). Monitors data quality in production.

Data Vault 2.0

An alternative modeling methodology optimized for the silver layer. Three building blocks: Hubs (business entities with a unique key), Links (relationships between hubs), Satellites (descriptive attributes with full history). Designed for auditability, multi-source integration, and handling schema changes gracefully. Growing adoption in regulated industries (banking, healthcare) where full traceability is non-negotiable.

Analytics engineer — the fastest-growing role

Emerged in the late 2010s as the bridge between data engineering and data analysis. Owns the transformation layer (dbt models), dimensional models, and metric definitions. Doesn't build pipelines from scratch (that's the data engineer) and doesn't build dashboards (that's the analyst) — instead ensures that the data flowing between them is modeled correctly, tested, documented, and trustworthy.

The universal toolkit

Across all four roles, the common denominators are: SQL (still the lingua franca of data — every platform speaks it), dbt (the transformation standard), Python (for everything SQL can't do), one cloud platform (Snowflake, Databricks, or BigQuery — know at least one deeply), one BI tool (Tableau, Power BI, or Looker — the consumption layer). The dimensional modeling, OLAP operations, and warehouse architecture concepts from this lecture are the vocabulary that makes all of these tools intelligible.
