01

How to Think About & Build a Query

Start here — the mental model that makes everything else click.
The 6-Step Mental Model — Write Queries in This Order
1
FROM — What data do I need?
Name the table (or tables) that hold the data you're working with. This is your starting point.
FROM orders o
2
JOIN — Do I need data from other tables?
If your answer requires columns from multiple tables, add the relevant JOINs now. Match on the shared key.
JOIN customers c ON o.customer_id = c.id
3
WHERE — What rows qualify?
Filter the rows before any grouping or aggregation. This operates on raw row data, not computed values.
WHERE o.status = 'completed' AND o.created_at >= '2024-01-01'
4
GROUP BY — Do I need to summarise?
Only needed when using aggregate functions (COUNT, SUM, AVG…). Group by every non-aggregated column in SELECT.
GROUP BY c.id, c.name
5
HAVING — Filter on the summary?
Like WHERE but operates on aggregated results. Only use when you need to filter on a COUNT, SUM, AVG etc.
HAVING COUNT(o.id) > 3
6
SELECT — What columns do I return?
Now that you know your rows and groups, specify exactly what to return. Apply expressions, aliases, and functions here.
SELECT c.name, COUNT(o.id) AS order_count, SUM(o.total) AS revenue
Logical Execution Order (how MySQL actually runs it)

MySQL processes clauses in this order — not the order you write them. This is why a SELECT alias cannot be used in WHERE.

FROM→ JOIN→ WHERE→ GROUP BY→ HAVING→ SELECT→ DISTINCT→ ORDER BY→ LIMIT
Key rule: You cannot reference a SELECT alias in WHERE or HAVING because SELECT hasn't been evaluated yet. Wrap it in a subquery or CTE instead.
Full Query — Putting It All Together 
SELECT
    c.name                    AS customer,
    COUNT(o.id)              AS order_count,
    SUM(o.total)             AS revenue,
    ROUND(AVG(o.total), 2)  AS avg_order
FROM   orders    o
JOIN   customers c  ON o.customer_id = c.id
WHERE  o.status  = 'completed'
  AND  o.created_at >= '2024-01-01'
GROUP BY  c.id, c.name
HAVING    COUNT(o.id) > 3
ORDER BY  revenue DESC
LIMIT     10;
02

SELECT

Organized into four logical groups: scalar, filtering & sorting, aggregation, rollups.
Group A — Scalar & Column Expressions
Basic Column Selection & Expressions 
-- Specific columns
SELECT id, first_name, last_name FROM users;

-- Aliased columns
SELECT
    first_name           AS fname,
    last_name            AS lname,
    salary * 1.1        AS new_salary,
    CONCAT(first_name, ' ', last_name) AS full_name
FROM employees;

-- DISTINCT — deduplicate results
SELECT DISTINCT department FROM employees;
CASE WHEN — Conditional Column Values 
SELECT
    name,
    salary,
    -- Searched CASE (conditions)
    CASE
        WHEN salary >= 90000 THEN 'Senior'
        WHEN salary >= 60000 THEN 'Mid'
        ELSE                      'Junior'
    END AS level,
    -- Simple CASE (equality match)
    CASE status
        WHEN 'A' THEN 'Active'
        WHEN 'I' THEN 'Inactive'
        ELSE       'Unknown'
    END AS status_label
FROM employees;
NULL-Handling & Conditional Functions 
SELECT
    -- First non-NULL value
    COALESCE(phone, mobile, 'N/A')   AS contact,
    -- Return NULL if equal, else first value
    NULLIF(division, 'None')          AS division,
    -- Inline if/else
    IF(is_active, 'Active', 'Inactive') AS status,
    -- NULL check shorthand
    IFNULL(notes, '—')               AS notes
FROM employees;
Prefer COALESCE — it's portable across SQL dialects and handles multiple fallbacks.

Group B — Filtering, Sorting & Limiting
WHERE — All Operators 
SELECT * FROM products
WHERE
    -- Comparison
    price > 100
    AND stock <> 0           -- <> same as !=

    -- Range (inclusive)
    AND price BETWEEN 10 AND 500

    -- List membership
    AND category IN ('Books', 'Electronics')
    AND tag NOT IN ('archived', 'draft')

    -- Pattern matching
    AND name   LIKE '%Pro%'   -- contains
    AND sku    LIKE 'A___'    -- A + 3 chars
    AND serial REGEXP '^[A-Z]{2}[0-9]+'

    -- NULL checks
    AND deleted_at IS NULL
    AND notes     IS NOT NULL;
ORDER BY, LIMIT & OFFSET 
-- Multi-column sort
SELECT * FROM employees
ORDER BY
    department  ASC,
    salary      DESC,
    last_name   ASC;

-- NULLs at the end (workaround for MySQL)
ORDER BY
    bonus IS NULL ASC,   -- FALSE(0) before TRUE(1)
    bonus DESC;

-- Pagination with LIMIT + OFFSET
SELECT * FROM products
ORDER BY created_at DESC
LIMIT  20             -- rows per page
OFFSET 40;            -- skip 40 rows (page 3)

-- Shorthand: LIMIT offset, count
LIMIT 40, 20;
EXISTS vs IN — When to Use Which 
-- IN: good for small static lists or subqueries
SELECT * FROM orders
WHERE customer_id IN (
    SELECT id FROM customers
    WHERE country = 'AU'
);

-- EXISTS: better for large tables — stops on first match
SELECT * FROM customers c
WHERE EXISTS (
    SELECT 1 FROM orders o
    WHERE o.customer_id = c.id   -- correlated
);

-- NOT EXISTS: find customers with no orders
WHERE NOT EXISTS (
    SELECT 1 FROM orders
    WHERE customer_id = c.id
);
ANY & ALL with Subqueries 
-- ANY: true if condition matches at least one row
SELECT name FROM products
WHERE price > ANY (
    SELECT price FROM products
    WHERE category = 'Budget'
);
-- ↑ price > the minimum budget price

-- ALL: true if condition matches every row
SELECT name FROM products
WHERE price > ALL (
    SELECT price FROM products
    WHERE category = 'Budget'
);
-- ↑ price > every budget product (i.e. > max)
> ANY ≡ > MIN(...)  |  > ALL ≡ > MAX(...)
Group C — Aggregation & GROUP BY
Aggregate Functions 
SELECT
    department,
    COUNT(*)                   AS headcount,
    COUNT(DISTINCT job_title)   AS unique_roles,
    SUM(salary)                 AS total_payroll,
    AVG(salary)                 AS avg_salary,
    MIN(hire_date)              AS earliest_hire,
    MAX(salary)                 AS top_salary,
    -- Aggregate only active employees
    SUM(CASE WHEN active = 1
          THEN salary ELSE 0 END) AS active_payroll,
    -- Ratio via conditional count
    AVG(active)                 AS active_ratio
FROM     employees
GROUP BY department
HAVING   COUNT(*) > 2
ORDER BY total_payroll DESC;
GROUP_CONCAT — Aggregate Strings 
-- Collapse multiple rows into one string per group
SELECT
    department,
    GROUP_CONCAT(name ORDER BY name SEPARATOR ', ')
        AS members
FROM     employees
GROUP BY department;

Result example:

Engineering | Alice, Bob, Carol
Marketing   | Dave, Eve
-- Distinct values, custom length limit
GROUP_CONCAT(DISTINCT tag
    ORDER BY tag
    SEPARATOR '|')
-- Default max length: 1024 chars
-- Increase: SET group_concat_max_len = 65535;
Window Functions — Aggregation Without Collapsing Rows (MySQL 8+) 
-- OVER() keeps all rows, adds derived column
SELECT
    name, department, salary,
    SUM(salary)  OVER (PARTITION BY department)
        AS dept_total,
    AVG(salary)  OVER (PARTITION BY department)
        AS dept_avg,
    RANK()       OVER (PARTITION BY department
                       ORDER BY salary DESC)
        AS rank_in_dept
FROM employees;

-- Running total across all rows
SUM(amount) OVER (ORDER BY sale_date
    ROWS BETWEEN UNBOUNDED PRECEDING
             AND CURRENT ROW)
    AS running_total
FunctionWhat it does
ROW_NUMBER()Unique sequential number (no ties)
RANK()Rank with gaps after ties (1,1,3)
DENSE_RANK()Rank without gaps (1,1,2)
NTILE(n)Divide rows into n buckets
LAG(col, n)Value from n rows before
LEAD(col, n)Value from n rows ahead
FIRST_VALUE(col)First value in window frame
LAST_VALUE(col)Last value in window frame
SUM / AVG OVER()Running or partitioned aggregates
PARTITION BY = GROUP BY equivalent inside window.
ORDER BY inside OVER = defines row sequence within the window.
Group D — Rollups & Grouping Sets
WITH ROLLUP — Subtotals & Grand Total 
-- Adds subtotal rows and a grand total automatically
SELECT
    department,
    job_title,
    SUM(salary) AS payroll
FROM     employees
GROUP BY department, job_title WITH ROLLUP;

Result — NULL marks rollup rows:

Engineering  Backend    320000
Engineering  Frontend   180000
Engineering  NULL       500000  ← dept subtotal
Marketing    NULL        90000  ← dept subtotal
NULL         NULL       590000  ← grand total
-- GROUPING() = 1 on rollup rows, 0 on normal rows
SELECT
    IF(GROUPING(department), 'ALL', department) AS dept,
    IF(GROUPING(job_title),  'ALL', job_title)  AS title,
    SUM(salary) AS payroll
FROM employees
GROUP BY department, job_title WITH ROLLUP;
UNION & UNION ALL — Combine Result Sets 
-- UNION: removes duplicates (slower)
SELECT email, 'customer' AS source FROM customers
UNION
SELECT email, 'supplier'             FROM suppliers;

-- UNION ALL: keeps duplicates (faster, prefer this)
SELECT id, total, created_at FROM orders_2023
UNION ALL
SELECT id, total, created_at FROM orders_2024
ORDER BY created_at DESC;   -- ORDER BY goes last

-- INTERSECT / EXCEPT emulation (pre MySQL 8.0.31)
-- Intersect: emails in both tables
SELECT email FROM customers
WHERE email IN (SELECT email FROM newsletter);

-- Except: customers NOT in unsubscribes
SELECT email FROM customers
WHERE email NOT IN (SELECT email FROM unsubscribes);
Column count & types must match across all UNION parts. Use NULL AS col_name to pad missing columns.
03

INSERT / UPDATE / DELETE

Data Manipulation Language — always use WHERE with UPDATE and DELETE.
INSERT — All Forms 
-- Single row
INSERT INTO users (name, email, role)
VALUES ('Alice', 'alice@acme.com', 'admin');

-- Multiple rows (one trip to the server)
INSERT INTO users (name, email, role)
VALUES
    ('Bob',   'bob@acme.com',   'user'),
    ('Carol', 'carol@acme.com', 'user');

-- Insert from a SELECT
INSERT INTO archive_orders (id, total, closed_at)
SELECT id, total, NOW()
FROM  orders
WHERE status = 'closed';

-- INSERT … ON DUPLICATE KEY UPDATE (upsert)
INSERT INTO page_views (page_id, views)
VALUES (42, 1)
ON DUPLICATE KEY UPDATE
    views = views + 1;

-- REPLACE INTO: delete + re-insert if PK exists
REPLACE INTO settings (key_name, value)
VALUES ('theme', 'dark');
UPDATE — Single, Multi-Table & Safe Patterns 
-- Single-table update
UPDATE employees
SET
    salary    = salary * 1.05,
    updated_at = NOW()
WHERE department = 'Engineering'
  AND hire_date < '2023-01-01';

-- Multi-table update (JOIN)
UPDATE orders o
JOIN   customers c ON o.customer_id = c.id
SET    o.priority = 'high'
WHERE  c.tier = 'vip';

-- UPDATE with subquery
UPDATE products
SET    stock = 0
WHERE  id IN (
    SELECT product_id FROM discontinued
);
⚠ Safety: Run SELECT with the same WHERE before executing UPDATE/DELETE. Check @@sql_safe_updates = 1 blocks updates without a WHERE clause.
DELETE & TRUNCATE 
-- Delete specific rows
DELETE FROM sessions
WHERE  expires_at < NOW();

-- Multi-table delete
DELETE o, oi
FROM  orders      o
JOIN  order_items oi ON oi.order_id = o.id
WHERE o.status = 'cancelled';

-- LIMIT deletions (for large tables)
DELETE FROM logs
WHERE  created_at < '2022-01-01'
LIMIT  10000;   -- batch to avoid lock contention

-- TRUNCATE: wipe all rows instantly
-- ⚠ cannot be rolled back in most storage engines
TRUNCATE TABLE temp_imports;
Transactions — Wrapping DML Safely 
START TRANSACTION;

UPDATE accounts SET balance = balance - 500
WHERE  id = 1;

UPDATE accounts SET balance = balance + 500
WHERE  id = 2;

-- All or nothing
COMMIT;     -- persist both changes
-- or:
ROLLBACK;   -- undo everything since START

-- Savepoints for partial rollback
SAVEPOINT sp1;
UPDATE ...; -- risky operation
ROLLBACK TO SAVEPOINT sp1;
COMMIT;
04

JOINs

The most important concept in relational SQL. Master the visual logic first.
Visual Guide — What Each JOIN Returns
INNER JOIN
Only rows matching in both tables. Most common join.
LEFT JOIN
All left table rows + matching right. NULLs for non-matches.
RIGHT JOIN
All right table rows + matching left. Rarely preferred over LEFT.
FULL OUTER
All rows from both. NULLs on either side. Emulate via UNION in MySQL.
LEFT EXCL.
Left rows with no match on right. Find orphaned records.
RIGHT EXCL.
Right rows with no match on left.
INNER, LEFT, RIGHT JOIN Syntax 
-- INNER JOIN: only matched rows
SELECT o.id, c.name, o.total
FROM   orders    o
INNER JOIN customers c  ON o.customer_id = c.id;
-- (INNER is optional, JOIN alone = INNER JOIN)

-- LEFT JOIN: all orders, even if customer deleted
SELECT o.id, c.name, o.total
FROM   orders o
LEFT JOIN customers c ON o.customer_id = c.id;

-- Find orders WITH NO customer (orphaned)
SELECT o.id
FROM   orders o
LEFT JOIN customers c ON o.customer_id = c.id
WHERE  c.id IS NULL;   -- ← LEFT EXCLUSIVE
Chained JOINs & Multiple Conditions 
-- Chain as many JOINs as you need
SELECT
    o.id        AS order_id,
    c.name      AS customer,
    p.title     AS product,
    oi.qty,
    a.city      AS ship_city
FROM      orders      o
JOIN      customers   c  ON o.customer_id  = c.id
JOIN      order_items oi ON o.id           = oi.order_id
JOIN      products    p  ON oi.product_id  = p.id
LEFT JOIN addresses   a  ON o.address_id   = a.id
                          AND a.type         = 'shipping'
WHERE o.status = 'shipped';

-- Multi-condition JOIN (compound key)
JOIN prices p
    ON p.product_id = oi.product_id
   AND p.region     = o.region
   AND p.valid_from <= o.order_date
Self-Join & Cross Join 
-- Self-join: employee → manager (same table)
SELECT
    e.name  AS employee,
    m.name  AS manager
FROM      employees e
LEFT JOIN employees m  ON e.manager_id = m.id;

-- Cross join: every combination (cartesian)
SELECT s.size, c.colour
FROM   sizes   s
CROSS JOIN colours c;
-- 3 sizes × 4 colours = 12 rows

-- FULL OUTER JOIN emulation (MySQL)
SELECT * FROM a LEFT JOIN  b ON a.id = b.a_id
UNION
SELECT * FROM a RIGHT JOIN b ON a.id = b.a_id;
JOIN Anti-Patterns to Avoid
Anti-patternWhy it's wrong
JOIN without ONCreates a cartesian product — every row × every row
SELECT * with JOINAmbiguous columns, returns duplicated join keys
JOIN on non-indexed FKFull table scan on every join — very slow at scale
Too many LEFT JOINsConsider whether you actually need all those NULLs
NOT IN with NULLsIf subquery can return NULL, NOT IN returns no rows — use NOT EXISTS instead
Rule of thumb: always alias tables when joining, qualify every column with its alias — prevents ambiguity errors.
05

Subqueries & CTEs

Subqueries for inline logic; CTEs for readable, reusable named results.
Subquery in WHERE / HAVING 
-- Scalar subquery: returns single value
SELECT name, salary
FROM   employees
WHERE  salary > (SELECT AVG(salary) FROM employees);

-- IN subquery: returns a list
SELECT * FROM orders
WHERE  customer_id IN (
    SELECT id FROM customers
    WHERE  tier = 'vip'
);

-- Correlated: references outer query (runs per row)
SELECT name, salary, department
FROM   employees e
WHERE  salary > (
    SELECT AVG(salary) FROM employees
    WHERE  department = e.department  -- outer ref
);
Subquery in FROM (Derived Table) 
-- Derived table: treat a subquery as a table
SELECT dept, avg_sal
FROM (
    SELECT
        department        AS dept,
        AVG(salary)       AS avg_sal,
        COUNT(*)         AS cnt
    FROM     employees
    GROUP BY department
) dept_summary            -- alias is required
WHERE avg_sal > 70000;

-- Subquery in SELECT (scalar)
SELECT
    name,
    salary,
    (SELECT AVG(salary) FROM employees) AS company_avg,
    salary - (SELECT AVG(salary) FROM employees) AS delta
FROM employees;
CTEs — WITH clause 
-- Simple CTE (named subquery, evaluated once)
WITH high_earners AS (
    SELECT id, name, salary
    FROM   employees
    WHERE  salary > 100000
)
SELECT * FROM high_earners
ORDER BY salary DESC;

-- Chained CTEs (reference earlier ones)
WITH
monthly AS (
    SELECT DATE_FORMAT(created_at, '%Y-%m') AS mo,
           SUM(total) AS rev
    FROM  orders GROUP BY mo
),
with_growth AS (
    SELECT mo, rev,
        LAG(rev) OVER (ORDER BY mo) AS prev_rev
    FROM monthly
)
SELECT mo, rev,
    ROUND((rev - prev_rev) / prev_rev * 100, 1) AS growth_pct
FROM with_growth
WHERE prev_rev IS NOT NULL;
Recursive CTE — Trees & Hierarchies (MySQL 8+) 
-- Walk an org chart / category tree
WITH RECURSIVE org AS (
    -- Anchor: top-level nodes
    SELECT id, name, manager_id, 0 AS depth,
           name AS path
    FROM   employees
    WHERE  manager_id IS NULL

    UNION ALL

    -- Recursive: join child to parent
    SELECT e.id, e.name, e.manager_id,
           o.depth + 1,
           CONCAT(o.path, ' › ', e.name)
    FROM   employees e
    JOIN   org o ON e.manager_id = o.id
)
SELECT depth, path, name
FROM   org
ORDER BY path;
MySQL default max recursion depth = 1000. Override: SET SESSION cte_max_recursion_depth = 5000;
Subquery vs CTE vs Temp Table — When to Use What
ApproachUse whenDrawback
Inline subquerySimple, one-off filter or scalar valueNested syntax, harder to debug; correlated ones run per row
CTE (WITH)Readable multi-step logic; reusing a result in the same query; recursionNot materialised by default — may re-evaluate; no persistent storage
Derived tableFilter/aggregate before joining to another tableMust alias; can't be referenced more than once
Temp tableHeavy computation used multiple times; materialised result neededSession-scoped; overhead to create; explicit cleanup

Indexes & Performance

Indexes are the single biggest lever for query speed. Understand them before optimizing anything else.
Creating & Managing Indexes 
-- Single-column index
CREATE INDEX idx_orders_status
    ON orders (status);

-- Composite (multi-column) index
-- Order matters: most selective first
CREATE INDEX idx_orders_cust_date
    ON orders (customer_id, created_at);

-- Unique index (enforce uniqueness + speed)
CREATE UNIQUE INDEX ux_users_email
    ON users (email);

-- Full-text index (for MATCH … AGAINST)
CREATE FULLTEXT INDEX ft_products_desc
    ON products (title, description);

-- Drop an index
DROP INDEX idx_orders_status ON orders;

-- Show all indexes on a table
SHOW INDEX FROM orders;
EXPLAIN — Read the Query Plan 
-- Basic EXPLAIN
EXPLAIN
SELECT * FROM orders
WHERE  customer_id = 42
  AND  status = 'completed';

-- EXPLAIN ANALYZE: actual runtime stats (8+)
EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 42;
EXPLAIN columnWhat to look for
typerefeq_refrange good  |  ALL = full scan = bad
keyWhich index is used. NULL = no index
rowsEstimated rows scanned — lower is better
ExtraUsing filesort = add ORDER BY index. Using temporary = review GROUP BY
possible_keysIndexes MySQL considered using
SARGable vs Non-SARGable WHERE Clauses

A SARGable condition can use an index. Wrapping a column in a function prevents index use.

-- ❌ Non-SARGable — function on column
WHERE YEAR(created_at) = 2024
WHERE LOWER(email) = 'alice@acme.com'
WHERE price + 10 > 100
WHERE SUBSTRING(sku, 1, 2) = 'AB'

-- ✅ SARGable rewrites
WHERE created_at BETWEEN '2024-01-01' AND '2024-12-31'
WHERE email = 'alice@acme.com'  -- use CI collation
WHERE price > 90
WHERE sku LIKE 'AB%'            -- prefix only
Performance Quick-Reference Rules
RuleReason
Avoid SELECT *Fetches unused columns, prevents covering indexes
Index foreign keysJOINs become fast; no FK = full scan on every join
Use UNION ALL not UNIONUNION deduplicates = extra sort pass; skip if data is already distinct
Prefer EXISTS over INEXISTS short-circuits on first match; IN scans all results
Avoid LIKE '%prefix'Leading wildcard can't use a B-tree index
Composite index col orderPut equality conditions first, range conditions last
Batch large DELETEsLIMIT 10000 per DELETE to avoid long locks
ANALYZE TABLERefreshes table stats so MySQL picks better plans
-- Force or ignore a specific index
SELECT * FROM orders FORCE INDEX (idx_orders_cust_date)
WHERE customer_id = 5;

-- Refresh optimizer statistics
ANALYZE TABLE orders;
