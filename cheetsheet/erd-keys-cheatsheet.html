00  /  At a Glance — All Key Types

A key is any column (or set of columns) that identifies or links rows. Every key type solves a different problem. The same column can simultaneously be multiple key types.

PK
Primary Key
The chosen unique row identifier. NOT NULL + UNIQUE. One per table.
FK
Foreign Key
References a PK in another table. Creates the relationship link.
AK
Alternate Key
A candidate key not chosen as PK. Still unique — enforce with UNIQUE constraint.
CPK
Composite Key
Two or more columns together form the PK. Standard in junction tables.
SK/NK
Surrogate / Natural
SK = system-generated ID. NK = real-world identifier. Choose wisely as your PK.

01  /  Primary Key PK

The one unique identifier chosen for every row

✓ Unique ✓ Not NULL ✗ Max 1 per table ✓ Indexed automatically

Every table must have exactly one primary key. It physically identifies each row and is referenced by foreign keys in other tables. It is always indexed automatically by the database engine.

studentID ← PK firstName lastName email
1001AliceChenalice@uni.edu
1002BobPatelbob@uni.edu
1003CaraMuñozcara@uni.edu
1004DanOkafordan@uni.edu
-- Primary key: single column, auto-increment CREATE TABLE student ( studentID INT PRIMARY KEY AUTO_INCREMENT, firstName VARCHAR(80) NOT NULL, lastName VARCHAR(80) NOT NULL, email VARCHAR(120) );
💡
Rule: studentID = 1001 never changes, even if Alice changes her name or email. The PK is the stable anchor everything else hangs off.

02  /  Foreign Key FK

The column that links a row to a row in another table

Can repeat Can be NULL (optional) ✓ Must reference a PK/UQ Multiple per table

A foreign key is how relationships are physically implemented. It holds the PK value of the related row. Referential integrity means the database rejects a value that doesn't exist in the referenced table.

enrollmentID studentID ← FK courseID ← FK grade
50011001CS101A
50021001MA201B+
50031002CS101A−
50041003PH301B
-- Two FKs linking enrollment to student + course CREATE TABLE enrollment ( enrollmentID INT PRIMARY KEY AUTO_INCREMENT, studentID INT NOT NULL, courseID CHAR(6) NOT NULL, grade VARCHAR(3), FOREIGN KEY (studentID) REFERENCES student(studentID) ON DELETE RESTRICT, FOREIGN KEY (courseID) REFERENCES course(courseID) ON DELETE RESTRICT );
💡
Read it: enrollment.studentID = 1001 means "this row belongs to Alice Chen." The FK is a pointer to another table's row.

03  /  Candidate & Alternate Keys CK / AK

All eligible PKs — and the runners-up

✓ Unique ✓ Not NULL Multiple candidates possible AK needs UNIQUE constraint

A Candidate Key is any column that could serve as the PK — unique and not null. You pick one to be the PK. Every remaining candidate becomes an Alternate Key, enforced with a UNIQUE constraint.

studentID ← PK (chosen) email ← AK (candidate not chosen) nationalID ← AK (candidate not chosen) firstName
1001alice@uni.eduAU-4829301Alice
1002bob@uni.eduAU-5571023Bob
1003cara@uni.eduAU-3398814Cara
1004dan@uni.eduAU-9901245Dan
-- studentID chosen as PK; email + nationalID become AKs CREATE TABLE student ( studentID INT PRIMARY KEY AUTO_INCREMENT, email VARCHAR(120) NOT NULL UNIQUE, -- AK nationalID VARCHAR(20) NOT NULL UNIQUE, -- AK firstName VARCHAR(80) NOT NULL );
💡
All three columns uniquely identify a student — they are all candidates. We chose studentID as PK because it's stable. Email could change; nationalID can be politically sensitive to store. Both still need UNIQUE constraints.

04  /  Composite Key CPK

Two or more columns whose combination is the PK

Neither col alone is unique ✓ Combination is unique ✓ Standard in junction tables

When no single column uniquely identifies a row, two (or more) columns together can form the primary key. This is the correct and expected pattern for junction / bridge tables that resolve M:N relationships.

studentID ← CPK part 1 courseID ← CPK part 2 enrollDate grade
1001CS1012024-02-01A
1001MA2012024-02-01B+
1002CS1012024-02-03A−
1003CS1012024-02-03B

↑ studentID 1001 appears 2× and courseID CS101 appears 3× — neither is unique alone. But (1001, CS101) only appears once.

-- Composite PK: (studentID, courseID) together CREATE TABLE enrollment ( studentID INT NOT NULL, courseID CHAR(6) NOT NULL, enrollDate DATE, grade VARCHAR(3), PRIMARY KEY (studentID, courseID), -- composite FOREIGN KEY (studentID) REFERENCES student(studentID), FOREIGN KEY (courseID) REFERENCES course(courseID) );
💡
Don't add a surrogate key to a junction table unless you have a specific reason (e.g. you need to reference enrollment rows from a third table). The composite PK is the correct, natural design.

05  /  Surrogate Key vs. Natural Key SK vs NK

System-generated stability versus real-world meaning

Surrogate Key (SK) — preferred

A meaningless, system-generated identifier. The database creates it — the real world never sees it or cares about it. Auto-increment integers and UUIDs are the most common forms.

instructorID ← SK (PK) name email department
301Dr. Yuenyuen@uni.eduCompSci
302Prof. Ibarraibarra@uni.eduMaths
303Dr. Nilssonnilsson@uni.eduPhysics
-- Surrogate PK: auto-increment integer instructorID INT PRIMARY KEY AUTO_INCREMENT -- Or UUID (distributed systems) instructorID CHAR(36) PRIMARY KEY DEFAULT (UUID())
✓ Stable — never changes even if the row's data changes
✓ Short — integers are fast to index and join on
✓ No business logic — decoupled from the domain
⚠ No human meaning — debugging requires a JOIN to read
Natural Key (NK) — use with caution

An identifier that exists in the real world. Meaningful to humans and domain experts. Safe only when the value is guaranteed to be stable, unique, and will never be reused or reassigned.

ISBN ← NK (PK) title author year
978-0-13-468599-1Clean CodeMartin2008
978-0-13-235088-4The Pragmatic…Hunt1999
978-0-596-51774-8JavaScript: TDGFlanagan2011
-- Natural PK: ISBN is globally unique & stable CREATE TABLE book ( isbn CHAR(17) PRIMARY KEY, title VARCHAR(200) NOT NULL, author VARCHAR(100), year SMALLINT );
✓ Human-readable — JOIN-free debugging
✓ Meaningful in exports, APIs, and logs
✗ Real-world values sometimes change (email, username, phone)
✗ Long strings make FK joins slower and FK columns bloated
⚖️
Decision rule: Use a natural key as PK only when it is externally standardised (ISBN, IATA airport code, ISO country code), guaranteed globally unique, and will provably never change or be reused. For every other case — people, orders, accounts, products — use a surrogate key and apply UNIQUE + NOT NULL to the business identifier separately.

06  /  Super Key & Partial Key

The theoretical foundations

Super Key Any set of columns that uniquely identifies a row

A super key can contain "extra" unnecessary columns. Every candidate key is a super key but most super keys are not candidate keys — they include redundant columns.

Super Key combinationIs it a Candidate Key?Why / Why not
{studentID}✓ YesMinimal — nothing removable, still unique
{email}✓ YesMinimal — still uniquely identifies the row
{studentID, email}✗ NoCan remove email — still unique. Not minimal.
{studentID, firstName}✗ NoCan remove firstName — still unique. Not minimal.
{studentID, email, lastName}✗ NoMultiple redundant columns — definitely not minimal.
📐
Candidate Key = Minimal Super Key. A super key is a candidate key only if removing any column from it makes it no longer unique.
Partial Key Only meaningful alongside a parent entity's PK

Partial keys exist only on weak entities — entities that cannot be uniquely identified without their owning parent. The partial key + the parent's PK together form the full identifier.

orderID (from ORDER — owner) lineNum ← Partial Key productID qty
ORD-5001PRD-882
ORD-5002PRD-911
ORD-5011PRD-453
ORD-5012PRD-881

lineNum 1 appears twice — not unique alone. But (ORD-500, 1) is unique. lineNum is the partial key; the full PK is (orderID, lineNum).

07  /  Key Hierarchy & Relationships

How all key types relate to each other

🔑
The containment rule: Super Key ⊃ Candidate Key ⊃ Primary Key. Every PK is automatically a candidate key and a super key. The reverse is not true — not every super key is a candidate key, and only one candidate key becomes the PK.

09  /  Practical Rules — What to Use When

Always do Every table gets a PK. If no natural stable unique key exists, create a surrogate. Apply NOT NULL to every column that must have a value. Add UNIQUE constraints to all business identifiers (email, username, code).
Junction tables Always use a composite PK (FK₁ + FK₂). Don't add a surrogate key to a junction unless you need to reference its rows from a third table. Add ON DELETE CASCADE if child rows have no meaning without the parent.
Never do Never use email, phone, or username as a PK — they change. Never leave a candidate key without a UNIQUE constraint. Never use a composite PK of more than 3 columns — if you need more, you likely have a modelling error.
FK actions Choose ON DELETE RESTRICT (default — safest) for most FKs. Use ON DELETE CASCADE only for "child owns nothing without parent" (e.g. order items). Use ON DELETE SET NULL for optional relationships (nullable FK columns).
Indexes PKs are automatically indexed. FK columns are not — always add an index on FK columns manually or queries joining across them will do full table scans. AK columns get an index automatically via UNIQUE constraint.
Int vs UUID INT AUTO_INCREMENT PKs are faster to join and smaller on disk. UUID PKs are better for distributed systems (no central sequence). UUID v7 (time-ordered) avoids index fragmentation. Never use UUID v4 as a clustered PK at scale.
