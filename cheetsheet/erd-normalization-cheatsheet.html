01  /  The Three Phases of ERD Design

Every well-designed schema passes through three distinct modelling stages. Skipping straight to physical design is the single most common cause of structural debt and costly schema migrations.

01
Conceptual Model
High-level map of the business domain. Identifies entities and relationships only — no data types, no PKs, no implementation detail. Built with domain experts, not DBAs.
Audience: Stakeholders
→
02
Logical Model
Adds Crow's Foot cardinality, primary keys, foreign keys, and attributes. DBMS-independent. Normalises to at least 3NF. Resolves all M:N relationships into junction tables.
Audience: Architects / DBAs
→
03
Physical Model
DBMS-specific: chooses data types (VARCHAR(255), BIGINT), indexes, partitioning, storage engines. May intentionally denormalise for performance. Produces actual DDL CREATE TABLE statements.
Audience: DBAs / Engineers
Common mistake: Teams jump directly from whiteboard sketches to CREATE TABLE statements. The conceptual stage is not optional — it surfaces disagreements about the domain before any code is written.

02  /  Entity vs. Attribute vs. Relationship

One of the hardest modelling decisions: should this concept be its own entity, an attribute of another entity, or just a relationship?

Make it an… When… Example
Entity It has its own attributes, has relationships to multiple other entities, or can exist independently ADDRESS — has street, city, postcode
Attribute It is a simple, single-valued property that belongs solely to one entity and has no life of its own email on CUSTOMER
Relationship It describes a meaningful association between two entities — especially if it carries payload attributes ENROLMENT between Student & Course
Weak Entity Its existence depends entirely on a parent entity — it cannot be uniquely identified without its owner's PK ORDER_ITEM needs orderID to exist
Address trap: Storing address as flat columns (street, city, zip) on CUSTOMER works until a Customer has multiple addresses. Model ADDRESS as a separate entity early — migration is painful later.

03  /  Functional Dependencies

A functional dependency A → B means: knowing the value of A always determines the value of B. Understanding FDs is the foundation of all normalization.

Full FD
{A,B} → C
C depends on the entire composite key {A,B}, not just part of it. This is what you want — required for 2NF.
Partial FD
A → C (in {A,B})
C depends only on part of the composite key. This is a 2NF violation. Move C to a table keyed by A alone.
Transitive FD
A → B → C
C depends on B, which depends on A (the PK). C doesn't depend on A directly. This is a 3NF violation. Move B→C to its own table.
Multivalued FD
A →→ B
A determines a set of B values independently of other attributes. This is a 4NF violation — separate into independent tables.
Trivial FD
{A,B} → A
Every set of attributes determines any subset of itself. Always true, never a violation — just not useful for design decisions.

Normalization is the process of structuring a relational database to reduce data redundancy and improve data integrity. Each normal form eliminates a specific class of anomaly. Red = violation · Green = fixed.

1NF
First Normal Form
Rule: Atomic values only · No repeating groups · Each row uniquely identifiable · Single-valued columns

BCNF
Boyce-Codd Normal Form
Rule: Must be in 3NF · For every functional dependency X → Y, X must be a superkey (stricter than 3NF — catches overlapping candidate keys)
Eliminates: non-superkey deps
✗ Violates BCNF

AlicePhysicsDr. Lee

teacher → subject (each teacher teaches one subject), but teacher is not a superkey. 3NF is satisfied but BCNF is violated.

Dr. SmithMaths

Decompose: TEACHER_SUBJECT(teacher, subject) + ENROLMENT(student, teacher). Each determinant is now a superkey.

Practical target: For OLTP systems (apps that read/write frequently), aim for 3NF minimum. Achieve BCNF where overlapping candidate keys exist. 4NF and 5NF are rarely needed in practice — focus on eliminating multi-valued dependencies if you encounter them.

05  /  The Three Database Anomalies — Why Normalization Matters

Anomalies are the symptoms of poor normalization — they occur when data is unnecessarily duplicated across rows. All three arise from the same root cause: storing facts about multiple subjects in a single table.

Insertion Anomaly

You cannot insert a new fact without also inserting unrelated data. Example: can't add a new Department unless at least one Employee exists in it, because department info lives in the EMPLOYEE table.

Update Anomaly

Changing a single fact requires updating multiple rows. Example: if "Engineering" renames to "Software Engineering," you must update every single employee row — miss one and the data is inconsistent.

Deletion Anomaly

Deleting one fact unintentionally destroys another. Example: deleting the last employee in a department also deletes all knowledge of that department's existence from the database.

The fix for all three: Each table should store facts about one subject only. If your EMPLOYEE table stores facts about Departments (deptName, deptBudget), you have two subjects in one table. Separate them — and all three anomalies disappear.

06  /  When to Denormalize

Denormalization is the intentional introduction of redundancy to improve read performance. It is a deliberate trade-off — never a shortcut.

✓ Aggregate caching Store a pre-computed totalOrders count on CUSTOMER to avoid expensive COUNT(*) queries on large ORDER tables at read time.
✓ Reporting flat tables OLAP data warehouses (star/snowflake schemas) intentionally denormalise dimensions for fast analytical queries — normalisation hinders columnar scan performance.
✓ Snapshot / audit rows Store the product price at time of purchase on ORDER_ITEM even though PRODUCT has a price column — preserving historical state is correct design, not denormalization.
✓ Lookup columns Duplicating a frequently-read, rarely-changed value (e.g. customerEmail on ORDER) to avoid a JOIN in hot-path queries is acceptable when the JOIN is measurably slow.
✗ Never: for laziness Don't denormalise because joins feel complex. Premature denormalization creates update anomalies and bugs before you've measured any performance problem.
✗ Never: without documentation Every denormalized column must be documented with why it's redundant, what it duplicates, and how it stays in sync (trigger, application logic, scheduled job).

07  /  SQL Constraints Quick Reference

Constraints are the physical enforcement of your logical model. Every rule modelled in the ERD should have a corresponding constraint in DDL.

PRIMARY KEY
Uniquely identifies each row. Implies NOT NULL + UNIQUE. Only one per table.
id INT PRIMARY KEY
FOREIGN KEY
References PK of another table. Enforces referential integrity. Optional: ON DELETE / ON UPDATE actions.
REFERENCES orders(id)
NOT NULL
Column must always have a value. Maps to mandatory participation (|) in the ERD.
email VARCHAR NOT NULL
UNIQUE
All values in column must be distinct. Use for alternate keys (email, username, slug).
UNIQUE (email)
CHECK
Validates that a value meets a logical condition before insert or update.
CHECK (qty > 0)
DEFAULT
Provides a fallback value when no value is supplied on insert.
DEFAULT CURRENT_TIMESTAMP
ON DELETE CASCADE
Automatically deletes child rows when the parent row is deleted. Use with care — can trigger mass deletion.
ON DELETE CASCADE
ON DELETE SET NULL
Sets FK column to NULL when parent is deleted. Maps to optional participation (○) in the ERD.
ON DELETE SET NULL
ON DELETE RESTRICT
Prevents deletion of parent row if child rows exist. The safest default for most FK relationships.
ON DELETE RESTRICT

08  /  ERD Design Smells — Common Mistakes & Their Fixes

A "design smell" is a structural pattern that signals poor modelling — even if the schema technically works today, it will cause pain at scale or during change.

Generic "type" column A single table with a type or category column that causes many columns to be NULL depending on the type (e.g. ASSET with type = "vehicle" | "software").
Use table-per-type inheritance or a polymorphic junction. Move type-specific columns to sub-type tables.
Multi-valued column Storing comma-separated lists, JSON arrays, or pipe-delimited values in a single column (e.g. tags = "red,sale,new"). Destroys indexability and referential integrity.
Create a separate ENTITY_TAG junction table. Each value gets its own row — 1NF compliance.
God table A single table with 50+ columns storing data about multiple real-world concepts. Often named ITEM, RECORD, or THING. Impossible to normalise, index effectively, or understand.
Identify distinct subjects within the table. Decompose into focused entities, each representing one concept.
Unresolved M:N A direct many-to-many relationship left in the logical model without a junction table. Cannot be implemented in any RDBMS directly without data duplication.
Always insert a junction/bridge table. Its composite PK = FK₁ + FK₂. Add payload attributes as needed.
Mutable natural key as PK Using email, username, phone, or SSN as a primary key. When the value changes, all FK references must be updated — cascading across the entire schema.
Use a surrogate key (AUTO_INCREMENT or UUID) as PK. Apply UNIQUE + NOT NULL to the business identifier.
Status as boolean flag Using isActive, isDeleted, isPaid columns. Boolean flags can't represent history and rapidly multiply (3 flags = 8 states, many invalid).
Use an ENUM status column or a separate STATUS_LOG table for auditable state transitions with timestamps.
Missing timestamps No createdAt or updatedAt columns. Impossible to audit changes, debug data issues, or implement incremental ETL pipelines without row-level timestamps.
Add createdAt DATETIME DEFAULT NOW() and updatedAt DATETIME ON UPDATE NOW() to every table.
Flat address storage Storing address as plain columns (street, city, zip) directly on an entity. Breaks as soon as one entity needs multiple addresses (billing vs. shipping vs. registered).
Create an ADDRESS entity with its own PK. Link with a 1:N or M:N relationship depending on business rules.
