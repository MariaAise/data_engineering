Selection criteria — how to evaluate any architecture

These are the benchmarks that determine fit. Every architecture option should be scored against these:

1. Data integration complexity

How many source systems? How different are they? Acme's answer: very high. Multiple ERPs, different DB vendors, acquisition-inherited systems. This is the hardest problem.

2. Time-to-value

How quickly can you deliver the pilot data mart? Vishal has a July 2015 deadline to present to VP Retail. Fast iteration > architectural purity at this stage.

3. Scalability

Can the architecture grow from one data mart (sales) to 11 business processes without rebuilding? Acme will expand — the architecture must not be a dead end.

4. Team capability

What skills does the team have? Acme's team knows relational databases and SQL. They don't know Spark, Python, or ML engineering. Platform must meet them where they are.

5. Total cost of ownership

Capital expense (hardware) vs operational expense (cloud subscription). Acme is a Rs 3,300Cr company — has budget, but needs to justify ROI to VP Retail.

6. Data governance

Who owns each dimension? How are data quality issues resolved? With 150 stores submitting data, governance is a survival requirement, not a nice-to-have.

Architecture options — the current landscape

Exhibit 6 from the case shows five architectures from the 2014 textbook era. Here's how those map to today's actual options, plus what's new:

Option A: On-premises data warehouse (traditional)

What it is

Physical servers running a relational database (Oracle, SQL Server, Teradata) in Acme's own data centre. ETL tools (Informatica, SSIS) extract from source systems, transform, and load into a star schema warehouse. BI tools (Tableau, Power BI) sit on top.

ProsCons
Full control over data — no sovereignty concernsLarge upfront capital expense: servers, storage, licenses, networking
Predictable cost once purchasedSizing must be done upfront — over-provision = wasted money, under-provision = performance bottleneck
No dependency on internet connectivityScaling requires purchasing more hardware — weeks to months lead time
Familiar to teams with traditional database skillsRequires DBA staff for maintenance, patching, backups, disaster recovery
Holiday season spikes (Diwali) can't be handled elastically — you either pay for peak capacity year-round or suffer during peaks
Acme fit assessment

Poor fit for 2025. Acme's IT is already fragmented — adding on-premises infrastructure adds operational burden to a team that already lacks DW expertise. The sizing problem (constraint 1c from the assessment) becomes critical: Acme would need to estimate hardware needs for 3-5 years upfront without any historical DW usage data to base it on. The cost and risk of getting this wrong is high.

Option B: Cloud data warehouse

What it is

A fully managed warehouse service in the cloud. No hardware to buy, no servers to maintain. Separation of storage and compute — scale each independently. Pay for what you use. The dominant model for new warehouse builds in 2025.

Three major platforms for Acme to evaluate:

Snowflake

Cloud-native warehouse. Separation of storage and compute. Near-zero admin. Multi-cloud (AWS, Azure, GCP). Strong for structured analytics and BI. SQL-first — fits Acme's team skills. Available in AWS Mumbai region.

Why it fits Acme: Simplest to adopt for a SQL-skilled team. Excellent for the dimensional modeling + OLAP workload Acme needs. Can start small (one warehouse) and scale as marts are added.

Google BigQuery

Serverless — no infrastructure at all. Pay per query (bytes scanned). Zero cluster management. Built-in ML (BigQuery ML). GCP Mumbai region available.

Why it fits Acme: Lowest operational overhead. No warehouses to size or manage. But: less ecosystem maturity in India compared to AWS/Azure. GCP adoption is lower in Indian enterprise.

Azure Synapse / Fabric

Microsoft unified analytics. Integrates with Power BI, Azure Data Factory, OneLake. Medallion architecture built-in. Azure Central India region available.

Why it fits Acme: If Acme's existing ERP systems include any SAP or Microsoft products (common in Indian retail), Azure integration is seamless. Power BI is likely the cheapest BI tool for enterprise rollout.

Option C: Data lakehouse

What it is

A unified platform that combines data lake storage (cheap, flexible, handles all data types) with warehouse-grade reliability (ACID transactions, schema enforcement, SQL performance). Data is stored in open formats (Delta Lake, Apache Iceberg) on cloud object storage. One copy of data serves both BI analytics and advanced ML workloads.

Databricks — the lakehouse pioneer

Built on Apache Spark + Delta Lake. Strongest ML/AI integration. Unity Catalog for governance. Medallion architecture (Bronze → Silver → Gold) is the recommended data organization pattern. Available on AWS/Azure/GCP in India regions.

Why it might fit Acme: If Acme plans to build forecasting models (the 30-40% deviation problem from Q2), recommendation engines, or customer segmentation ML models, Databricks provides both the warehouse and the ML platform in one. The medallion architecture gives a clean structure for handling Acme's heterogeneous source data.

Why it might not fit: Requires more technical skill than Snowflake. The team needs Python/Spark capability, not just SQL. Overkill if the primary need is star schema BI — which it is for the pilot.

Option D: Hybrid architecture

What it is

Combine cloud warehouse for structured BI with a lakehouse or document store for advanced analytics. For example: Snowflake for the star schema data marts + Databricks for ML forecasting models, or Snowflake + MongoDB for semi-structured customer profile data (Q6 from the assessment). Many large retailers use both platforms.

ProsCons
Best tool for each job — BI in a warehouse, ML in a lakehouseMore complex to manage — two platforms, two skill sets, two cost models
Can start with warehouse only, add lakehouse later as needs matureData synchronization between platforms adds ETL complexity
No single vendor lock-inHigher total cost — paying for two platforms

Cloud-based architecture — pros and cons (assessment requirement)

Pros for Acme

Eliminates the sizing problem — Q1c asks about hardware estimation. Cloud makes this question irrelevant: start small, scale on demand. No upfront capacity planning needed.

Elastic for seasonal peaks — Acme's electronics retail has massive Diwali/Navratri spikes. Cloud compute can scale up in minutes for festival periods, scale down to near-zero cost in quiet months.

Faster pilot delivery — Vishal can spin up a Snowflake account today and have the sales data mart loaded within days. No procurement, no hardware setup, no DBA hiring. Directly addresses the 6-month pilot deadline.

Managed governance — built-in encryption, access control, audit logging. Acme doesn't need to build these from scratch.

No DBA overhead — the platform handles backups, patching, performance tuning, disaster recovery. Acme's team can focus on building data marts, not managing infrastructure.

India cloud regions available — AWS Mumbai, Azure Central India, GCP Mumbai all operational. Data stays in-country.

Cons for Acme

Ongoing operational cost — no "buy once" model. Monthly cloud bills must be budgeted and monitored. 150 stores uploading data continuously = non-trivial ingestion cost.

Data sovereignty — even with Indian cloud regions, data is managed by a foreign cloud provider (AWS/Google/Microsoft). May face regulatory or board-level resistance. Some Indian sectors have data localization requirements.

Vendor lock-in — migrating from Snowflake to BigQuery (or vice versa) is a major project. The SQL dialects differ, ETL pipelines need rewriting, governance policies need remapping. Choose carefully because switching is expensive.

Internet dependency — 150 stores need reliable connectivity to upload POS data to the cloud. If a store's internet goes down, data ingestion stops. Need fallback: local staging → batch upload.

Cost unpredictability — usage-based billing means costs can spike if a poorly written query scans the entire fact table, or if someone leaves a compute warehouse running over a weekend. Requires cost monitoring discipline.

Training investment — team must learn the cloud platform. While SQL skills transfer, cloud-specific concepts (virtual warehouses, credits, partitioning, clustering) require training.

Recommendation for Acme

Recommended architecture: Cloud data warehouse (Snowflake or Azure Synapse) with phased data mart rollout

Why:

1. Team skill match — Acme's team knows SQL and relational databases. Snowflake and Azure Synapse are SQL-native. No Python/Spark skill gap to bridge for the pilot.

2. Time-to-value — Vishal has 6 months to deliver a pilot. Cloud warehouse can have the sales data mart running in weeks, not months. No hardware procurement cycle.

3. Eliminates sizing risk — The assessment asks about hardware estimation. Cloud makes this a non-issue: start with a small compute tier, scale as data grows. No risk of over-provisioning.

4. Supports phased expansion — Start with retail sales data mart (Kimball bottom-up approach). Add inventory, warehouse operations, promotions as separate marts with conformed dimensions. The Business Matrix (Exhibit 3) becomes the roadmap — one row per phase.

5. Seasonal elasticity — Acme's Diwali period likely generates 3-5x normal transaction volume. Cloud handles this without over-provisioning year-round.

6. India region available — data stays in-country, addresses sovereignty concerns.

Growth path: add Databricks later for ML

When Acme is ready to tackle the forecasting problem (30-40% deviation in Q2) and customer segmentation for loyalty programs (Q3), they can add Databricks alongside the cloud warehouse. The warehouse handles BI; Databricks handles ML. This is the hybrid path — and it's what many large retailers actually do in practice. Don't try to solve everything with one platform on day one.

Implementation phasing

Phase 1 (Months 1-3): Pilot — Retail Product Sales data mart. Star schema with dim_date, dim_product, dim_store, dim_customer, dim_promotion, dim_salesperson + fact_sales. Load data from 5-10 stores. Prove the OLAP queries from the case's analytic requirements work.

Phase 2 (Months 4-6): Expand — add remaining 140+ stores. Add Retail Inventory data mart (second row of Business Matrix). Deploy BI dashboards to regional managers.

Phase 3 (Months 7-12): Warehouse Operations data mart — fact_order_fulfillment for the shipment delay problem. Retail Promotions data mart for campaign effectiveness.

Phase 4 (Year 2): Add ML capability (Databricks or BigQuery ML) for demand forecasting, customer segmentation, recommendation engine. This addresses Q2.1 and Q3 at a deeper level.
