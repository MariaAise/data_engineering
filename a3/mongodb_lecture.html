Introduction to MongoDB

Document databases for business intelligence. For learners who already know relational databases and graph databases — this lecture bridges you to the third paradigm.

1 The problem MongoDB solves

You already know that relational databases store data in tables with fixed columns, and graph databases store data as nodes connected by relationships. Both assume you know the shape of your data in advance.

But what happens when you don't?

The electronics retailer problem

An electronics retailer sells 12,000 products across 9 categories. A laptop has RAM, CPU, screen size, battery life, and weight. A refrigerator has capacity in litres, energy rating, number of doors, and compressor type. A camera has megapixels, sensor size, and lens mount. A washing machine has drum capacity, spin speed, and water efficiency.

In a relational table, you have three options — none of them good:

Relational approachWhat you doWhy it hurts
One wide tableCreate a PRODUCTS table with columns for every possible attribute across all categories: ram_gb, capacity_litres, megapixels, drum_capacity, spin_speed...Hundreds of columns, most NULL for any given row. A laptop row has NULL for capacity_litres, energy_rating, drum_capacity. Wastes storage, confuses queries, and breaks when a new category arrives.
Table per categoryCreate LAPTOPS, REFRIGERATORS, CAMERAS, etc. — each with category-specific columns.Queries across categories require UNION ALL of 9 tables. Adding a new category means a new table + new application code. Cross-category reporting is painful.
Entity-Attribute-Value (EAV)Three columns: product_id, attribute_name, attribute_value. One row per attribute per product.Querying "all laptops with RAM >= 16GB and price < 60000" requires self-joins and type casting from strings. Performance degrades. Universally regarded as an antipattern.
MongoDB's answer

Each product is a document — a self-contained JSON-like object. A laptop document has ram_gb and cpu fields. A refrigerator document has capacity_litres and energy_rating fields. They live in the same collection. No NULLs, no UNION ALLs, no EAV. The database doesn't require all documents to have the same structure.

Side-by-side: relational vs document

Relational (MySQL)
CREATE TABLE products (
  product_id INT PRIMARY KEY,
  name       VARCHAR(100),
  category   VARCHAR(30),
  brand      VARCHAR(30),
  price      DECIMAL(10,2),
  -- laptop-specific
  ram_gb     INT,          -- NULL for non-laptops
  cpu        VARCHAR(50),  -- NULL for non-laptops
  -- fridge-specific
  capacity_l INT,          -- NULL for non-fridges
  energy_rat VARCHAR(10),  -- NULL for non-fridges
  -- camera-specific
  megapixels INT,          -- NULL for non-cameras
  -- ... 50+ more columns
);

-- Query: find 16GB+ laptops under 60K
SELECT * FROM products
WHERE category = 'Computers'
  AND ram_gb >= 16
  AND price < 60000;
vs
Document (MongoDB)
// Laptop document
{
  "name": "Lenovo ThinkPad T14",
  "category": "Computers",
  "brand": "Lenovo",
  "price": 58000,
  "specs": {
    "ram_gb": 16,
    "cpu": "Intel i7",
    "screen": 14
  }
}
// Fridge document — different fields, same collection
{
  "name": "Samsung 253L",
  "category": "Home Appliances",
  "brand": "Samsung",
  "price": 26000,
  "specs": {
    "capacity_litres": 253,
    "energy_rating": "5 star",
    "doors": 2
  }
}

// Query: find 16GB+ laptops under 60K
db.products.find({
  "category": "Computers",
  "specs.ram_gb": { $gte: 16 },
  "price": { $lt: 60000 }
})

The MongoDB query reaches inside the nested specs object using dot notation (specs.ram_gb). No JOINs, no NULL filtering, no type casting. The query reads almost like English.

2 The document model

A MongoDB document is a BSON (Binary JSON) object. It looks like JSON but supports additional types (dates, ObjectIds, decimal128). Every document has a unique _id field — like a primary key, but auto-generated if you don't provide one.

What a document can contain

Simple values

Strings, numbers, booleans, dates, null. Same types you know from SQL columns.

"name": "Priya Sharma",
"age": 28,
"active": true,
"joined": ISODate("2023-03-15")
Nested documents

A document inside a document. Like a joined table embedded directly. Accessed with dot notation: address.city

"address": {
  "street": "100 MG Road",
  "city": "Bangalore",
  "state": "Karnataka"
}
Arrays

Ordered lists of values — including arrays of nested documents. Like a one-to-many relationship, but without a second table.

"tags": ["premium", "new"],
"reviews": [
  { "rating": 4, "text": "Good" },
  { "rating": 5, "text": "Great" }
]

The schema difference is the key concept

In MySQL, you run CREATE TABLE to define columns before inserting any data. Every row must conform. In MongoDB, you just start inserting documents. The first document creates the collection implicitly. The next document can have completely different fields. This is called schema-on-read — the application interprets the structure when reading, rather than the database enforcing it on write.

This doesn't mean "no structure." In practice, most documents in a collection share a common structure. But the flexibility to vary — different specs per product category, different questions per survey, different profile fields per customer type — is the core advantage.

Embedded vs referenced — the fundamental design decision

In relational databases, you normalise: separate tables joined by foreign keys. In MongoDB, you have a choice:

Embed (denormalise)

Put the related data inside the parent document.

// Customer with embedded address and orders
{
  "name": "Priya Sharma",
  "address": { "city": "Bangalore" },
  "recent_orders": [
    { "date": "2024-12-18", "total": 24000 },
    { "date": "2024-11-05", "total": 65000 }
  ]
}

Use when: the related data is always read together, doesn't grow unboundedly, and is owned by the parent (address belongs to one customer).

Advantage: one read returns everything. No joins.

Reference (normalise)

Store related data in a separate collection and link with IDs — like a foreign key.

// Customer — stores only a reference
{ "name": "Priya Sharma", "city": "Bangalore" }

// Orders — separate collection
{
  "customer_id": "C10042",
  "date": "2024-12-18",
  "items": ["SKU1039", "SKU1044"],
  "total": 89000
}

Use when: the related data is large, shared across documents, updated independently, or grows without limit (thousands of orders per customer).

Trade-off: requires $lookup (MongoDB's equivalent of JOIN) at query time.

Rule of thumb

"Data that is accessed together should be stored together." If the application always needs a customer's profile + address + loyalty status in the same API call, embed them in one document. If orders are only loaded on a separate "order history" screen, keep them in a separate collection and reference.

3 CRUD operations

MongoDB's operations map directly to what you know from SQL, with one important difference: you work with JSON-like documents instead of rows and columns.

OperationSQLMongoDB
Insert INSERT INTO products VALUES (...) db.products.insertOne({ name: "...", price: 58000 })
Read SELECT * FROM products WHERE price > 50000 db.products.find({ price: { $gt: 50000 } })
Update UPDATE products SET price = 55000 WHERE _id = 'SKU1001' db.products.updateOne({ _id: "SKU1001" }, { $set: { price: 55000 } })
Delete DELETE FROM products WHERE _id = 'SKU1001' db.products.deleteOne({ _id: "SKU1001" })

// Complete example: find premium Samsung products with high ratings
db.products.find({
  "brand": "Samsung",
  "price": { $gte: 30000 },
  "avg_rating": { $gte: 4.0 },
  "category": { $in: ["TVs", "Mobile Phones", "Computers"] }
}).sort({ "price": -1 }).limit(10)

The .sort() and .limit() methods chain onto the query — like SQL's ORDER BY and LIMIT.

The aggregation pipeline — MongoDB's analytical engine

For anything beyond simple find queries — grouping, calculating totals, reshaping data — MongoDB uses the aggregation pipeline. Data flows through a sequence of stages, each transforming the documents before passing them to the next stage.

Think of it as a conveyor belt

Documents enter on one end. Each stage does one transformation: filter, group, reshape, sort, join. The output of one stage is the input of the next. The final stage produces the result.

StageSQL equivalentWhat it does
$matchWHEREFilter documents matching a condition. Put this early — it reduces the number of documents downstream.
$groupGROUP BYGroup documents by one or more fields. Apply accumulators: $sum, $avg, $count, $min, $max, $push.
$projectSELECTInclude/exclude fields. Rename. Compute new fields.
$sortORDER BYSort documents. 1 = ascending, -1 = descending.
$limitLIMITReturn only the first N documents.
$unwind(no direct equivalent)Deconstruct an array into individual documents. One input document with a 3-element array → three output documents.
$lookupJOINLeft outer join with another collection. Use when data is referenced, not embedded.
$addFieldsComputed columnAdd new fields calculated from existing fields.
// Pipeline: average product price by category, sorted highest first
db.products.aggregate([
  { $group: {
      "_id": "$category",                    // GROUP BY category
      "avg_price": { $avg: "$price" },       // AVG(price)
      "product_count": { $sum: 1 },          // COUNT(*)
      "max_price": { $max: "$price" }        // MAX(price)
  }},
  { $sort: { "avg_price": -1 } },           // ORDER BY avg_price DESC
  { $project: {                               // SELECT (reshape output)
      "category": "$_id",
      "avg_price": { $round: ["$avg_price", 0] },
      "product_count": 1,
      "max_price": 1,
      "_id": 0
  }}
])

The equivalent SQL would be: SELECT category, ROUND(AVG(price), 0), COUNT(*), MAX(price) FROM products GROUP BY category ORDER BY AVG(price) DESC. The pipeline syntax is more verbose, but it handles nested and variable-schema data that SQL cannot.

4 Three-way routing — relational vs graph vs document

You now know three database paradigms. The skill is knowing which to apply to which problem:

Question typeBest paradigmExample
"What is the total/average/count of X grouped by Y?"Relational (star schema)Total revenue by category by quarter. Average basket size by customer segment. Promotion ROI.
"How are A and B connected? What's the path between them?"Graph (Neo4j)Trace a damaged product through the supply chain. Find products co-purchased with item X.
"Show me all entities matching these variable attributes."Document (MongoDB)Find all laptops with 16GB RAM under Rs 60K. Retrieve a customer's full profile with embedded preferences.

When MongoDB is the right choice

Variable schema across records

Products with different attributes per category. Surveys that change format over time. Customer profiles with different fields per segment. If you'd need hundreds of nullable columns in SQL — use MongoDB.

Data that's always read together

A customer's profile, preferences, loyalty status, and recent activity — all needed in one API call. Embedding in a document eliminates the 5-table JOIN that relational requires.

Rapidly evolving data model

New fields added weekly as the application evolves. In relational: every change is an ALTER TABLE migration. In MongoDB: new documents simply include the new fields. Old documents still work.

High-volume writes

Event logs, clickstream, IoT sensors — millions of writes per second. MongoDB's sharding distributes writes across multiple servers. Relational databases hit single-server bottlenecks.

When MongoDB is NOT the right choice

Aggregation across millions of rows

"Total revenue by category by quarter across 150 stores." Star schemas on columnar storage (Snowflake, BigQuery) are 10-100x faster for SUM/COUNT/AVG on large datasets. Don't put your fact table in MongoDB.

OLAP operations

ROLLUP, CUBE, GROUPING SETS, window functions — these are SQL specialities that MongoDB's aggregation pipeline doesn't match in performance or expressiveness.

Multi-collection JOINs as the primary pattern

MongoDB's $lookup exists but is not optimised for the 5-dimension star schema join. If every query joins 5 collections, you're fighting the data model.

Relationship traversal

"Trace this product through 5 levels of the supply chain." This is a graph problem. MongoDB can do $graphLookup for simple recursive traversals, but Neo4j is purpose-built for path queries and graph algorithms.

The key insight

MongoDB, Neo4j, and a relational data warehouse are complementary — not competing. An enterprise may use all three: the warehouse for OLAP dashboards, Neo4j for supply chain analysis, and MongoDB for the product catalog and customer profiles. They share source data through ETL pipelines. Each serves the queries it handles best.

Just as Neo4j AuraDB is Neo4j's cloud service, MongoDB Atlas is MongoDB's fully managed cloud platform. It runs on AWS, Azure, or Google Cloud in 125+ regions worldwide.

Free tier (M0)

Dedicated clusters

Production workloads. Choose instance size, region, cloud provider. Auto-scaling available. Enterprise security and compliance (SOC 2, HIPAA, PCI DSS).

Notice: the specs object has completely different fields in each document. A laptop has ram_gb and cpu. A refrigerator has capacity_litres and energy_rating. Headphones have noise_cancellation and bluetooth. All coexist in the same collection.

Practice queries

// 1. All products rated 4.5 or above, sorted by price
db.products.find(
  { "avg_rating": { $gte: 4.5 } }
).sort({ "price": 1 })

// 2. All Samsung products available in store 7
db.products.find({
  "brand": "Samsung",
  "stores": 7    // MongoDB automatically matches if 7 is IN the array
})

// 3. All products with noise cancellation (field only exists on audio products)
db.products.find({
  "specs.noise_cancellation": true
})

Query 3 demonstrates a key advantage: specs.noise_cancellation only exists on audio products. In SQL, you'd need to handle the NULL column or use EAV. In MongoDB, you just query the field — documents without it are simply not matched.

Aggregation pipeline walkthrough

Task: "Show the number of products and average price per category, but only for categories where the average price exceeds Rs 25,000."

SQL equivalent: SELECT category, COUNT(*), AVG(price) FROM products GROUP BY category HAVING AVG(price) > 25000 ORDER BY AVG(price) DESC

db.products.aggregate([

  // Stage 1: Group by category, calculate aggregates
  { $group: {
      "_id": "$category",
      "product_count": { $sum: 1 },
      "avg_price": { $avg: "$price" },
      "brands": { $addToSet: "$brand" }  // collect unique brands per category
  }},

  // Stage 2: Filter groups (SQL's HAVING clause)
  { $match: {
      "avg_price": { $gt: 25000 }
  }},

  // Stage 3: Sort by average price, descending
  { $sort: { "avg_price": -1 } },

  // Stage 4: Reshape output for readability
  { $project: {
      "category": "$_id",
      "product_count": 1,
      "avg_price": { $round: ["$avg_price", 0] },
      "brands": 1,
      "_id": 0
  }}

])

This returns something like:

// Output
[
  { "category": "Computers",       "product_count": 1, "avg_price": 72000, "brands": ["Lenovo"] },
  { "category": "Home Appliances", "product_count": 1, "avg_price": 26000, "brands": ["Samsung"] }
]

The $addToSet accumulator is a bonus — it collects unique brand names per category into an array. This has no SQL equivalent without a subquery. It's a natural operation in MongoDB because arrays are first-class values.
