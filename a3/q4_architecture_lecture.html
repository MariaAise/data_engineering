Data Warehouse Architecture

Current landscape, platform comparison, and where it's all heading. Lecture format — 1 hour.

1 Core tensions every architecture balances ~8 min

The fundamental job of a data warehouse architecture hasn't changed: bridge the gap between systems optimized for recording transactions and systems optimized for answering questions. What changed is the scale, the data types, and the tools available. Every architecture makes trade-offs across three tensions:

Flexibility vs governance

Can you add new data sources without breaking existing reports? Can you enforce quality without slowing ingestion? Lean too far toward flexibility → data swamp. Too far toward governance → bottleneck.

Cost vs performance

Pre-aggregate data for fast reads (costs storage, stale data) or query raw data on-demand (slower, always fresh)? Pay for always-on compute or burst on demand?

Simplicity vs capability

SQL-only teams need a warehouse. ML/AI teams need Python/Spark. One platform that does both is complex. Two platforms create integration overhead.

A 150-store electronics retailer wants to analyze promotion effectiveness across all stores. The operational databases use different ERP vendors across regions. The architecture must integrate heterogeneous sources (flexibility), ensure "revenue" means the same thing everywhere (governance), handle Diwali traffic spikes without paying for peak capacity year-round (cost vs performance), and serve both marketing dashboards (SQL) and demand forecasting models (ML) — ideally without maintaining two separate platforms (simplicity vs capability).

ETL vs ELT — the pipeline shift

ETL — Extract, Transform, Load

Transform happens on a separate server before loading into the warehouse. Traditional approach — necessary when warehouse compute was expensive and limited. Tools: Informatica, SSIS, Talend, Ab Initio.

When it still makes sense: heavily regulated industries where data must be cleansed/masked before it touches the warehouse; legacy environments with limited warehouse compute.

ELT — Extract, Load, Transform

Load raw data first, transform inside the warehouse using its own scalable compute. The dominant modern pattern — made possible by cheap, elastic cloud warehouse compute.

Why it won: the warehouse is now the most powerful compute engine in the stack. Transforming data there is faster, cheaper, and keeps lineage in one system. dbt (data build tool) is the standard transformation tool in ELT workflows.

getdbt.com

The medallion architecture — ELT's organizing pattern

Data flows through three progressive refinement layers: Bronze (raw, as-received, append-only — the replay source), Silver (cleaned, conformed, deduplicated — data quality enforcement happens here), Gold (business-ready aggregations and star schemas — what analysts and BI tools query). Kimball's dimensional modeling lives in the Gold layer. This pattern is now the default for both lakehouse (Databricks, Fabric) and warehouse (Snowflake, BigQuery) architectures.

2A Cloud data warehouse ~10 min

What it is

A fully managed SQL engine in the cloud with separated storage and compute. No hardware to buy. Scale each layer independently. Pay for what you use. The dominant model for new warehouse builds.

CharacteristicDetail
Core mechanicELT — load raw data, transform inside the warehouse (dbt, stored procedures, SQL pipelines)
Data modelStar schema / snowflake schema in the Gold layer. Staging tables in Bronze/Silver.
Data typesStructured (tables) + semi-structured (JSON, Avro, Parquet). Limited for unstructured (images, video, audio).
Query languageSQL (primary). Python/Java extensions available but SQL is the center of gravity.
Who it's forOrganizations whose primary need is BI, reporting, and SQL-based analytics. SQL-skilled teams.
PlatformsSnowflake, Google BigQuery, Amazon Redshift, Azure Synapse

A retail chain with 150 stores needs cross-store sales analysis, promotion effectiveness dashboards, and quarterly executive reporting. Their team knows SQL and uses Power BI. A cloud data warehouse (Snowflake or BigQuery) is the natural fit — fast to set up, SQL-native, handles the star schema + OLAP workload perfectly. No Spark or Python expertise required.

What it handles well

Concurrent dashboard queries from hundreds of users, OLAP operations (roll-up, drill-down, slice, dice), governed access control, semi-structured data (JSON columns), and increasingly — basic ML via SQL extensions (BigQuery ML, Snowflake Cortex).

What it doesn't handle well

Unstructured data at scale (images, video, sensor logs), large-scale ML model training (need GPUs), real-time streaming (sub-second latency), and very large raw data volumes where storage cost matters (warehouse storage is 3-5x more expensive than object storage).

2B Data lakehouse ~10 min

What it is

Data lake storage (S3/ADLS/GCS) + open table format (Delta Lake / Iceberg / Hudi) + SQL engine + ML engine — unified on one platform. Warehouse-grade reliability on lake economics.

The enabling technology: open table formats

Before 2020, data lakes couldn't do ACID transactions, schema enforcement, or time travel. Open table formats solved this by tracking metadata about files rather than relying on directory structures:

FormatOriginPhilosophyReference
Delta LakeDatabricks (2019)Spark-native, transaction log tracks file-level changesdelta.io
Apache IcebergNetflix → Apache (2018)Vendor-neutral, snapshot-based metadata. Increasingly the default open standard.iceberg.apache.org
Apache HudiUber → Apache (2016)Optimized for streaming updates and upserts/deletes. Strong for CDC workloads.hudi.apache.org

All three provide ACID transactions, time travel (query historical snapshots), schema evolution, and partition pruning — on files stored in cheap cloud object storage.

The same retailer now wants to build demand forecasting models to fix 30-40% forecast deviation. They also have customer survey data (semi-structured), product images for the e-commerce catalog (unstructured), and want real-time inventory visibility across stores. A lakehouse (Databricks) handles all of this: star schemas in the Gold layer for BI, Spark ML for forecasting, streaming ingestion for inventory — one platform, one governance layer.

Trade-off vs cloud warehouse

More capability, more complexity. The team needs Python/Spark skills, not just SQL. Setup and optimization require engineering expertise. If the primary need is dashboards and OLAP — a pure warehouse is simpler and faster to deliver value.

2C Hybrid architecture ~5 min

What it is

Best tool for each job. Star schema BI in a warehouse, ML in a lakehouse, semi-structured data in a document store, graph relationships in Neo4j. Shared data layer via open formats (Iceberg) or ETL pipelines feeding multiple targets.

Many large retailers use both Snowflake (for BI) and Databricks (for ML). Open table formats are making this less painful — Snowflake, Databricks, Spark, Trino, and Dremio can all read the same Iceberg tables without duplicating data.

The data mesh organizational layer

Hybrid architectures at scale often adopt a data mesh pattern: domain teams (sales, warehouse operations, marketing) own their data products end-to-end, publishing to a central marketplace with governance standards. Each domain picks the tools that fit their workload — but conformed dimensions and shared governance ensure consistency. Relevant for multi-region, multi-department organizations.

2D Real-time / streaming-first ~5 min

What it is

Event streaming platform (Kafka) feeding a real-time OLAP engine (ClickHouse, Druid, Pinot) that queries data seconds after ingestion. For use cases where hours-old data is too stale.

ComponentProductRoleReference
Event streamingApache Kafka / ConfluentIngest millions of events/second, deliver to consumers in real timekafka.apache.org
Real-time OLAPClickHouseColumn-oriented, sub-second queries on billions of rowsclickhouse.com
Real-time OLAPApache DruidReal-time ingestion + fast aggregation, strong for time-seriesdruid.apache.org
Real-time OLAPApache PinotLinkedIn-origin, optimized for user-facing analytics at scalepinot.apache.org

The retailer wants real-time fraud detection on payment transactions across 150 stores + e-commerce. Every transaction streams through Kafka, gets scored by a fraud model in milliseconds, and suspicious transactions are flagged before the customer leaves the store. A batch warehouse running nightly ETL cannot serve this use case.

When NOT to use: If the business question can wait 15 minutes for an answer, a cloud warehouse with frequent micro-batch loading is simpler and cheaper. Streaming architecture requires specialist Kafka/ClickHouse engineers.

Google BigQuery — serverless analytics

Core architecture

Fully serverless — no clusters to manage, no warehouses to size. Pay per query (bytes scanned) or flat-rate reservations. Columnar storage (Capacitor format). Dremel execution engine. Separate from compute.

Microsoft Fabric — unified analytics

Core architecture

Microsoft's all-in-one analytics platform. Unifies Power BI, Synapse Data Engineering, Data Factory, Data Science, and Real-Time Intelligence under a single SaaS product. OneLake as the single storage layer (built on ADLS Gen2). Medallion architecture built into the product.

microsoft.com/microsoft-fabric

Key differentiators

Direct Lake mode: Power BI queries Parquet/Delta files in OneLake directly — no import step, no data duplication. Combines the speed of imported data with the freshness of DirectQuery.

Copilot integration: Natural language analytics in Power BI, Data Factory, and notebooks. AI-assisted report building, DAX formula generation, pipeline creation.

Best for: Organizations already in the Microsoft ecosystem (Office 365, Azure AD, Teams). Power BI is the most deployed BI tool globally — Fabric makes it the consumption layer of a unified analytics platform.

Amazon Redshift — AWS-native warehouse

Core architecture

Columnar storage, massively parallel processing (MPP). Tight integration with the AWS ecosystem: S3, Glue, SageMaker, Athena, Kinesis. Redshift Serverless available for pay-per-query model.

aws.amazon.com/redshift

Key developments

Zero-ETL: Automatic replication from Aurora (PostgreSQL/MySQL), DynamoDB, and other AWS services directly into Redshift — no pipeline to build. Data available for analytics seconds after operational write.

Redshift Spectrum: Query data in S3 directly without loading into Redshift. Extends the warehouse into a lakehouse pattern.

Best for: AWS-native organizations. Strongest when combined with the broader AWS data stack (Glue for ETL, SageMaker for ML, Athena for ad-hoc S3 queries).

→ The convergence ~3 min

Every platform is adding the others' features

Snowflake adds Iceberg support, Python execution (Snowpark), ML (Cortex), and operational data. Databricks adds BI-grade SQL performance, semantic layer (Metric Views), and an operational database (Lakebase). BigQuery adds continuous queries, ML, and vector search. Fabric unifies warehouse + lakehouse + BI in one product.

The architectural category (warehouse vs lakehouse) matters less each year. What matters: which platform fits your team's skills, existing ecosystem, and primary workload mix.

Cloud architecture — pros & cons ~5 min

Pros

Eliminates hardware sizing — start small, scale on demand. No upfront capacity planning.

Elastic for seasonal peaks — spin up compute for Diwali, scale down to near-zero in quiet months. Pay only for what you use.

Managed infrastructure — no DBA staff for patching, backups, disaster recovery, performance tuning.

Fast time-to-value — spin up a warehouse and load data in hours, not months of procurement.

Built-in governance — encryption, access control, audit logging, lineage out of the box.

Global availability — data stays in-country with regional deployments (India, EU, US, APAC regions available).

Cons

Ongoing operational cost — no "buy once" model. Monthly bills must be monitored. Usage spikes can surprise.

Vendor lock-in — migrating between platforms is expensive. SQL dialects differ, pipelines need rewriting. Open formats (Iceberg) mitigate this but don't eliminate it.

Data sovereignty concerns — data managed by foreign cloud provider, even in local regions. May face regulatory or board-level resistance in some industries/countries.

Internet dependency — stores/offices need reliable connectivity. If connectivity fails, data ingestion stops. Requires fallback: local staging → batch upload.

Cost unpredictability — poorly written queries scanning entire fact tables, or compute left running over weekends, create surprise bills. Requires cost monitoring discipline.

Training investment — team must learn cloud platform. Cloud-specific concepts (virtual warehouses, credits, partitioning) require upskilling.

5 The semantic layer — where OLAP is heading ~7 min

The problem (unchanged since the 1990s)

Sales says revenue is $18M. Finance says $17.2M. Both numbers are "correct" — different filters, different date logic, different currency handling. This inconsistency erodes trust in data.

The old solution: OLAP cubes

Pre-aggregated, pre-defined multidimensional structures (SSAS, Cognos, Hyperion). Baked metric logic into the cube. Solved consistency but created rigidity — new dimensions required rebuilding the cube. Vendor-locked (MDX query language). Being phased out.

The modern solution: semantic layer

Define metrics once, in code, serve them to every consuming tool (BI dashboards, notebooks, AI agents, APIs). Three architectural approaches emerged between 2020-2025:

ApproachProductHow it worksBest forReference
Transformation-layerdbt Semantic Layer / MetricFlowMetrics-as-code in YAML, version-controlled in Git, compiled to optimized SQL at query timeMulti-cloud, vendor-neutral environments. Teams already using dbt.dbt semantic layer
Warehouse-nativeSnowflake Semantic Views, Databricks Metric ViewsMetric definitions stored as database objects in the warehouse/catalog itselfSingle-platform environments. Tightest integration.Databricks Metric Views
OLAP-accelerationCube.devPre-aggregation layer with REST/GraphQL API. Caches results for sub-second latency.Embedded analytics, customer-facing dashboards. High concurrency.cube.dev
Why AI is the killer use case for the semantic layer

LLMs querying a semantic layer produce dramatically more accurate results than LLMs querying raw tables. The semantic layer provides the business context — what "revenue" means, which filters to apply, how dimensions join — that models need to generate correct SQL. Accuracy increases up to 300% with a semantic layer vs raw table access. The semantic layer is becoming AI infrastructure, not just BI infrastructure.

Open Semantic Interchange (OSI)

Launched 2025 by dbt Labs, Snowflake, and Salesforce. Goal: standardize metric definitions in vendor-neutral YAML so metrics are portable across tools. Define a metric once, consume it in Looker, Tableau, Power BI, notebooks, and AI agents. Still early but signals industry convergence.

6 What comes next ~5 min

AI-native data platforms

Architectures designed primarily for AI workloads (model training, RAG, embeddings, agent workflows) with traditional analytics as secondary. Databricks is furthest along — Lakebase + Mosaic AI + Unity Catalog makes it an AI development platform that also does BI, not the other way around.

Real-time convergence

The batch/streaming distinction dissolving. Delta Live Tables, Kafka-to-Iceberg pipelines, BigQuery continuous queries, Snowflake Snowpipe Streaming — the architecture handles both in one pipeline. "Batch is just a special case of streaming with a very long window."

Automated governance via AI

Data catalogs that auto-classify PII, auto-detect schema drift, auto-suggest access policies. Unity Catalog already auto-classifies sensitive data within 24 hours. Snowflake AI_REDACT detects and masks PII automatically. Manual governance doesn't scale to petabytes.

Edge analytics

Process data at the point of capture (store POS, factory sensor, IoT device) before sending to the cloud. Gartner predicts 55%+ of deep neural network analysis will occur at the edge by 2025. Relevant for retailers: if internet fails, edge processing keeps local analytics running.

Composable data stack

Instead of one monolithic platform, assemble best-of-breed tools: Fivetran/Airbyte for ingestion, dbt for transformation, Snowflake/Databricks for warehouse, Looker/Power BI for BI, Monte Carlo/Soda for data quality. Connected via APIs and open formats. The "anti-lock-in" movement.

fivetran.com · airbyte.com · montecarlodata.com

Natural language as the query interface

Snowflake Cortex Analyst, Databricks Genie, BigQuery Gemini — all converting English questions into SQL. The BI tool becomes optional for simple queries. Business users ask questions directly, the semantic layer ensures correctness. The "last mile" of data democratization.

→ Next problems — once the warehouse is running

The warehouse/lakehouse is live, the star schema is serving dashboards, the initial analytical requirements are met. What breaks next?

Problem 1: Forecast accuracy

Descriptive analytics (what happened) is solved. Now the business wants predictive analytics (what will happen). Demand forecasting, inventory optimization, customer churn prediction. The star schema provides the training data — but you need ML models. This is where BigQuery ML (SQL-based, lowest friction) or Databricks (full ML platform) enters the stack.

Problem 2: Real-time inventory visibility

Batch ETL means inventory data is hours old. Store managers need to know current stock across all 150 stores — not yesterday's snapshot. This pushes toward streaming ingestion (Kafka/Snowpipe/Kinesis) and near-real-time dashboard refresh. The architecture evolves from nightly batch to micro-batch (every 5-15 minutes) to streaming.

Problem 3: Personalization at scale

The loyalty program is live, customer segments are defined (RFM). Now marketing wants personalized recommendations — "customers who bought X also bought Y" — served in real-time on the e-commerce site. This requires a recommendation engine (collaborative filtering / embeddings), a feature store (serving customer features at low latency), and an operational database (Lakebase / DynamoDB) to serve recommendations to the application layer.

Problem 4: Unstructured data

Customer survey free text, product reviews, social media mentions, call center transcripts. These don't fit in a star schema. The lakehouse handles them natively — store in Bronze, process with LLMs (sentiment analysis, entity extraction), land structured outputs in Gold alongside the star schema. Snowflake Cortex AI functions (AI_CLASSIFY, AI_EMBED) can process unstructured data directly in SQL queries.

Problem 5: Governance at scale

With 150 stores, dozens of data domains, multiple teams, and ML models making decisions — who owns what? How do you audit which model made which recommendation? Column-level lineage, model governance, metric consistency, automated PII detection — this is where Unity Catalog and Snowflake Horizon earn their value. Governance is not a "later" problem — it's the problem that determines whether anyone trusts the numbers.
