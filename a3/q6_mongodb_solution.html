Q6 — MongoDB Document Database Solution

When to use a document database, how it complements both the data warehouse and the graph database, and what it solves for a multi-store electronics retailer.

Document model — concept refresher

A document database stores data as documents — self-contained JSON-like objects (BSON in MongoDB). Documents are grouped into collections (analogous to tables). Unlike relational databases, documents in the same collection can have different structures — no fixed schema is enforced.

Document

A JSON-like object with key-value pairs. Values can be strings, numbers, arrays, or nested documents. Example: a product document can embed its specifications, reviews, and images as nested objects — all in one document.

Collection

A group of documents. Unlike a relational table, documents in a collection don't need the same fields. A products collection can hold a laptop document with ram and cpu fields alongside a refrigerator document with capacity_litres and energy_rating.

Aggregation pipeline

MongoDB's analytical query engine. A sequence of stages ($match, $group, $project, $unwind, $lookup) that process documents through a pipeline. Analogous to SQL's SELECT/WHERE/GROUP BY but operating on nested document structures.

Embedded vs referenced — the key design decision

Embed (denormalize)

Put related data inside the document. A customer document embeds their address, preferences, and recent purchase summary. Best when: the related data is always read together, the embedded data doesn't grow unboundedly, and updates to embedded data are infrequent.

Reference (normalize)

Store related data in separate collections and link with IDs. An order document references a customer_id rather than embedding the full customer. Best when: the related data is large, shared across documents, or updated independently. Use $lookup to join at query time.

When document vs relational — the fundamental distinction

Use a document database when

The data structure varies across records of the same type. Different products have different attributes. Different survey responses have different questions. Different customer profiles have different fields.

You need to embed related data that's always read together — a customer with their entire profile, preferences, and activity history in one read.

The schema evolves frequently — new fields added to new documents without migrating existing data. Critical for agile development.

High write throughput — MongoDB's horizontal sharding handles millions of writes/second (event logs, clickstream, IoT sensor data).

Use relational / star schema when

The primary need is aggregation across millions of rows — SUM, COUNT, AVG, ROLLUP, CUBE. Columnar storage in warehouses (Snowflake, BigQuery) is 10-100x faster than MongoDB for these operations.

The data has a fixed, stable schema — all rows have the same columns. Star schemas with fact and dimension tables.

Multi-collection joins are the primary query pattern. MongoDB's $lookup exists but is not optimized for the 5-table star schema join pattern. SQL is purpose-built for this.

Decision framework — document vs relational vs graph

The assessment covers three database paradigms: relational (Q1-Q4), graph (Q5), and document (Q6). This framework determines which paradigm fits each problem:

What is the primary analytical need?
Aggregation (SUM, COUNT, AVG across millions of rows, ROLLUP/CUBE, time-series trends) → Relational / Star Schema
Traversal (follow connections, find paths, network patterns, impact analysis) → Graph (Neo4j)
Flexible storage & retrieval (variable-schema data, embedded nested objects, high-volume writes) → Document (MongoDB)
Does the data have a fixed, consistent schema across all records?
YES → Relational. Fixed columns, well-defined types. Star schema works perfectly.
NO — the schema varies per record → MongoDB. Different products have different attributes. Different surveys have different questions.
N/A — graph doesn't care about schema consistency per se, but about relationships between entities.
Are the relationships between entities the primary subject of analysis?
YES → Graph (Neo4j). Supply chain traversal, co-purchase networks, impact analysis.
NO — the entities themselves (and their attributes) are the primary subject → MongoDB or Relational, depending on schema variability.
Do you need to embed related data that's always read together?
YES → MongoDB. A customer document with embedded profile, preferences, and activity log. One read returns everything. In relational, this requires multiple JOINs.
NO — the data is naturally tabular and joins are well-defined → Relational. Star schema for analytics.
Graph embeds properties on nodes and relationships but doesn't nest documents. If you need deep nesting, MongoDB is the choice.
Is write volume extremely high (millions of events/second)?
YES → MongoDB (sharded clusters) or a dedicated event store (Kafka). Relational databases struggle with this write volume. Graph databases are optimized for read-heavy traversal, not high-throughput writes.
NO → write volume doesn't drive the database choice. Focus on query patterns instead.
Why not graph for document problems?

Graphs model relationships between entities. Documents model the entities themselves with rich, variable attributes. A customer profile with 50+ demographic and psychographic fields is a document problem — the richness of the entity's attributes matters, not its connections to other entities. Putting 50 properties on a Neo4j node technically works but is an antipattern: graph databases are optimized for traversal performance, not for storing and querying rich attribute sets. MongoDB's indexing, text search, and aggregation pipeline are purpose-built for querying attributes within documents.

Similarly, a product catalog where you need to search "all laptops with RAM >= 16GB and screen >= 14 inches and price < 50000" is a filtered attribute query, not a graph traversal. MongoDB handles this natively with compound indexes. In Neo4j, you'd need to filter properties on nodes — possible but inefficient compared to MongoDB's optimized document scanning.

Rule of thumb: If the question starts with "find entities where [attribute conditions]" → document/relational. If the question starts with "find what's connected to X through Y" → graph.

Acme's document-suitable problems

1. Product catalog (strongest fit)

12,000 SKUs across 9 categories. A laptop has RAM, CPU, screen size. A refrigerator has capacity, energy rating, door count. A camera has megapixels, sensor size, lens mount. In relational: one massive table with hundreds of sparse columns (mostly NULL), or an EAV pattern (painful to query). In MongoDB: each product has whatever fields are relevant to its category. A laptop and a refrigerator have completely different specs fields — and that's fine.

Enables rich product search and filtering on the e-commerce portal without EAV hell.

2. Customer profiles

Exhibit 2 shows CUSTOMER_PROFILE with "demographic profile, psychographic profile." This is semi-structured by definition. A corporate buyer has company, industry, procurement contact. A retail customer has age, family size, interests. A student has institution, course.

Directly enables the loyalty program (Q3) and customer targeting — rich profiles power personalized promotions.

3. Customer surveys

The case mentions "periodic customer survey reports." Survey formats change over time — new questions added, old ones removed. Different stores may run different surveys. In relational: every format change requires schema migration. In MongoDB: each survey response is a document with whatever questions were asked. Old and new formats coexist.

4. Activity / event log

POS transactions, customer queries, product returns, complaint records, warranty claims. Each event type has different attributes. MongoDB's flexible schema handles mixed event types in one collection. Useful for Customer 360 — unified activity history per customer.

5. E-commerce clickstream

Acme has an online portal (300 cities). Clickstream data: page views, searches, cart additions, abandonments. High-volume, semi-structured, schema-variable. Too granular and volatile for a star schema. MongoDB (or data lake) is the natural landing zone. Feeds recommendation and personalization models.

Problems that are NOT document-shaped at Acme

Total revenue by category by quarter → aggregation → star schema / warehouse
Promotion ROI across all stores → arithmetic on measures across millions of rows → warehouse
Supply chain traceability → traversal of connected entities → graph (Q5)
Co-purchase recommendations → network traversal → graph (Q5)
OLAP operations (slice/dice/rollup) → star schema with columnar storage
Don't force these into MongoDB. The right tool for each job.

Aggregation pipeline queries

// Customer segmentation from profiles — group by loyalty tier and psychographic
db.customer_profiles.aggregate([
  { $match: { "loyalty.member": true } },
  { $group: {
      "_id": {
        "tier": "$loyalty.tier",
        "tech_savviness": "$psychographic.tech_savviness"
      },
      "count": { $sum: 1 },
      "avg_monetary": { $avg: "$rfm.monetary" },
      "avg_frequency": { $avg: "$rfm.frequency" }
  }},
  { $sort: { "avg_monetary": -1 } }
])
// Product search — all laptops with RAM >= 16GB, price < 60000, in stock at Bangalore stores
db.products.find({
  "category": "Computers",
  "subcategory": "Laptop",
  "specs.ram_gb": { $gte: 16 },
  "price": { $lt: 60000 },
  "stores_stocking": { $in: [6, 7, 22] }  // Bangalore store keys
})
// Survey sentiment analysis — average NPS by store, only 2024+ surveys
db.surveys.aggregate([
  { $match: { "responses.nps_score": { $exists: true } } },
  { $group: {
      "_id": "$store_id",
      "avg_nps": { $avg: "$responses.nps_score" },
      "survey_count": { $sum: 1 },
      "promoters": { $sum: { $cond: [{ $gte: ["$responses.nps_score", 9] }, 1, 0] } },
      "detractors": { $sum: { $cond: [{ $lte: ["$responses.nps_score", 6] }, 1, 0] } }
  }},
  { $sort: { "avg_nps": -1 } }
])
// Customer activity log — find customers who browsed but didn't purchase in last 30 days
db.customer_profiles.aggregate([
  { $match: { "loyalty.member": true } },
  { $project: {
      "name": 1,
      "loyalty.tier": 1,
      "recent_browses": {
        $filter: {
          "input": "$recent_activity",
          "as": "a",
          "cond": { $and: [
            { $eq: ["$$a.type", "browse"] },
            { $gte: ["$$a.date", "2024-12-01"] }
          ]}
        }
      },
      "recent_purchases": {
        $filter: {
          "input": "$recent_activity",
          "as": "a",
          "cond": { $and: [
            { $eq: ["$$a.type", "purchase"] },
            { $gte: ["$$a.date", "2024-12-01"] }
          ]}
        }
      }
  }},
  { $match: {
      "recent_browses.0": { $exists: true },
      "recent_purchases.0": { $exists: false }
  }}

Three databases, three purposes

The complete Acme solution uses all three paradigms — each handling what it does best. They share source data through ETL pipelines or direct connections.

Data flow between systems

MongoDB → Warehouse: MongoDB aggregation pipeline produces structured summaries (e.g., average NPS per store per month) → loaded into the warehouse as a dimension or fact for OLAP analysis alongside sales data.

Warehouse → MongoDB: RFM scores calculated in the warehouse (SQL window functions on fact_sales) → written back into customer profile documents in MongoDB as the rfm embedded object. The e-commerce app reads from MongoDB to personalize the experience.

MongoDB → Neo4j: Customer purchase events from MongoDB → loaded as relationships in the co-purchase graph. Product catalog from MongoDB → loaded as Product nodes with category/brand relationships.

Future developments — general

Vector search & AI-native databases

MongoDB Atlas Vector Search eliminates the need for a separate vector database. Store embeddings alongside operational data. Power RAG, semantic search, and AI agents from the same database. With the Voyage AI acquisition, MongoDB can generate embeddings natively — no external API needed. 74% of organizations plan to use integrated vector databases for agentic AI workflows.

Atlas Vector Search

Serverless & auto-scaling

Atlas Serverless instances scale from zero to peak automatically. No capacity planning. Pay per operation. Ideal for variable-traffic applications like e-commerce — Diwali traffic spike handled automatically, costs drop to near-zero during quiet periods.

Real-time with Change Streams

Change Streams notify applications in real-time when documents change. Enables reactive architectures: new survey inserted → trigger sentiment analysis → update customer profile → trigger personalized promotion. Event-driven without polling.

Time-series collections

Purpose-built for IoT, metrics, and event data. Efficient compression, windowed aggregation, automated expiration (TTL). Relevant for Acme's store sensor data, POS event streams, and equipment monitoring in warehouses.

Multi-model convergence

MongoDB increasingly handles multiple paradigms: document storage + search + vector search + time-series + streaming. Azure Cosmos DB offers document + graph + column-family in one service. The trend: fewer specialized databases, more multi-model platforms.

Edge to cloud sync

MongoDB Atlas Device Sync (formerly Realm) synchronizes data between edge devices (store POS, mobile apps) and cloud. Relevant for Acme's 150 stores: local MongoDB on store servers syncs to Atlas when connected. Offline-capable — works even if internet fails.

The document model stores the conversation history, customer preferences, and product context in one place.

The key message for the assessment

MongoDB is complementary to both the data warehouse and the graph database. It solves specific problems — variable-schema storage, rich entity profiles, high-volume event ingestion, AI/vector search — that relational star schemas handle poorly (due to fixed schema) and graph databases don't address (because they're about relationships, not rich entity attributes). The three-database hybrid architecture (warehouse + graph + document) gives Acme the right tool for each problem type.
