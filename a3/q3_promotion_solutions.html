Acme's promotion problem — from the case

What the case says

"The sales and marketing team at Acme was interested in building a loyalty card program to retain its customers and improve overall profitability. The company also did not have appropriate metrics in place to measure the effectiveness of their promotional campaigns. While the basic sales data is available, it lacks the ability to get an integrated view of the sales across multiple stores, perform slicing and dicing of data, conduct multi-dimensional data analysis and build data mining models for identifying the right customer targets."

Critical design decision: promo_key = 0 means "no promotion". Every transaction gets a promo_key — either a real promotion or the "None" row. This makes baseline vs promoted comparison possible in a single query without complex CASE logic.

Why dim_promotion is the key to Q3

Without a promotion dimension, Acme cannot answer "which promotions worked?" The dim_promotion table with its promo_type (festival / seasonal / clearance / flash / bundle) and media_channel (TV / internet / radio / hoarding / social) attributes enables every promotional analysis the case asks for. This is the single most important design decision for Q3.

OLAP operations on promotional data — SQL demonstrations

-- SLICE: All sales during Diwali Dhamaka promotion only
SELECT p.category, s.city, SUM(f.net_amount) AS revenue
FROM fact_sales f
JOIN dim_promotion pr ON f.promo_key = pr.promo_key
JOIN dim_product p    ON f.product_key = p.product_key
JOIN dim_store s      ON f.store_key = s.store_key
WHERE pr.promo_name = 'Diwali Dhamaka'
GROUP BY p.category, s.city
ORDER BY revenue DESC;
-- DICE: Festival promos + South region + TVs + Q4
SELECT s.city, p.product_name, pr.promo_name,
       SUM(f.quantity) AS units, SUM(f.net_amount) AS revenue
FROM fact_sales f
JOIN dim_date d       ON f.date_key = d.date_key
JOIN dim_product p    ON f.product_key = p.product_key
JOIN dim_store s      ON f.store_key = s.store_key
JOIN dim_promotion pr ON f.promo_key = pr.promo_key
WHERE p.category = 'TVs'
  AND s.region = 'South'
  AND d.quarter = 'Q4'
  AND pr.promo_type = 'Festival'
GROUP BY s.city, p.product_name, pr.promo_name
ORDER BY revenue DESC;
-- ROLL-UP: Promotion effectiveness by promo_type → quarter → year
SELECT
    COALESCE(pr.promo_type, '** ALL TYPES **') AS promo_type,
    COALESCE(d.quarter, '** ALL QUARTERS **') AS quarter,
    SUM(f.net_amount) AS revenue,
    SUM(f.discount_amount) AS total_discount,
    SUM(f.gross_margin) AS margin
FROM fact_sales f
JOIN dim_promotion pr ON f.promo_key = pr.promo_key
JOIN dim_date d       ON f.date_key = d.date_key
WHERE pr.promo_key > 0
GROUP BY pr.promo_type, d.quarter WITH ROLLUP;
-- DRILL-DOWN: From promo_type → individual promotion → specific SKU
SELECT pr.promo_type, pr.promo_name, p.product_name,
       SUM(f.quantity) AS units, SUM(f.net_amount) AS revenue
FROM fact_sales f
JOIN dim_promotion pr ON f.promo_key = pr.promo_key
JOIN dim_product p    ON f.product_key = p.product_key
WHERE pr.promo_type = 'Festival'
GROUP BY pr.promo_type, pr.promo_name, p.product_name
ORDER BY pr.promo_name, revenue DESC;

L3 Promotion effectiveness metrics

The metrics Acme's marketing managers are missing. Each one is a SQL query on the star schema.

Incremental lift
(promo_revenue - baseline_revenue) / baseline_revenue × 100
Did the promotion generate revenue above what would have happened anyway? Baseline = same store, same category, same period prior year (or non-promoted average).
Promotion ROI
(incremental_margin - discount_cost) / discount_cost × 100
For every rupee of discount given, how many rupees of incremental margin were generated? Negative ROI = promotion destroyed value.
Cannibalization rate
Δ same-category non-promoted sales during promotion period
Did the Samsung TV promotion reduce LG TV sales? If total category revenue didn't grow — the promotion just shifted revenue within category.
Halo effect
Δ related-category sales during promotion period
Did the gaming console promotion also lift gaming accessories sales? Cross-category correlation on the same time windows. Positive halo = promotion creates broader value.
Media channel effectiveness
incremental_revenue per channel / spend per channel
Did the TV campaign drive more revenue than social media contests? Requires dim_promotion.media_channel attribute. Answers: where should Acme allocate promotional budget?
Discount depth vs lift curve
Plot: discount_pct (x) vs lift_pct (y) across all promotions
At what discount percentage does incremental lift plateau? A 20% discount might only generate 5% more lift than 15%. Finds the optimal discount depth.

Incremental lift — the SQL

-- Compare promoted vs non-promoted avg daily revenue by category
WITH baseline AS (
    SELECT p.category,
           SUM(f.net_amount) / COUNT(DISTINCT f.date_key) AS avg_daily_rev
    FROM fact_sales f
    JOIN dim_product p    ON f.product_key = p.product_key
    JOIN dim_promotion pr ON f.promo_key = pr.promo_key
    WHERE pr.promo_key = 0  -- non-promoted sales only
    GROUP BY p.category
),
promoted AS (
    SELECT pr.promo_name, p.category,
           SUM(f.net_amount) / COUNT(DISTINCT f.date_key) AS avg_daily_rev,
           SUM(f.discount_amount) AS total_discount
    FROM fact_sales f
    JOIN dim_product p    ON f.product_key = p.product_key
    JOIN dim_promotion pr ON f.promo_key = pr.promo_key
    WHERE pr.promo_key > 0
    GROUP BY pr.promo_name, p.category
)
SELECT promoted.promo_name, promoted.category,
       ROUND(baseline.avg_daily_rev, 0) AS baseline_daily,
       ROUND(promoted.avg_daily_rev, 0) AS promo_daily,
       ROUND((promoted.avg_daily_rev - baseline.avg_daily_rev)
             / baseline.avg_daily_rev * 100, 1) AS lift_pct,
       ROUND(promoted.total_discount, 0) AS discount_given
FROM promoted
JOIN baseline ON promoted.category = baseline.category
ORDER BY lift_pct DESC;

L4 Customer targeting & data mining

This is where Acme moves from descriptive analytics (what happened) to predictive analytics (who to target). Directly addresses "data mining models for identifying the right customer targets."

RFM segmentation

Recency, Frequency, Monetary — the classic customer segmentation

Score every customer 1–5 on three dimensions using their purchase history from fact_sales. Built entirely in SQL — no ML library required.

-- RFM scoring from the star schema
WITH rfm_raw AS (
    SELECT
        c.customer_key,
        c.customer_name,
        c.customer_segment,
        DATEDIFF('2024-12-31', MAX(d.full_date)) AS recency_days,
        COUNT(DISTINCT f.date_key) AS frequency,
        SUM(f.net_amount) AS monetary
    FROM fact_sales f
    JOIN dim_customer c ON f.customer_key = c.customer_key
    JOIN dim_date d     ON f.date_key = d.date_key
    WHERE c.customer_key > 0  -- exclude walk-ins
    GROUP BY c.customer_key, c.customer_name, c.customer_segment
)
SELECT *,
    NTILE(5) OVER (ORDER BY recency_days DESC)  AS r_score,
    NTILE(5) OVER (ORDER BY frequency ASC)      AS f_score,
    NTILE(5) OVER (ORDER BY monetary ASC)       AS m_score
FROM rfm_raw
ORDER BY monetary DESC;

Resulting segments drive targeted promotions:

SegmentRFM profilePromotion strategy
ChampionsR=5, F=5, M=5Reward with exclusive early access. Don't discount — they'll buy anyway. Focus on loyalty tier upgrades.
LoyalR=4-5, F=4-5, M=3-5Upsell and cross-sell. Bundle promotions. Invite to loyalty program if not enrolled.
Potential loyalistsR=4-5, F=2-3, M=2-3Offer membership incentives. Frequency-building promos ("buy 3 get 10% off next").
At riskR=2-3, F=3-5, M=3-5Win-back campaign. Personalized discount on their preferred category. Time-limited urgency.
LostR=1, F=1-2, M=1-2Aggressive reactivation offer or accept churn. Don't over-invest — low ROI on this segment.

Market basket analysis

Association rules for bundle promotions

"Customers who buy laptops also buy laptop bags and extended warranties in the same transaction." The case mentions product bundling as a promotion type — basket analysis identifies which bundles to create.

Implementation: Apriori algorithm via Python mlxtend library reading from fact_sales. Group by transaction (same customer_key + date_key), find frequent itemsets, extract rules with confidence > 0.3 and lift > 1.5.

Alternative: BigQuery ML supports association rules natively. Or implement in SQL using self-joins on the fact table to find co-purchased products.

Customer lifetime value (CLV)

For the loyalty program Acme wants to build

Predict future value of each customer based on historical patterns. Determines loyalty tier assignment: which customers justify Platinum benefits (higher discount, free delivery, exclusive access)?

Simple CLV: avg_purchase_value × purchase_frequency × avg_customer_lifespan — computable in SQL from the star schema.

Probabilistic CLV: BG/NBD model (predicts future transactions) + Gamma-Gamma model (predicts future monetary value). Implemented in Python lifetimes library. More accurate for Acme's mixed walk-in + loyalty customer base.

Churn prediction

Which loyalty members are about to leave?

Train a classifier on historical data: customers who stopped purchasing after being active. Features from the star schema: days since last purchase, purchase frequency trend (declining?), average basket size trend, response rate to promotions (did they buy during promos?). Flag at-risk customers for targeted retention promotions before they're gone.

Implementation: Logistic regression or gradient boosting in Python (scikit-learn / XGBoost) or BigQuery ML. The star schema provides all training features.

Critical point: every commercial platform needs the star schema first

These tools don't replace the data warehouse — they sit on top of it. They need clean, integrated, dimensional data to function. If Acme buys Cognira but hasn't built the star schema, they'll spend 6 months on data integration before the tool does anything useful. Build L1 first, always.

Data flow for a promotion cycle

Plan: Use historical promo effectiveness data (L3) + customer segments (L4) to design next promotion → Execute: Run promotion across selected stores/channels → Capture: POS data flows through ETL into fact_sales with promo_key → Measure: Calculate lift, ROI, cannibalization (L3) → Learn: Feed results back into next cycle's planning. This is the closed-loop promotion optimization cycle that Acme currently cannot do.

Recommendation for Acme — phased implementation

Phase 1: Foundation (Months 1-3) — L1 + L2

Build the star schema with dim_promotion in Snowflake or BigQuery. Connect Power BI. Load historical POS data from pilot stores. Deliver the first dashboards showing cross-store promotion performance. This alone delivers the "integrated view" and "slicing and dicing" the case asks for.

Phase 2: Metrics (Months 3-5) — L3

Implement incremental lift and promo ROI calculations as SQL views in the warehouse. Build a promotion effectiveness dashboard in Power BI. Marketing managers can now measure which promotions work. This is the capability they explicitly said was missing.

Phase 3: Loyalty + targeting (Months 5-8) — L4

Launch loyalty program with tier assignment based on RFM scores calculated from fact_sales. Implement market basket analysis for bundle promotion design. Build churn prediction model. Marketing can now run targeted promotions to specific customer segments instead of blanket discounts.

Phase 4: AI optimization (Year 2) — L5

Evaluate commercial platforms (Cognira, Impact Analytics, Yieldigo) for AI-powered promotion planning. By this point Acme has 12+ months of clean star schema data — the platforms can deliver immediate value because the data foundation exists.
