Q2.1 — Forecasting Accuracy

Forecast estimates deviate 30-40% for some SKUs, causing excess inventory and stockouts. How to diagnose, measure, and fix it.

The problem — stated precisely

From the case

"The forecast estimates were often inaccurate deviating as much as 30-40% for some SKUs. This results in excess inventory in a few cases and stock-outs in many other cases."

30-40% forecast deviation is catastrophic for a retailer. It means:

Excess inventory (overforecast)

Capital tied up in unsold stock. Storage costs in regional warehouses. Markdown risk — products lose value (especially electronics with rapid model cycles). Increases the shrinkage rate (currently 1.2-1.5% of sales — Acme wants to reduce to 0.6%).

Stockouts (underforecast)

Lost sales — customer wanted to buy but the product isn't there. Customer goes to competitor. Particularly damaging during festival periods (Diwali, Navratri) when foot traffic peaks. Erodes brand trust: "Acme never has what I want."

The 74% problem: The case states Acme uses standard EOQ (Economic Order Quantity) models driven by warehouse managers' estimates. EOQ assumes stable, predictable demand — which doesn't hold for a consumer electronics retailer with 12,000 SKUs, seasonal spikes, promotional effects, and product lifecycle variability.

Root cause analysis

The 30-40% deviation isn't one problem — it's multiple problems compounding:

Root causeWhy it happens at AcmeData signal
1. No integrated demand data Each store and warehouse uses different DB products. Warehouse managers forecast based on their regional view, not national patterns. A product trending in Mumbai stores is invisible to the Kolkata warehouse manager. Cross-store sales data not available in one place. The data warehouse solves this directly.
2. Seasonality not modeled Electronics retail has extreme seasonality: Diwali (Oct-Nov) drives 3-5x normal volume. Back-to-school (Jun-Jul) spikes laptops/tablets. Summer spikes ACs and refrigerators. EOQ doesn't capture this. Sales data by month shows seasonal patterns — but only if you have multi-year history in one place.
3. Promotional demand not separated A "Diwali Dhamaka" promotion causes a sales spike. The next month's forecast is inflated because it includes the promotional uplift as if it were organic demand. When no promotion runs, actual sales fall short of forecast. Requires dim_promotion to separate promoted vs baseline sales.
4. Product lifecycle effects New Samsung Galaxy launches → old model demand drops. Forecasts based on historical data for the old model overpredict. New model has no history to forecast from. Product age, lifecycle stage (introduction / growth / maturity / decline) need to be tracked.
5. SKU-level granularity 12,000 SKUs. Forecasting at category level is easy. Forecasting at SKU level (Samsung Galaxy S23 128GB Black vs 256GB Blue) is exponentially harder — sparse data per SKU, high variance. Need sufficient history at SKU level. Some SKUs will always be hard to forecast — the system should flag these.
6. No forecast accuracy measurement "The company was unable to clearly identify the root cause." They can't fix what they can't measure. There's no system comparing forecasted demand vs actual demand to identify which SKUs, stores, or categories have the worst accuracy. Need a fact_forecast_accuracy or comparison table: forecast vs actual, by SKU × store × week.

Data requirements — what needs to be captured

Before building forecasting models, you need the data infrastructure to support them:

Data currently available at Acme

POS transaction data (fact_sales), store inventory counts (fortnightly physical verification), indent records (orders from store to warehouse), shipment records (warehouse to store).

Data that needs to be captured or derived

Inventory snapshots — daily or weekly on-hand quantity per SKU per store. Currently only fortnightly physical counts. Need periodic automated snapshots from the inventory system.

Forecast vs actual — the warehouse manager's forecast for each SKU must be recorded at the time it's made, then compared against actual sales. Without this, forecast accuracy cannot be measured.

Promotional flags — which transactions were promoted vs organic. Without dim_promotion, you can't separate promotional spikes from baseline demand.

External data — festival calendar (Diwali/Navratri dates vary yearly), school term dates (back-to-school timing), new product launch dates (from manufacturers), competitor activity (price matching).

Star schema — Inventory Data Mart

A separate data mart from the sales mart, sharing conformed dimensions:

Fact table: fact_inventory_snapshot

-- Grain: one row per product per store per week
CREATE TABLE fact_inventory_snapshot (
  snapshot_key       INT NOT NULL AUTO_INCREMENT,
  date_key           INT NOT NULL,        -- FK → dim_date (week-ending date)
  store_key          INT NOT NULL,        -- FK → dim_store
  product_key        INT NOT NULL,        -- FK → dim_product
  quantity_on_hand   INT NOT NULL,        -- current stock level
  quantity_on_order  INT NOT NULL DEFAULT 0, -- indented but not yet received
  quantity_received  INT NOT NULL DEFAULT 0, -- received this week from warehouse
  quantity_sold      INT NOT NULL DEFAULT 0, -- sold this week (from fact_sales)
  quantity_shrinkage INT NOT NULL DEFAULT 0, -- losses this week
  stockout_days      TINYINT DEFAULT 0,    -- days with zero stock this week
  reorder_point      INT,                   -- current reorder level for this SKU
  forecasted_demand  INT,                   -- warehouse manager's forecast
  PRIMARY KEY (snapshot_key),
  FOREIGN KEY (date_key) REFERENCES dim_date(date_key),
  FOREIGN KEY (store_key) REFERENCES dim_store(store_key),
  FOREIGN KEY (product_key) REFERENCES dim_product(product_key)
);
Why this is a periodic snapshot fact table (not transactional)

Unlike fact_sales (one row per event), this captures the state of inventory at regular intervals. This enables trend analysis: is on-hand quantity rising or falling? How many weeks of supply remain? What's the trajectory toward stockout? Kimball calls this a "periodic snapshot" fact table — the second most common fact table type after transactional.

Shared conformed dimensions

dim_date, dim_store, dim_product — same tables used by the sales data mart. This is why conformed dimensions matter: the same product_key joins both fact_sales and fact_inventory_snapshot, enabling combined sales + inventory analysis.

Diagnostic queries — measuring the problem

-- Forecast accuracy by product category
SELECT
    p.category,
    COUNT(*) AS observations,
    ROUND(AVG(ABS(i.forecasted_demand - i.quantity_sold)
        / NULLIF(i.quantity_sold, 0) * 100), 1) AS avg_deviation_pct,
    SUM(CASE WHEN i.stockout_days > 0 THEN 1 ELSE 0 END) AS stockout_weeks,
    SUM(CASE WHEN i.quantity_on_hand > i.quantity_sold * 4
        THEN 1 ELSE 0 END) AS excess_inventory_weeks
FROM fact_inventory_snapshot i
JOIN dim_product p ON i.product_key = p.product_key
WHERE i.forecasted_demand IS NOT NULL
GROUP BY p.category
ORDER BY avg_deviation_pct DESC;
-- Worst-forecasted SKUs (the "30-40% deviation" offenders)
SELECT
    p.sku_id, p.product_name, p.category, s.store_name,
    SUM(i.forecasted_demand) AS total_forecast,
    SUM(i.quantity_sold) AS total_actual,
    ROUND((SUM(i.forecasted_demand) - SUM(i.quantity_sold))
        / NULLIF(SUM(i.quantity_sold), 0) * 100, 1) AS bias_pct
FROM fact_inventory_snapshot i
JOIN dim_product p ON i.product_key = p.product_key
JOIN dim_store s   ON i.store_key = s.store_key
GROUP BY p.sku_id, p.product_name, p.category, s.store_name
HAVING ABS(bias_pct) > 30
ORDER BY ABS(bias_pct) DESC;
-- Inventory turns by category (annual)
-- Low turns = excess inventory. High turns = healthy or at risk of stockout.
SELECT
    p.category,
    ROUND(SUM(s.quantity_sold * p.unit_cost)
        / NULLIF(AVG(s.quantity_on_hand * p.unit_cost), 0), 1) AS inventory_turns,
    ROUND(365 / NULLIF(
        SUM(s.quantity_sold * p.unit_cost)
        / NULLIF(AVG(s.quantity_on_hand * p.unit_cost), 0)
    , 0), 0) AS days_of_supply
FROM fact_inventory_snapshot s
JOIN dim_product p ON s.product_key = p.product_key
GROUP BY p.category
ORDER BY inventory_turns DESC;

Current solution methods

Level 1: Statistical baselines (SQL-based — immediate)

Replace warehouse manager gut-feel with data-driven baselines. Implementable immediately on the star schema, no ML required:

Moving average

4-week or 8-week moving average of sales per SKU per store. Smooths noise, captures recent trends. Simple: AVG(quantity_sold) OVER (ORDER BY date_key ROWS 7 PRECEDING). Limitation: lags behind sudden changes.

Same-period-last-year (SPLY)

Use last year's sales for the same week as the forecast baseline. Captures annual seasonality (Diwali, summer). Adjust for growth trend: SPLY × year-over-year growth rate. Limitation: doesn't work for new products with no prior year data.

Promotional adjustment

Calculate a "promotion uplift factor" per promo_type from historical data: avg promoted daily sales / avg baseline daily sales. When planning a future promotion, multiply baseline forecast by the uplift factor. When no promotion is planned, use only the baseline. This directly fixes root cause #3 (promotional demand not separated).

Future scenario

Once the data warehouse is mature (12-24 months of clean data) and the basic forecasting models are working:

Phase 1 → Phase 3 evolution

Phase 1 (immediate): Build the inventory data mart. Measure forecast accuracy for the first time. Identify the worst-performing SKU × store combinations. Replace gut-feel with moving average + SPLY baselines. Promotional adjustment factor applied manually.

Phase 2 (6-12 months): Enough historical data for Prophet/XGBoost models. Train per-category or per-brand models. Automated weekly forecast generation. Forecast accuracy dashboard showing improvement over time. Promotional uplift automatically incorporated as a model feature.

Phase 3 (12-24 months): Deep learning models (TFT) across all 12,000 SKUs. Automated reorder point adjustment based on forecast + safety stock calculation. Demand sensing: incorporate real-time signals — e-commerce browsing data, competitor price changes, weather, social media mentions — to adjust short-term forecasts. The warehouse manager shifts from "forecaster" to "forecast reviewer" — the model does the prediction, the human applies judgment.

What "good" looks like

Industry benchmark for electronics retail: 15-20% MAPE (Mean Absolute Percentage Error) at SKU-store-week level. Acme is currently at 30-40%. Getting to 20% would reduce excess inventory by ~40% and stockout incidents by ~50%. The data warehouse is the prerequisite — without it, none of these methods have the integrated, clean, historical data they need to work.
