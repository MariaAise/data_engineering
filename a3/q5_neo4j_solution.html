Q5 — Neo4j Graph Database Solution

When to use a graph database, how it complements the data warehouse, and what it solves for a multi-store electronics retailer.

Graph database — concept refresher

A graph database stores data as nodes (entities) connected by relationships (edges). Both nodes and relationships can have properties (key-value pairs). Nodes have labels (types). This is the property graph model.

Node

An entity: a store, a product, a customer, a supplier. Has a label (:Store, :Product) and properties ({name: "MG Road", city: "Bangalore"}).

Relationship

A connection between two nodes. Has a type (:PURCHASED, :SHIPPED_TO), a direction (always directed), and properties ({quantity: 2, date: "2024-10-15"}).

Traversal

Following relationships from node to node. The core operation. "Start at Samsung Galaxy S23, follow all PURCHASED relationships, find all Customers, then follow their other PURCHASED relationships to find co-purchased Products." This is a 3-hop traversal — trivial in a graph, expensive in SQL.

Cypher — the query language

// Pattern matching — the core of Cypher
MATCH (c:Customer)-[:PURCHASED]->(p:Product)
WHERE p.category = 'TVs'
RETURN c.name, p.name, p.brand

// Multi-hop traversal — find products co-purchased with a specific item
MATCH (target:Product {name: 'Samsung 55 Crystal 4K'})
      <-[:PURCHASED]-(c:Customer)-[:PURCHASED]->(other:Product)
WHERE other <> target
RETURN other.name, other.category, count(c) AS co_purchases
ORDER BY co_purchases DESC LIMIT 10

// Variable-length path — supply chain trace
MATCH path = (s:Supplier)-[*1..5]->(store:Store {name: 'MG Road'})
RETURN path

When graph vs relational — the fundamental distinction

Use a graph when

The relationships between entities are the primary subject of analysis. You're asking: "how are things connected?", "what's the path between A and B?", "what patterns emerge from the network structure?"

Query depth is variable — you don't know how many joins in advance. In SQL you must specify exact join count; in Cypher, [*1..5] traverses 1-5 hops dynamically.

The schema is flexible — new relationship types and node labels can be added without altering existing data. Good for evolving models.

Use a relational/star schema when

The aggregation of measures is the primary analysis. You're asking: "what is total revenue by category by quarter?", "what's the average order value?" — these are SUM/COUNT/AVG operations across millions of rows.

OLAP operations (roll-up, drill-down, slice, dice) are the workload. Star schemas with columnar storage are optimized for exactly this.

The schema is stable — dimensions and facts don't change structure frequently.

They are complementary, not competing

A graph database does not replace the data warehouse. The warehouse handles aggregation; the graph handles traversal. The same enterprise data can live in both — star schema for OLAP, property graph for relationship analysis. The question is: which Acme problems are aggregation problems (→ warehouse) and which are traversal problems (→ graph)?

Decision framework — is this a graph problem?

Not every problem benefits from a graph database. This decision process identifies which problems are graph-shaped:

Are the relationships between entities the primary subject of the analysis?
YES → Graph is a strong candidate. Continue below.
NO → the primary need is aggregation (SUM, COUNT, AVG across rows) → Star schema / data warehouse. Graph adds no value here.
Does the analysis require traversing connections of variable or unknown depth?
YES → Graph. Examples: "trace a product through the supply chain" (3-6 hops), "find all products connected through shared customers" (2-3 hops), "what's the impact if this supplier fails?" (unbounded depth).
NO → if the join depth is fixed (e.g., always fact → dim, always 1-2 joins), SQL handles it efficiently. No graph needed.
Do you need to discover patterns in the network structure itself?
YES → Graph. Community detection (which stores cluster together by customer overlap?), centrality (which product is most central to the purchase network?), path analysis (shortest supply chain path), similarity (which customers have the most similar purchase networks?).
NO → if the analysis is about the attributes of entities (revenue, quantity, margin) rather than the structure of connections, the warehouse is the right tool.
Is the query performance degrading because of excessive JOINs in SQL?
YES → Graph. If your SQL query has 5+ self-joins on the same table or recursive CTEs to traverse hierarchies, the graph model will be dramatically simpler and faster.
NO → if your queries are performing well with standard star schema joins, there's no performance reason to add a graph layer.
The litmus test

If you catch yourself writing SELECT ... FROM table t1 JOIN table t1 AS t2 ON ... JOIN table t1 AS t3 ON ... — self-joining the same table multiple times to traverse connections — you have a graph problem disguised as a SQL query. The graph model makes the traversal explicit and efficient.

Acme's graph-suitable problems

Applying the decision framework to the case, four problems emerge as genuinely graph-shaped:

1. Supply chain traceability (strongest fit)

The path: Supplier → Warehouse → Shipment → Transporter → Store

The question: "A batch of Samsung TVs arrived damaged at the Bangalore store. Trace back through the chain — which warehouse shipped them? Which transporter handled them? Which supplier provided them? Have other shipments from the same transporter/supplier had similar damage rates?"

Why graph: The chain has variable depth (3-6 nodes depending on intermediate handling). In SQL, this requires 5+ joins across multiple fact tables (fact_order_fulfillment, dim_transporter, dim_warehouse, dim_product, dim_store). In Cypher, it's one path query.

Directly relevant to Q2.2 — damage root cause analysis.

2. Product recommendation network

The pattern: Customer → PURCHASED → Product ← PURCHASED ← Other Customer → PURCHASED → Other Product

The question: "Customers who bought an Apple MacBook Air also bought Apple AirPods Pro, a laptop bag, and AppleCare warranty. Recommend these as a bundle."

Why graph: Market basket analysis via self-joins in SQL is O(n²). In a graph, co-purchase traversal is O(neighbors). Scales to 12,000 SKUs × 100K+ customers without performance degradation.

Directly relevant to Q3 — customer targeting and bundle promotions.

3. Impact analysis

The question: "If Supplier Samsung delays deliveries for 2 weeks, which products across which stores are affected? What's the revenue at risk?"

Why graph: Impact radiates outward from the supplier through warehouse → store → product availability → customer experience. Unbounded traversal from a single starting node.

Directly relevant to warehouse management and business continuity planning.

4. Customer 360 / entity resolution

The problem: Acme grew through acquisitions. Same customer may exist in multiple store databases with different IDs, slightly different names, different addresses. The graph can link: (Customer A)-[:SAME_AS]->(Customer B) based on shared phone number, email, or address.

Why graph: Entity resolution is a matching/linking problem — fundamentally graph-shaped. Critical for the loyalty program (Q3) — you can't measure customer lifetime value if one customer appears as three separate records.

Problems that are NOT graph-shaped at Acme

Total revenue by category by quarter → aggregation → warehouse.
Promotion ROI calculation → arithmetic on measures → warehouse.
Forecast accuracy measurement → comparison of predicted vs actual values → warehouse.
Inventory turns → ratio of aggregated measures → warehouse.
Don't force these into a graph. The star schema handles them better.

Graph data model for Acme

// Node labels and their key properties

(:Store       {store_id, name, city, state, region, floor_area})
(:Warehouse   {warehouse_id, name, city, state, region, capacity})
(:Product     {sku_id, name, brand, category, subcategory, unit_price})
(:Customer    {customer_id, name, city, segment, loyalty_tier})
(:Supplier    {supplier_id, name, location, lead_time_days})
(:Transporter {transporter_id, name, service_type, sla_hrs})
(:Brand       {brand_name, country_of_origin})
(:Category    {category_name})
(:Shipment    {shipment_id, ship_date, delivery_date, status})

// Relationship types

(Customer)-[:PURCHASED   {date, quantity, amount}]->(Product)
(Store)-[:RECEIVED       {date, quantity}]->(Shipment)
(Shipment)-[:CONTAINS    {quantity}]->(Product)
(Shipment)-[:SHIPPED_FROM]->(Warehouse)
(Shipment)-[:TRANSPORTED_BY {cost, transit_hrs}]->(Transporter)
(Warehouse)-[:STOCKS     {quantity_on_hand}]->(Product)
(Supplier)-[:SUPPLIES    {lead_time, cost}]->(Product)
(Product)-[:BELONGS_TO]->(Category)
(Product)-[:MANUFACTURED_BY]->(Brand)
(Brand)-[:SUPPLIED_BY]->(Supplier)
(Store)-[:LOCATED_IN]->(City)        // geographic hierarchy as graph
(Warehouse)-[:SERVES]->(Store)       // which warehouse serves which stores

Hybrid architecture — warehouse + graph

Architecture principle

The data warehouse (star schema) and the graph database (Neo4j) sit side by side, fed from the same source systems. They serve different query patterns. The BI team uses the warehouse for aggregation. The operations team uses the graph for traversal and impact analysis. Shared source data, different analytical models.

Cypher queries for Acme's problems

Supply chain trace — damaged product investigation

// Trace the full chain for a damaged shipment to a specific store
MATCH path = (sup:Supplier)-[:SUPPLIES]->(p:Product)
             <-[:CONTAINS]-(ship:Shipment)-[:SHIPPED_FROM]->(wh:Warehouse),
      (ship)-[:TRANSPORTED_BY]->(tr:Transporter),
      (store:Store)-[:RECEIVED]->(ship)
WHERE store.name = 'MG Road'
  AND p.category = 'TVs'
  AND ship.status = 'damaged'
RETURN sup.name AS supplier, wh.name AS warehouse,
       tr.name AS transporter, p.name AS product,
       ship.ship_date, ship.delivery_date

Product recommendation — co-purchase network

// Find top co-purchased products for a specific item
MATCH (target:Product {name: 'Apple MacBook Air M2'})
      <-[:PURCHASED]-(c:Customer)-[:PURCHASED]->(other:Product)
WHERE other <> target
RETURN other.name, other.category, other.brand,
       count(DISTINCT c) AS shared_customers
ORDER BY shared_customers DESC LIMIT 10

Impact analysis — supplier disruption

// If Samsung delays: which stores and how much revenue is at risk?
MATCH (sup:Supplier {name: 'Samsung'})-[:SUPPLIES]->(p:Product)
      <-[:STOCKS]-(wh:Warehouse)<-[:SERVES]-(store:Store)
RETURN store.name, store.city,
       collect(p.name) AS affected_products,
       count(p) AS product_count
ORDER BY product_count DESC

Transporter damage pattern — graph algorithm

// Find which transporters have the highest damage centrality
// (connected to the most damaged shipments)
MATCH (tr:Transporter)<-[:TRANSPORTED_BY]-(ship:Shipment)
WHERE ship.status = 'damaged'
WITH tr, count(ship) AS damaged_shipments
MATCH (tr)<-[:TRANSPORTED_BY]-(all_ship:Shipment)
WITH tr, damaged_shipments, count(all_ship) AS total_shipments
RETURN tr.name, total_shipments, damaged_shipments,
       round(damaged_shipments * 100.0 / total_shipments, 1) AS damage_rate_pct
ORDER BY damage_rate_pct DESC

Future developments — general

GraphRAG — knowledge graphs for AI

Combining graph databases with LLMs. The graph provides structured context (entities, relationships, hierarchies) that improves LLM accuracy when answering questions about enterprise data. Neo4j provides native vector search alongside graph traversal — enabling hybrid retrieval (semantic similarity + graph context). Gartner Hype Cycle feature for 2024-2025.

neo4j.com/graphrag

GQL standardization

ISO GQL (Graph Query Language) standardized in April 2024. Like SQL did for relational, GQL will enable cross-vendor graph querying. Neo4j's Cypher is GQL-compliant. Amazon Neptune supports openCypher. Portability between graph platforms improves — reducing vendor lock-in concerns.

Graph + warehouse convergence

Neo4j Aura Graph Analytics can run directly on Snowflake/BigQuery/Databricks data. No separate graph database needed for analytics-only use cases. The graph becomes an analytical lens over existing warehouse data rather than a separate data store. Simplifies architecture.

Real-time graph analytics

Streaming data into graph databases via Kafka connectors. Real-time fraud detection, recommendation updates, supply chain monitoring. Neo4j's 15x read capacity improvement (2024) enables real-time workloads that weren't feasible before.

Graph neural networks (GNNs)

ML models that operate directly on graph structure — learning from both node features and network topology. Applications: link prediction (will this customer buy this product?), node classification (is this transaction fraudulent?), graph classification (is this supply chain route at risk?). Research-stage but entering production at scale.

Digital twins as graphs

Physical systems (stores, warehouses, supply chains) modeled as graphs that mirror real-world state in real time. Update the graph as events happen (shipment departs, inventory level changes, transporter reports delay). The graph becomes the operational model, not just the analytical one.

Future for Acme — graph evolution path

Phase 1 → Phase 4

Phase 1 (pilot — month 3-6): Load supply chain data into Neo4j AuraDB. Build supply chain traceability queries. Demonstrate damage root cause analysis via graph traversal. Show the value: "this transporter has 3x the damage rate on this route — here's the visual evidence in Bloom." This builds the case for Phase 2.

Phase 2 (expansion — month 6-12): Add customer-product purchase network. Build co-purchase recommendation queries. Feed recommendations into the loyalty program (Q3). A/B test: stores using graph-based bundle recommendations vs stores using manual bundle selection. Measure revenue lift.

Phase 3 (intelligence — year 2): Graph Data Science algorithms on the full dataset. Community detection on the customer network: find natural customer segments based on purchase patterns (different from RFM — this is network-based segmentation). PageRank on the product network: which products are most "central" to purchase behavior? Similarity algorithms: which stores have the most similar customer bases? (Useful for new product rollout — test in similar stores first.)

Phase 4 (AI integration — year 2-3): GraphRAG: build a knowledge graph of Acme's products, categories, features, customer preferences, and supply chain relationships. Use it to power an AI assistant that store managers can query in natural language: "Which Samsung products are at risk of stockout in the South region next week, and which alternative suppliers can fulfill?" The LLM uses the graph for context, the warehouse for numbers, and returns an actionable answer.

The key message for the assessment

Neo4j is complementary to the data warehouse, not a replacement. It solves specific problems — supply chain traceability, product recommendations, impact analysis, entity resolution — that the star schema handles poorly due to the JOIN-heavy nature of traversal queries. The hybrid architecture (warehouse for aggregation + graph for traversal) is the correct answer. Position Neo4j as an additional analytical layer that enriches the data warehouse investment.
