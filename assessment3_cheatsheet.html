Q1 Case study questions Report

Five sub-questions drawn from the conclusion of the case. Address each one explicitly.

1a. Pitfalls integrating DW with existing IT systems

Identify Acme's heterogeneity problem: multiple ERP vendors, different DB products/versions, inconsistent data definitions across 150+ stores
List specific integration pitfalls: data type mismatches, inconsistent naming conventions (e.g., customer_id vs cust_no), different date formats, duplicate records across systems, missing foreign keys
Propose ETL/ELT as the solution layer — explain how staging area resolves inconsistencies before loading into the warehouse

1b. Design considerations for analytic requirements

Reference the Kimball four-step process from the case: (1) select business process, (2) declare grain, (3) choose dimensions, (4) identify facts
Walk through this for the Retail Product Sales process — grain = transaction line item, dimensions = Date/Product/Store/Customer/Promotion/Geography, facts = quantity/revenue/margin
Reference the Business Matrix (Exhibit 3) — show how each business process maps to dimensions
Discuss star vs snowflake schema trade-offs for Acme's use case

1c. Sizing and hardware estimation

Calculate estimated data volume: 150 stores × ~100 transactions/day × 365 days × average row size
Factor in dimension table sizes (12,000 SKUs × attributes)
Discuss historical retention: grain trade-off from the case — 90 days at transaction level, monthly aggregation for older data
Mention modern alternative: cloud-native (Snowflake/BigQuery) eliminates hardware sizing — pay per usage

1d. Architectural choices

Reference Exhibit 6 directly — compare the four architectures shown: Independent Data Mart, Data Mart with Linked Dimensions, Enterprise DW, Virtual DW
Recommend Enterprise DW + Data Mart (the combined option in Exhibit 6) with justification specific to Acme's multi-store, multi-region structure

1e. Change management & communication

Executive sponsorship (Steve Barley as champion)
Training plan for regional managers — they need to use the analytical tools
Phased rollout: pilot one data mart (sales) → prove value → expand to inventory, warehouse, promotions
Data stewardship — assign ownership of each dimension (who maintains the product master?)

Q2 Warehouse management Report

2.1 Forecasting accuracy (30-40% deviation)

Design a fact_inventory table — grain: one row per product per store per week. Measures: quantity_on_hand, quantity_ordered, quantity_received, stockout_flag
Design supporting dimensions: dim_product (with brand, category hierarchy), dim_store, dim_date (with week/month/quarter for time-series)
Show how OLAP operations on this fact table enable demand pattern analysis — roll-up by category/region to find systematic over/under-forecasting
Propose time-series analysis on historical sales data from fact_sales to generate data-driven forecasts (moving averages, seasonal decomposition)
Be specific: show the star schema ERD for the inventory data mart, not just describe it in words

2.2 Delayed shipments + warehouse estimation

Design a fact_order_fulfillment table — grain: one row per order per fulfillment stage. Measures: picking_time, packaging_time, shipping_time, transport_time, delivery_time, total_lead_time
Dimensions: dim_product, dim_store, dim_warehouse, dim_transporter, dim_date
Show queries that answer the case's warehouse user questions: avg/min/max ship time by store, bottleneck identification by pipeline stage
Present a warehouse architecture diagram: source systems → ETL → staging → data mart → OLAP/reporting

Design a fact_promotion_sales or extend fact_sales with a promotion dimension (which is what the Acme star schema already does)

Q5 Neo4j solution Report

Key framing: Neo4j is not a replacement for the DW — it solves specific graph problems

Identify which Acme problems are graph-shaped: supply chain traceability, product-customer-store relationships, recommendation engines, root cause analysis for damaged shipments.

Define the graph model — nodes: Store, Product, Customer, Warehouse, Supplier, Transporter, Shipment
Define relationships: (Customer)-[:PURCHASED]->(Product), (Store)-[:RECEIVED_FROM]->(Warehouse), (Shipment)-[:TRANSPORTED_BY]->(Transporter), (Product)-[:SUPPLIED_BY]->(Supplier)
Architecture: source systems → ETL → Neo4j AuraDB + relational DW (hybrid approach)
Use cases:
— Supply chain path analysis: trace a product from supplier → warehouse → store → customer
— Recommendation engine: customers who bought X also bought Y (collaborative filtering via graph traversal)
— Root cause for damaged items: traverse shipment → transporter → warehouse → handling stage to identify bottleneck
Show sample Cypher queries for at least 2 use cases
Steps: (1) identify graph-suitable problems, (2) design node/relationship model, (3) define ETL from operational systems, (4) build and load, (5) query and analyze

Q6 MongoDB solution Report

Key framing: MongoDB for semi-structured/unstructured data that doesn't fit the star schema

Acme has customer surveys, customer profiles (demographic + psychographic), product reviews, social media data — these are document-shaped, not tabular.

Identify Acme data suited to document storage: customer survey responses (varying question formats), product reviews (free text + ratings), customer profiles (Exhibit 2 shows CUSTOMER_PROFILE with demographic/psychographic — semi-structured), promotional campaign metadata (mixed media types)
Design document collections:
— customers: embedded profile, purchase history summary, loyalty data
— product_reviews: nested ratings, text, images
— surveys: flexible schema per survey version
Architecture: operational systems → MongoDB (flexible ingestion) → aggregation pipeline → feed into DW or serve directly to applications
Show sample MongoDB aggregation pipeline queries — e.g., average rating by product category, customer sentiment analysis
Steps: (1) identify document-suitable data, (2) design collections and document structure, (3) ingest from sources, (4) build aggregation pipelines, (5) integrate with DW for combined analytics

! Common pitfalls to avoid

Generic answers

Don't write "a data warehouse integrates data from multiple sources." Instead: "Acme's 150 stores use different ERP vendors and DB products. The ETL staging area resolves customer_id vs cust_no naming inconsistencies, standardizes date formats from DD/MM/YYYY to ISO 8601, and deduplicates customer records across store databases using fuzzy matching on name + phone number."

No data models

Every question that mentions "solution" or "architecture" needs a diagram — star schema ERD, architecture diagram, or graph model. Text-only answers will score poorly against the "data-oriented" requirement.

Ignoring the case exhibits

Reference Exhibit 2 (ER diagram), Exhibit 3 (Business Matrix), Exhibit 5 (OLAP operations), Exhibit 6 (architecture alternatives) explicitly. The markers expect to see engagement with the case materials.

Treating Q5/Q6 as replacements for the DW

Neo4j and MongoDB are complementary to the data warehouse, not replacements. Frame them as solving specific problems (graph traversal, semi-structured data) that the star schema can't handle efficiently. A hybrid architecture is the correct answer.

Forgetting the Pilot Data Mart requirements (pages 8-9)

The assessment brief specifically says "taking detailed attention to the information presented in Pilot Data Mart Solution - Key Analytic Requirements." Those bullet-point queries from retail and warehouse users are your requirements spec — your dimensional models should demonstrably answer them.
