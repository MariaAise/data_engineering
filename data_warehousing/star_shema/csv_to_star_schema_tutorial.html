From CSV to Star Schema

A hands-on tutorial — starting from a raw POS export, ending with a working star schema in MySQL Workbench

0 Start with the flat CSV

You are the data analyst for a coffee chain with 12 stores across Melbourne, Sydney, Brisbane, and Adelaide. The POS system exports a CSV file called coffee_pos_export.csv. Here are the first few rows:

transaction_id, transaction_date, transaction_time, store_code, store_name,
city, state, country, item_name, category, subcategory, size,
quantity, unit_price, line_total, customer_name, loyalty_tier
10001, 2024-01-01, 08:15, ST006, Bondi, Sydney, NSW, Australia, Veggie Wrap, Sandwich, Cold, regular, 2, 8.00, 16.00, Noah Brown, Gold
10002, 2024-01-01, 07:00, ST004, George St, Sydney, NSW, Australia, Long Black, Coffee, Black Coffee, regular, 1, 4.20, 4.20, Emma Smith, Gold
10002, 2024-01-01, 07:00, ST004, George St, Sydney, NSW, Australia, Croissant, Pastry, Baked, regular, 2, 4.50, 9.00, Emma Smith, Gold

This is a denormalized flat file — every row repeats the store name, city, state, customer name, etc. This is typical of what POS systems export. It's fine for a spreadsheet. It's terrible for analysis at scale.

17 columns. 1,745 rows. One year of sales data. Your job: turn this into a star schema.

1 What does each row mean?

The first question to ask — always

Look at the CSV. What does one row represent? Not the columns — the row itself.

Look at transaction 10002: it appears twice — once for Long Black, once for Croissant. Same transaction_id, same customer, same time. Two different items.

So one row = one item purchased within one transaction. This is a line item, not a transaction. If this CSV had one row per transaction, the item details would be crammed into a single row somehow (or missing entirely).

This observation is critical. It determines everything that follows.

2 Declare the grain

Write it as a sentence

"One row in my fact table will represent one line item in one transaction at one store on one date."

This is the grain statement — the most important design decision in dimensional modeling. Get this wrong and the entire model is unreliable.

The grain constrains everything downstream: what dimensions are possible, what measures are additive, and what questions the schema can answer.

Could we choose a coarser grain — say, daily totals per store? Yes, but we'd lose the ability to analyze individual transactions, customer behavior, time-of-day patterns, and item-level profitability. Start at the finest grain you have; you can always roll up, but you can never drill down below your grain.

3 Measures vs context — the column sort

Go through every column in the CSV. Each one is either a measure or context:

ColumnTypeWhy

Result: 3 measures, 14 context columns. The measures go into the fact table. The context columns get organized into dimensions.

The test for a measure

Ask: "Would I ever SUM, AVG, or COUNT this column across many rows?" If yes → measure. If no → context. You'd SUM quantity and line_total. You'd never SUM a store name.

4 Group context columns into dimensions

Context columns cluster naturally around real-world entities. Columns that describe the same thing belong in the same dimension table:

dim_store

store_code, store_name, city, state, country

All describe where the sale happened. Contains the geographic hierarchy: store → city → state → country.

dim_product

item_name, category, subcategory, size, unit_price

All describe what was sold. Contains the product hierarchy: item → subcategory → category.

dim_customer

customer_name, loyalty_tier

Describes who bought it. Includes a "Walk-in" row for anonymous transactions (empty customer_name in the CSV).

dim_date

Derived from transaction_date

Describes when it happened. This dimension doesn't exist in the CSV — we generate it. See next step.

The grouping rule

If you're unsure whether a column belongs in dimension A or dimension B, ask: "Does this attribute always travel with entity A, regardless of any transaction?" City always belongs to a store. Category always belongs to a product. Loyalty tier always belongs to a customer. The answer tells you which dimension it lives in.

5 Build dim_date — designed, not discovered

The source CSV has a transaction_date column with values like 2024-01-01. That's just a date string. A proper date dimension enriches this with every attribute you'd ever want to filter or group by:

CREATE TABLE dim_date (
  date_key      INT NOT NULL PRIMARY KEY,   -- 20240101 format
  full_date     DATE NOT NULL,
  day_name      VARCHAR(10),                  -- Monday, Tuesday...
  day_of_week   TINYINT,                      -- 1=Mon, 7=Sun
  month         TINYINT,                      -- 1-12
  month_name    VARCHAR(10),                  -- January, February...
  quarter       CHAR(2),                      -- Q1, Q2, Q3, Q4
  year          SMALLINT,                     -- 2024
  is_weekend    TINYINT                       -- 0 or 1
);
Why generate this?

The date dimension is always designed, never extracted from source data. You generate a row for every day in your date range — including days with zero sales. This enables time-series analysis with no gaps, fiscal calendar alignment, holiday flagging, and rolling period calculations. Every warehouse has a date dimension, and they all look roughly like this.

The date_key is an integer in YYYYMMDD format (e.g., 20240115 for January 15, 2024). This is the standard convention — it's human-readable, sortable, and efficient as a join key.

6 Assign surrogate keys

Every dimension table needs a surrogate key — a new auto-incrementing integer that becomes the primary key. The original business identifiers become regular attributes.

DimensionSurrogate keyBusiness key (becomes attribute)
dim_datedate_key (YYYYMMDD integer)full_date
dim_storestore_key (1, 2, 3...)store_code (ST001, ST002...)
dim_productproduct_key (1, 2, 3...)item_name
dim_customercustomer_key (0, 1, 2...)customer_name
Why not just use store_code as the PK?

Three reasons. (1) Insulation — if the business changes their store coding scheme, the warehouse doesn't break. (2) History tracking — surrogate keys enable Slowly Changing Dimensions (Type 2): the same store_code can have multiple surrogate keys representing different historical versions (e.g., before and after a name change). (3) Performance — integer joins are faster than string joins.

Special case: customer_key = 0 is reserved for "Walk-in" — the unknown customer. When the CSV has an empty customer_name, the fact table points to key 0. Every dimension should have a row for the unknown/not-applicable case.

7 Build the fact table

The fact table contains only two types of columns: foreign keys to dimensions + measures. Nothing else. No descriptive text, no store names, no product categories. If you see a product name in the fact table, something is wrong.

CREATE TABLE fact_sales (
  sale_id        INT AUTO_INCREMENT PRIMARY KEY,

  -- Foreign keys (one per dimension)
  date_key       INT NOT NULL,       -- → dim_date
  store_key      INT NOT NULL,       -- → dim_store
  product_key    INT NOT NULL,       -- → dim_product
  customer_key   INT NOT NULL,       -- → dim_customer

  -- Measures
  quantity       INT NOT NULL,
  unit_price     DECIMAL(5,2),
  line_total     DECIMAL(7,2),

  -- Constraints
  FOREIGN KEY (date_key)     REFERENCES dim_date(date_key),
  FOREIGN KEY (store_key)    REFERENCES dim_store(store_key),
  FOREIGN KEY (product_key)  REFERENCES dim_product(product_key),
  FOREIGN KEY (customer_key) REFERENCES dim_customer(customer_key)
);

This is the star: fact_sales in the center, four dimension tables around it, connected by foreign keys. Every analytical query joins the fact table to one or more dimensions to get context for the measures.

8 The full SQL — create in MySQL Workbench

Open MySQL Workbench and run this script. It creates the database, all four dimension tables, and the fact table with foreign key constraints.

-- ============================================================
-- COFFEE CHAIN STAR SCHEMA
-- From CSV to Star Schema Tutorial
-- ============================================================

DROP DATABASE IF EXISTS coffee_star;
CREATE DATABASE coffee_star;
USE coffee_star;

-- DIMENSION: Date (generated for full year 2024)
CREATE TABLE dim_date (
  date_key      INT NOT NULL,
  full_date     DATE NOT NULL,
  day_name      VARCHAR(10) NOT NULL,
  day_of_week   TINYINT NOT NULL,
  month         TINYINT NOT NULL,
  month_name    VARCHAR(10) NOT NULL,
  quarter       CHAR(2) NOT NULL,
  year          SMALLINT NOT NULL,
  is_weekend    TINYINT NOT NULL DEFAULT 0,
  PRIMARY KEY (date_key)
) ENGINE=InnoDB;

-- DIMENSION: Store
CREATE TABLE dim_store (
  store_key     INT NOT NULL,
  store_code    VARCHAR(10) NOT NULL,
  store_name    VARCHAR(50) NOT NULL,
  city          VARCHAR(30) NOT NULL,
  state         VARCHAR(5) NOT NULL,
  country       VARCHAR(20) NOT NULL,
  PRIMARY KEY (store_key)
) ENGINE=InnoDB;

-- DIMENSION: Product
CREATE TABLE dim_product (
  product_key   INT NOT NULL,
  product_name  VARCHAR(50) NOT NULL,
  category      VARCHAR(20) NOT NULL,
  subcategory   VARCHAR(20) NOT NULL,
  size          VARCHAR(10) NOT NULL,
  unit_price    DECIMAL(5,2) NOT NULL,
  PRIMARY KEY (product_key)
) ENGINE=InnoDB;

-- DIMENSION: Customer (key=0 is walk-in/unknown)
CREATE TABLE dim_customer (
  customer_key   INT NOT NULL,
  customer_name  VARCHAR(50) NOT NULL,
  loyalty_tier   VARCHAR(10) NOT NULL,
  PRIMARY KEY (customer_key)
) ENGINE=InnoDB;

-- FACT TABLE
CREATE TABLE fact_sales (
  sale_id        INT NOT NULL AUTO_INCREMENT,
  date_key       INT NOT NULL,
  store_key      INT NOT NULL,
  product_key    INT NOT NULL,
  customer_key   INT NOT NULL,
  quantity       INT NOT NULL,
  unit_price     DECIMAL(5,2) NOT NULL,
  line_total     DECIMAL(7,2) NOT NULL,
  PRIMARY KEY (sale_id),
  FOREIGN KEY (date_key)     REFERENCES dim_date(date_key),
  FOREIGN KEY (store_key)    REFERENCES dim_store(store_key),
  FOREIGN KEY (product_key)  REFERENCES dim_product(product_key),
  FOREIGN KEY (customer_key) REFERENCES dim_customer(customer_key)
) ENGINE=InnoDB;

9 Load data from CSV

Now we need to populate the dimension tables by extracting distinct values from the flat CSV, then load the fact table by mapping each row to dimension keys.

Step 9a — Populate dim_date

Generate every day in 2024 with derived attributes. Run this in MySQL:

-- Generate 366 rows for 2024 (leap year)
INSERT INTO dim_date
WITH RECURSIVE dates AS (
  SELECT '2024-01-01' AS dt
  UNION ALL
  SELECT dt + INTERVAL 1 DAY FROM dates WHERE dt < '2024-12-31'
)
SELECT
  CAST(DATE_FORMAT(dt, '%Y%m%d') AS UNSIGNED) AS date_key,
  dt AS full_date,
  DAYNAME(dt) AS day_name,
  DAYOFWEEK(dt) AS day_of_week,
  MONTH(dt) AS month,
  MONTHNAME(dt) AS month_name,
  CONCAT('Q', QUARTER(dt)) AS quarter,
  YEAR(dt) AS year,
  CASE WHEN DAYOFWEEK(dt) IN (1, 7) THEN 1 ELSE 0 END AS is_weekend
FROM dates;

Step 9b — Load the flat CSV into a staging table

First, create a temporary staging table that mirrors the CSV structure exactly. This is where the raw data lands before being split into dimensions and facts.

CREATE TABLE stg_pos_export (
  transaction_id   INT,
  transaction_date DATE,
  transaction_time VARCHAR(5),
  store_code       VARCHAR(10),
  store_name       VARCHAR(50),
  city             VARCHAR(30),
  state            VARCHAR(5),
  country          VARCHAR(20),
  item_name        VARCHAR(50),
  category         VARCHAR(20),
  subcategory      VARCHAR(20),
  size             VARCHAR(10),
  quantity         INT,
  unit_price       DECIMAL(5,2),
  line_total       DECIMAL(7,2),
  customer_name    VARCHAR(50),
  loyalty_tier     VARCHAR(10)
);

-- Load CSV using MySQL import wizard or LOAD DATA:
LOAD DATA INFILE '/path/to/coffee_pos_export.csv'
INTO TABLE stg_pos_export
FIELDS TERMINATED BY ','
ENCLOSED BY '"'
LINES TERMINATED BY '\n'
IGNORE 1 ROWS;

Step 9c — Populate dimensions from staging

-- dim_store: extract distinct stores
INSERT INTO dim_store (store_key, store_code, store_name, city, state, country)
SELECT
  ROW_NUMBER() OVER (ORDER BY store_code) AS store_key,
  store_code, store_name, city, state, country
FROM (
  SELECT DISTINCT store_code, store_name, city, state, country
  FROM stg_pos_export
) t;

-- dim_product: extract distinct products
INSERT INTO dim_product (product_key, product_name, category, subcategory, size, unit_price)
SELECT
  ROW_NUMBER() OVER (ORDER BY category, item_name) AS product_key,
  item_name, category, subcategory, size, unit_price
FROM (
  SELECT DISTINCT item_name, category, subcategory, size, unit_price
  FROM stg_pos_export
) t;

-- dim_customer: walk-in (key=0) + distinct loyalty customers
INSERT INTO dim_customer VALUES (0, 'Walk-in', 'None');

INSERT INTO dim_customer (customer_key, customer_name, loyalty_tier)
SELECT
  ROW_NUMBER() OVER (ORDER BY customer_name) AS customer_key,
  customer_name, loyalty_tier
FROM (
  SELECT DISTINCT customer_name, loyalty_tier
  FROM stg_pos_export
  WHERE customer_name IS NOT NULL AND customer_name != ''
) t;

Step 9d — Populate fact_sales by joining staging to dimensions

INSERT INTO fact_sales (date_key, store_key, product_key, customer_key,
                        quantity, unit_price, line_total)
SELECT
  CAST(DATE_FORMAT(s.transaction_date, '%Y%m%d') AS UNSIGNED) AS date_key,
  st.store_key,
  p.product_key,
  COALESCE(c.customer_key, 0) AS customer_key,
  s.quantity,
  s.unit_price,
  s.line_total
FROM stg_pos_export s
JOIN dim_store st   ON s.store_code = st.store_code
JOIN dim_product p  ON s.item_name = p.product_name
LEFT JOIN dim_customer c ON s.customer_name = c.customer_name
                        AND s.customer_name != '';
Why LEFT JOIN for customer?

Walk-in customers have empty customer_name in the CSV. The LEFT JOIN returns NULL for these, and COALESCE(..., 0) maps them to customer_key = 0 (our Walk-in row). Every fact row must have a valid dimension key — no NULLs in foreign key columns.

Step 9e — Drop the staging table

DROP TABLE stg_pos_export;

10 Verify with queries

Run these to confirm the star schema works and produces the same totals as the source CSV:

-- Check row counts
SELECT 'dim_date' AS tbl, COUNT(*) AS rows_ct FROM dim_date
UNION ALL SELECT 'dim_store', COUNT(*) FROM dim_store
UNION ALL SELECT 'dim_product', COUNT(*) FROM dim_product
UNION ALL SELECT 'dim_customer', COUNT(*) FROM dim_customer
UNION ALL SELECT 'fact_sales', COUNT(*) FROM fact_sales;
-- Total revenue should match CSV total
SELECT SUM(line_total) AS total_revenue FROM fact_sales;
-- The payoff: revenue by category by city by quarter
-- This is the query that justifies the whole exercise
SELECT
  d.quarter,
  s.city,
  p.category,
  SUM(f.line_total) AS revenue,
  SUM(f.quantity) AS units
FROM fact_sales f
JOIN dim_date d     ON f.date_key = d.date_key
JOIN dim_store s    ON f.store_key = s.store_key
JOIN dim_product p  ON f.product_key = p.product_key
GROUP BY d.quarter, s.city, p.category
ORDER BY d.quarter, s.city, revenue DESC;
The payoff

That last query — revenue by category by city by quarter — is clean, readable, and fast. Every dimension join is a single integer key lookup. The business question maps directly to the SQL structure. Compare this to writing the same query against the flat CSV: you'd be doing string-based GROUP BYs on repeated denormalized columns with no foreign key integrity. The star schema makes the hard queries simple.
