1 Why your MySQL database isn't enough

You already know how to build a MySQL database. You create tables, define primary keys, set up foreign keys, normalize to avoid redundancy, and write SELECT queries with JOINs. That type of database is called an OLTP system — Online Transaction Processing. It's designed to record things: a sale, a signup, a payment.

But here's the problem. When someone asks a business question like:

"What was our total revenue by product category, by city, by quarter, for the last two years — and how does each quarter compare to the same quarter last year?"

...your normalized OLTP database makes this painful. You need to join 4-6 tables, write complex aggregations, and the query runs slowly because the database is optimized for recording one transaction at a time, not scanning millions of rows.

Think of it this way

Your OLTP database is like a cash register. It's great at recording each sale as it happens. But when the CEO asks "which stores are profitable and which should we close?" — nobody pulls out a cash register to answer that. You need a different tool designed for analysis. That tool is a data warehouse.

OLTP (your MySQL database)

Records transactions as they happen

Normalized (3NF) to avoid redundancy

Optimized for INSERT and UPDATE

Current data (today's state)

Thousands of short queries/sec

Users: clerks, apps, systems

vs
OLAP (data warehouse)

Analyzes historical data for decisions

Denormalized for fast reads

Optimized for SELECT and aggregation

Historical data (years of trends)

Fewer but complex, heavy queries

Users: managers, analysts, executives

2 What is a data warehouse

Bill Inmon, considered the father of data warehousing, defined it as:

"A data warehouse is a subject-oriented, integrated, time-variant, and non-volatile collection of data in support of management's decision-making process."

Let's unpack each word — because they matter:

PropertyWhat it meansMySQL analogy
Subject-orientedData organized around business subjects (Sales, Inventory, Customers) not application functionsInstead of tables per application (POS system, ERP, CRM), you have tables per business topic
IntegratedData from multiple source systems is cleaned, standardized, and combined into one consistent viewIf Store A calls it cust_id and Store B calls it customer_no, the warehouse resolves this into one customer_key
Time-variantKeeps historical data — you can see what things looked like last month, last year, 3 years agoYour OLTP overwrites a customer's address when they move. The warehouse keeps both addresses with effective dates.
Non-volatileWrite-once, read-many. Data is loaded and then only read — never updated or deleted by usersNo UPDATE or DELETE on warehouse tables. This means no transaction locking, no recovery logs — much faster reads.

3 The star schema

The star schema is the fundamental data model in a warehouse. If you learn one thing from this entire lecture, learn this.

The core idea in one sentence

Separate what happened (facts) from the context in which it happened (dimensions).

Fact tables — what happened

A fact table records business events — typically transactions. Each row is one measurable event. The table contains two types of columns:

Foreign keys

Pointers to dimension tables. Together, these form the composite primary key. They define which product, which store, which customer, which date.

Measures (facts)

Numeric values you want to aggregate: quantity, revenue, cost, gross_margin. These are what you SUM(), AVG(), COUNT() in queries.

Dimension tables — the context

Dimension tables describe the who, what, where, when of each fact. They're typically wide (many columns), denormalized, and contain text attributes used for filtering and grouping.

-- This is a dimension table. Notice: lots of descriptive text columns,
-- single-column primary key, no foreign keys to other dimensions.

CREATE TABLE dim_product (
  product_key   INT PRIMARY KEY,     -- surrogate key (warehouse-generated)
  sku_id        VARCHAR(10),            -- natural key (from source system)
  product_name  VARCHAR(60),
  brand         VARCHAR(30),
  category      VARCHAR(30),            -- used in GROUP BY, WHERE filters
  subcategory   VARCHAR(30),
  unit_price    DECIMAL(10,2)
);

Why "star" schema?

When you draw the ERD, the fact table sits in the center with dimension tables radiating outward — it looks like a star. There are no joins between dimensions; every dimension connects only to the fact table.

The Kimball four-step design process

Ralph Kimball developed the standard methodology for designing star schemas:

Step 1. Select the business process (what are you analyzing? Sales? Inventory? Shipments?)

Step 2. Declare the grain (what does one row in the fact table represent? One transaction? One line item? One daily snapshot?)

Step 3. Choose the dimensions (the "by" words in business questions — revenue by product, by store, by month)

Step 4. Identify the facts (the numeric measures — quantity, revenue, cost, margin)

Grain — the single most important decision

The grain defines the level of detail in your fact table. Getting this wrong breaks everything downstream.

Fine grain (transaction line item)

One row per product per transaction. Maximum flexibility — you can always aggregate up. But more rows = more storage and slower queries.

Coarse grain (daily summary)

One row per product per store per day. Smaller, faster. But you lose the ability to analyze individual transactions or time-of-day patterns.

Rule of thumb

Start with the finest grain you can. You can always roll up from transaction-level to daily/weekly/monthly. You can never drill down from monthly to daily if the detail wasn't captured.

Surrogate keys vs natural keys

In your OLTP database, you probably use natural business keys as primary keys — product_id = 'SKU1001', customer_id = 'C10042'. In a warehouse, we add a surrogate key — a system-generated integer that has no business meaning.

Why? Three reasons:

1. Source system independence — if Store A uses P-001 and Store B uses PROD001 for the same product, the warehouse assigns one product_key = 7 to both.

2. History tracking — if a product changes category, you can have two rows in the dimension: product_key = 7 (old category) and product_key = 108 (new category), both with the same natural key.

3. Performance — integer joins are faster than varchar joins.

4 Building a star schema in MySQL

Let's build a complete star schema for a retail electronics company. This is real, runnable MySQL code.

Step 1: The business process is Sales

Step 2: The grain is one row per line item per transaction

Step 3: Dimensions — Date, Store, Product, Customer, Promotion

Step 4: Facts — quantity, unit_price, gross_amount, discount, net_amount, cost, margin

The date dimension (every warehouse has one)

CREATE TABLE dim_date (
  date_key      INT NOT NULL PRIMARY KEY,  -- e.g. 20240315 for March 15, 2024
  full_date     DATE NOT NULL,
  day_name      VARCHAR(10),               -- Monday, Tuesday, ...
  day_of_week   TINYINT,                   -- 1=Mon, 7=Sun
  month         TINYINT,
  month_name    VARCHAR(10),               -- January, February, ...
  quarter       CHAR(2),                   -- Q1, Q2, Q3, Q4
  year          SMALLINT,
  is_weekend    TINYINT DEFAULT 0,
  is_holiday    TINYINT DEFAULT 0
);

-- Why a separate date table? Because you want to GROUP BY month_name,
-- filter WHERE is_holiday = 1, or compare quarters — without parsing
-- dates in every query. The date dimension pre-computes all of this.

The store dimension

CREATE TABLE dim_store (
  store_key       INT NOT NULL PRIMARY KEY,
  store_id        VARCHAR(10),     -- natural key from source system
  store_name      VARCHAR(50),
  city            VARCHAR(30),
  state           VARCHAR(30),
  region          VARCHAR(10),     -- North, South, East, West
  floor_area_sqft INT
);

-- Notice: city, state, region are all in ONE table (denormalized).
-- In your normalized OLTP, these might be separate tables.
-- In the warehouse, we denormalize for query simplicity.

The product dimension

CREATE TABLE dim_product (
  product_key   INT NOT NULL PRIMARY KEY,
  sku_id        VARCHAR(10),
  product_name  VARCHAR(60),
  brand         VARCHAR(30),
  category      VARCHAR(30),      -- Computers, TVs, Mobile Phones, ...
  subcategory   VARCHAR(30),      -- Laptop, Desktop, LED TV, OLED TV, ...
  unit_cost     DECIMAL(10,2),
  unit_price    DECIMAL(10,2)
);

The fact table — everything connects here

CREATE TABLE fact_sales (
  sale_id          INT NOT NULL PRIMARY KEY,
  -- Foreign keys to every dimension:
  date_key         INT NOT NULL,
  store_key        INT NOT NULL,
  product_key      INT NOT NULL,
  customer_key     INT NOT NULL,
  promo_key        INT NOT NULL,
  -- Measures (the numbers you aggregate):
  quantity         INT,
  unit_price       DECIMAL(10,2),
  gross_amount     DECIMAL(12,2),
  discount_amount  DECIMAL(10,2),
  net_amount       DECIMAL(12,2),
  cost_amount      DECIMAL(12,2),
  gross_margin     DECIMAL(12,2),
  -- Foreign key constraints:
  FOREIGN KEY (date_key)     REFERENCES dim_date(date_key),
  FOREIGN KEY (store_key)    REFERENCES dim_store(store_key),
  FOREIGN KEY (product_key)  REFERENCES dim_product(product_key),
  FOREIGN KEY (customer_key) REFERENCES dim_customer(customer_key),
  FOREIGN KEY (promo_key)    REFERENCES dim_promotion(promo_key)
);

Your first star schema query

-- Total revenue by product category by city
SELECT
    p.category,
    s.city,
    SUM(f.net_amount) AS revenue
FROM fact_sales f
JOIN dim_product p ON f.product_key = p.product_key
JOIN dim_store s   ON f.store_key = s.store_key
GROUP BY p.category, s.city
ORDER BY revenue DESC;

-- Notice how clean this is compared to an OLTP query:
-- - Only 2 JOINs (fact → product, fact → store)
-- - No subqueries needed
-- - The GROUP BY matches the business question exactly
-- - Adding more dimensions is just another JOIN

5 The data cube

A data cube is the mental model for multidimensional analysis. Imagine your data as a physical cube:

Each axis is a dimension: Product on one axis, Geography on another, Time on the third.

Each cell contains a measure: the revenue for that product + geography + time combination.

With more than 3 dimensions, it's called a hypercube — impossible to visualize, but the same concept.

The data cube isn't a physical structure you build in MySQL. It's a way of thinking about your data. When someone says "slice the cube on Q4 2024" they mean "filter the time dimension to Q4 2024." The star schema is how you implement the cube in a relational database.

6 OLAP operations

There are five core operations you perform on a data cube. Every analytical question you'll ever ask can be decomposed into some combination of these.

Roll-up (drill-up)

Aggregate to a higher level in a hierarchy. You're zooming out.

Hierarchy: Store → City → State → Region → Country

Roll-up example: You're looking at revenue per store. You roll up to see revenue per city. Then per state. Then per region. Each step reduces detail and increases aggregation.

Also means removing a dimension entirely: if you had revenue by product × city × month, rolling up on city gives you revenue by product × month.

Drill-down

Decompose to a finer grain. The exact reverse of roll-up. You're zooming in.

You see national revenue is down 5%. You drill down to region — South is down 12% while others are flat. Drill down to state — Tamil Nadu specifically. Drill down to city — Chennai store dropped 25%. Drill down to product — TVs in Chennai collapsed. Now you have something actionable.

Slice

Fix one dimension to a single value. You're cutting a single sheet out of the cube.

You have a cube of Product × Geography × Time. You slice on Time = 'Q4 2024'. Now you have a 2D sheet showing Product × Geography for Q4 2024 only.

In SQL: WHERE d.quarter = 'Q4' AND d.year = 2024

Dice

Filter on two or more dimensions. You're cutting a smaller sub-cube from the original.

Show me sales where category = 'Mobile Phones' AND region IN ('South', 'West') AND year = 2024. This creates a smaller cube restricted on three dimensions simultaneously.

In SQL: WHERE p.category = 'Mobile Phones' AND s.region IN ('South','West') AND d.year = 2024

Pivot (rotate)

Swap the axes. Same data, different cross-tabulation. If your rows are months and columns are categories, pivoting puts categories on rows and months on columns.

In SQL, you implement this with CASE expressions — turning row values into column headers. Excel pivot tables do this visually.

7 OLAP in SQL

Modern SQL (including MySQL 8.0) has built-in syntax for OLAP operations. You don't need a separate OLAP server.

GROUP BY with ROLLUP — automatic subtotals

-- Revenue by region and city, with subtotals per region and a grand total
SELECT
    COALESCE(s.region, '*** GRAND TOTAL ***') AS region,
    COALESCE(s.city, '*** Region Total ***') AS city,
    SUM(f.net_amount) AS revenue
FROM fact_sales f
JOIN dim_store s ON f.store_key = s.store_key
GROUP BY s.region, s.city WITH ROLLUP;

-- Output includes:
-- Each city's revenue
-- Each region's subtotal (city = NULL → we use COALESCE to label it)
-- Grand total (both region and city = NULL)
-- This is the ROLL-UP operation in pure SQL.

Slice in SQL

-- Slice: fix the time dimension to Diwali 2024
SELECT
    p.category,
    s.city,
    SUM(f.net_amount) AS revenue
FROM fact_sales f
JOIN dim_date d    ON f.date_key = d.date_key
JOIN dim_product p ON f.product_key = p.product_key
JOIN dim_store s   ON f.store_key = s.store_key
WHERE d.year = 2024 AND d.month = 10 AND d.is_holiday = 1
GROUP BY p.category, s.city
ORDER BY revenue DESC;

Dice in SQL

-- Dice: Mobile Phones + South region + Q4 2024
SELECT
    s.city,
    p.product_name,
    SUM(f.quantity) AS units,
    SUM(f.net_amount) AS revenue
FROM fact_sales f
JOIN dim_date d    ON f.date_key = d.date_key
JOIN dim_product p ON f.product_key = p.product_key
JOIN dim_store s   ON f.store_key = s.store_key
WHERE p.category = 'Mobile Phones'
  AND s.region = 'South'
  AND d.year = 2024 AND d.quarter = 'Q4'
GROUP BY s.city, p.product_name
ORDER BY revenue DESC;

Pivot in SQL

-- Pivot: categories as columns, quarters as rows
SELECT
    d.year,
    d.quarter,
    SUM(CASE WHEN p.category = 'Mobile Phones' THEN f.net_amount ELSE 0 END) AS mobile,
    SUM(CASE WHEN p.category = 'Computers'     THEN f.net_amount ELSE 0 END) AS computers,
    SUM(CASE WHEN p.category = 'TVs'           THEN f.net_amount ELSE 0 END) AS tvs,
    SUM(f.net_amount) AS total
FROM fact_sales f
JOIN dim_date d    ON f.date_key = d.date_key
JOIN dim_product p ON f.product_key = p.product_key
GROUP BY d.year, d.quarter
ORDER BY d.year, d.quarter;

Window functions — trend analysis

-- Monthly revenue with running YTD total and month-over-month growth %
SELECT
    year, month, month_name,
    monthly_revenue,
    SUM(monthly_revenue) OVER (
        PARTITION BY year ORDER BY month
    ) AS ytd_revenue,
    ROUND(
        (monthly_revenue - LAG(monthly_revenue) OVER (ORDER BY year, month))
        / LAG(monthly_revenue) OVER (ORDER BY year, month) * 100, 1
    ) AS mom_growth_pct
FROM (
    SELECT d.year, d.month, d.month_name,
           SUM(f.net_amount) AS monthly_revenue
    FROM fact_sales f
    JOIN dim_date d ON f.date_key = d.date_key
    GROUP BY d.year, d.month, d.month_name
) monthly
ORDER BY year, month;

-- LAG() looks at the previous row's value
-- SUM() OVER (PARTITION BY year ORDER BY month) = running total within each year
-- These are MySQL 8.0 window functions — they work in MySQL Workbench

8 ETL — getting data in

Your data warehouse doesn't generate data — it receives data from source systems (your OLTP databases, ERP systems, CRM, spreadsheets, APIs). The process of moving data from source to warehouse is called ETL.

Extract
→
Transform
→
Load
StepWhat happensExample
ExtractPull raw data from source systemsRead yesterday's transactions from each store's POS database
TransformClean, standardize, resolve conflicts, apply business logicStandardize date formats, deduplicate customers, calculate gross_margin = net_amount - cost_amount
LoadInsert the clean data into the warehouse tablesINSERT INTO fact_sales, update dimension tables with new products/customers

ETL vs ELT

A modern alternative is ELT — load the raw data first, then transform it inside the warehouse using the warehouse's own compute power. This is the dominant approach in cloud platforms where compute is cheap and elastic.

ETL (traditional)

Transform happens on a separate server before loading. Tools: Informatica, SSIS, Talend. Required when warehouse compute was expensive.

ELT (modern)

Load raw data first, transform inside the warehouse. Tools: dbt, SQL-based transformations. Works because cloud warehouse compute is cheap.

The staging area

Before data reaches dimension/fact tables, it lands in a staging area — a temporary holding zone. This decouples extraction from transformation, so if something fails during transformation you don't need to re-extract from source systems.

9 Schema variations

Snowflake schema

A variation of the star schema where dimension tables are normalized into sub-dimensions. Instead of one dim_product table with a category column, you'd have dim_product → dim_subcategory → dim_category.

When to snowflake

Very large dimensions where normalization saves significant storage. When you need strict governance over dimension hierarchies. When dimensions have many shared attributes.

When to stay with star

Almost always. The extra joins in snowflake make queries more complex and slower. The storage saved is rarely worth the query complexity. Star schema is the default recommendation.

Fact constellations (galaxy schema)

Multiple fact tables sharing dimension tables. A retail business might have fact_sales and fact_inventory both referencing the same dim_product and dim_store. This is normal — any warehouse with more than one business process will have multiple fact tables sharing conformed dimensions.

Slowly changing dimensions (SCDs)

What happens when a dimension attribute changes? A customer moves to a new city. A product gets reclassified into a different category.

TypeWhat it doesHowUse when
Type 1Overwrite the old valueUPDATE dim_customer SET city = 'Mumbai' WHERE ...You don't care about history (e.g., fixing a typo)
Type 2Add a new row, expire the old oneOld row gets end_date = today, new row gets start_date = today, new surrogate keyYou need historical analysis (most common)
Type 3Add a "previous" columnAdd previous_city column alongside current_cityYou only need to compare current vs immediately previous (rare)

10 Architecture choices

How do you structure the overall data warehouse infrastructure? There are four common architectures:

ArchitectureHow it worksProsCons
Independent data martsEach department builds its own mini-warehouse in isolationFast, cheap, each team is self-sufficientData silos — Finance and Sales define "revenue" differently. No integration.
Linked dimension data martsSeparate marts but sharing conformed dimensions (same dim_date, dim_customer across all marts)Some integration via shared dimensions. Phased rollout possible.Still decentralized. More complex to manage shared dimensions.
Enterprise data warehouseOne centralized warehouse. All source data flows in. All departments query it.Single source of truth. Full integration and consistency.Expensive. Slow to build. Requires massive upfront commitment.
Enterprise DW + data martsCentral warehouse feeds department-specific marts (best of both)Integration + departmental flexibility. Marts are fast; warehouse is the single source of truth.Most complex. Highest cost.
The Kimball approach (bottom-up)

Build dimensional data marts one at a time, ensuring they share conformed dimensions. Over time, the collection of linked marts becomes the enterprise warehouse. This is the pragmatic approach — delivers value quickly while building toward integration.

The Inmon approach (top-down)

Build the normalized enterprise data warehouse first (3NF model). Then derive dimensional data marts from it for each department. Architecturally pure but takes much longer to deliver the first usable output.

You can build a warehouse in MySQL Workbench for learning. In the real world, organizations use cloud platforms designed for analytical workloads:

The key difference from MySQL

These platforms use columnar storage — data is stored by column, not by row. When your query only needs 3 columns out of 50, a columnar engine reads only those 3 columns. MySQL reads entire rows. This is why a warehouse can scan billions of rows in seconds on queries that would take hours in MySQL.
