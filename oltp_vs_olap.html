OLTP vs OLAP

Same data, two different database designs — side by side in MySQL Workbench

The business question we're answering

"What is total revenue by product category, by city, by quarter for 2024?"

We'll answer this using both an OLTP (normalized) schema and an OLAP (star) schema — same data, same MySQL database — and see why the warehouse design exists.

The two schemas

OLTP Normalized (3NF)

8 tables with foreign keys enforcing relationships. No redundancy — every piece of data stored once. This is what you'd build for a POS or e-commerce app.

oltp_regions
  └── oltp_cities
        └── oltp_stores
              └── oltp_orders
                    └── oltp_order_items
                          └── oltp_products
                                └── oltp_categories
oltp_customers ──┘

To get from order_items to city, you traverse: order_items → orders → stores → cities. Three hops.

OLAP Star schema (denormalized)

5 tables — one fact table in the center, four dimensions radiating out. City and region are baked into dim_store. Category is baked into dim_product. Redundant? Yes. Fast? Extremely.

         dim_date
            │
dim_store ──┤
            │
        fact_sales
            │
dim_product─┤
            │
      dim_customer

To get from fact_sales to city: one JOIN to dim_store. One hop. Done.

The same question, two SQL queries

"Total revenue by product category, by city, by quarter for 2024"

OLTP 6 tables, 5 JOINs
SELECT 
    cat.category_name AS category,
    ci.city_name      AS city,
    CONCAT('Q', QUARTER(o.order_date)) AS qtr,
    SUM(oi.line_total) AS revenue
FROM oltp_order_items oi
JOIN oltp_orders o       ON oi.order_id = o.order_id
JOIN oltp_products p     ON oi.product_id = p.product_id
JOIN oltp_categories cat ON p.category_id = cat.category_id
JOIN oltp_stores st      ON o.store_id = st.store_id
JOIN oltp_cities ci      ON st.city_id = ci.city_id
WHERE YEAR(o.order_date) = 2024
GROUP BY cat.category_name, 
         ci.city_name, 
         QUARTER(o.order_date)
ORDER BY category, city, qtr;

You need to know the full schema to write this. The analyst must understand that cities are in a separate table from stores, that categories are separate from products, and chain the JOINs correctly. Date parsing happens in the query.

OLAP 3 tables, 2 JOINs
SELECT 
    p.category,
    s.city,
    d.quarter,
    SUM(f.net_amount) AS revenue
FROM fact_sales f
JOIN dim_product p ON f.product_key = p.product_key
JOIN dim_store s   ON f.store_key = s.store_key
JOIN dim_date d    ON f.date_key = d.date_key
WHERE d.year = 2024
GROUP BY p.category, s.city, d.quarter
ORDER BY p.category, s.city, d.quarter;

The query reads like the business question: revenue by category (dim_product), by city (dim_store), by quarter (dim_date). Adding another dimension is just one more JOIN. No date parsing — quarter is pre-computed.

Subtotals with ROLLUP

"Revenue by region and city, with subtotals per region and a grand total"

OLTP 5 tables to reach region
SELECT 
    COALESCE(r.region_name, '*** TOTAL ***') AS region,
    COALESCE(ci.city_name, '*** Subtotal ***') AS city,
    SUM(oi.line_total) AS revenue
FROM oltp_order_items oi
JOIN oltp_orders o  ON oi.order_id = o.order_id
JOIN oltp_stores st ON o.store_id = st.store_id
JOIN oltp_cities ci ON st.city_id = ci.city_id
JOIN oltp_regions r ON ci.region_id = r.region_id
GROUP BY r.region_name, ci.city_name
    WITH ROLLUP;
OLAP 1 JOIN — region is in dim_store
SELECT 
    COALESCE(s.region, '*** TOTAL ***') AS region,
    COALESCE(s.city, '*** Subtotal ***') AS city,
    SUM(f.net_amount) AS revenue
FROM fact_sales f
JOIN dim_store s ON f.store_key = s.store_key
GROUP BY s.region, s.city
    WITH ROLLUP;

Monthly trend with growth % — only practical in OLAP

-- This query uses window functions that rely on dim_date.
-- In the OLTP schema, you'd need to parse dates, self-join for the
-- previous month, and calculate growth manually. In OLAP, it's clean:

SELECT 
    d.quarter, d.month_name,
    SUM(f.net_amount) AS revenue,
    ROUND(
        (SUM(f.net_amount) - LAG(SUM(f.net_amount)) OVER (ORDER BY d.month))
        / LAG(SUM(f.net_amount)) OVER (ORDER BY d.month) * 100, 1
    ) AS mom_growth_pct
FROM fact_sales f
JOIN dim_date d ON f.date_key = d.date_key
GROUP BY d.quarter, d.month, d.month_name
ORDER BY d.month;

The takeaway

They're not competing — they're complementary

OLTP records the data. OLAP analyzes it. In a real organization, the OLTP system feeds the OLAP warehouse via ETL (Extract, Transform, Load). You don't replace one with the other — you need both.

OLTP

Use when you need to record a sale, update a customer address, process a return — one row at a time, fast, correct, concurrent.

OLAP

Use when you need to analyze revenue trends, compare regions, find top products — aggregate millions of rows, slice by dimensions, generate reports.
